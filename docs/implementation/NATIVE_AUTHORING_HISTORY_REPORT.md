## Command ownership and grouping

`NativeAuthoring` owns session gameplay history, separate from scene `EditorDocument` history. Commands retain before/after native JSON values, with a monotonic draft revision and current saved-source byte fence. Ability/Effect/action fields and source locators are included. Assignment restores the kit slot, locator map and obsolete-binding cleanup together; binding restores effect catalogue, locator and binding/power together. Multi-source edits can be recorded as one command. Continuous changes to one active ImGui widget coalesce until that interaction ends; discrete edits remain separate. New edits discard Redo. History is bounded to 128 commands/16 MiB; open drafts are bounded to 64.

The embedded Ability workspace exposes Undo gameplay and Redo gameplay beside Save. Drafts and history survive workspace changes. Revert is an undoable command. Save retains history: Undo after Save makes drafts dirty and blocks Play until another Save. Reload explicitly adopts current source bytes, checks UUID/type/schema and clears session gameplay history, retaining other drafts. Stale revision/source commands reject clearly and identify the changed source; external bytes are preserved.

Creation/duplication still persists a fresh source through the existing non-overwriting native API. Creation/deletion is outside draft Undo. Create retains compatible action/schema references; duplicate a shared action before changing its timing independently.

## Coordinated source/cook publication

`AssetService::prepare_native` snapshots the owned mount into a private cache directory, checks optimistic hashes and immutable UUID/type/schema, overlays the changed native sources and uses existing importers/recipes/CAS. Existing source locators identify dependent ability and kit consumers, including unchanged abilities that reference an edited action. Selected scene model/skin/collision/input/kit closure and every changed source are cooked before publication. A frozen candidate manifest checks missing dependencies, shared-product conflicts and the existing 64-root/512-product limits. No source bytes or catalog heads change during preparation; unpublished immutable CAS blobs may remain after rejection.

The current bounded implementation snapshots at most 4096 files/256 MiB, with a cache outside the source mount. It rechecks every snapshot file and conservatively rejects unrelated external changes or additions/removals. Short, exclusively created `cache/ns-*` directories with `s`/`o` subdirectories avoid excessive Windows staging path depth. Dependent discovery uses existing native locators, followed by full native cook validation; unsupported unrelated animation kits need not be cooked in an animation-disabled build.

`commit_native` opens every watched source with Windows sharing exclusion, rechecks its bytes and the inventory, then obtains a SQLite write transaction and rechecks catalog revisions/recipes and CAS digests. Changed files are written and flushed through those protected handles. All selected catalog heads/products/dependencies commit in one SQLite transaction. A normal validation, conflict or publication failure retains/restores prior source bytes and all prior heads. Recovery restores exact originals before releasing file protection. Successful Save updates draft baselines only after commit.

The editor supplies the current selected kit and scene roots to Save. Subsequent Play retains the existing complete package, GPU/input/CharacterPreviewResources and isolated probe preparation before resource replacement, then starts a fresh WorldSession-backed session. Save never patches a live session; it is disabled during Play. Unsaved gameplay drafts still block Play. The previous published runtime registry and immutable leases survive failed candidates.

## Atomicity and recovery limits

Windows sharing exclusion prevents ordinary writers and rename replacements from changing the watched files during commit. An already-open reader/writer can make Save report busy; close it and retry. This is one synchronous writer operation, not a cross-process snapshot protocol for multi-file readers. Readers that finish before commit can retain old source bytes; catalog/package readers in another process need their own snapshot coordination. New files can still be created outside the watched set after its final inventory check; they are preserved and the next inventory refresh revalidates their identities. The ordinary cooker also rechecks its observed head and inputs under the SQLite write transaction, rejecting delayed conversions that would overwrite a newer coordinated head.

Source files and SQLite do **not** share a crash-atomic transaction. Process termination or power loss during publication can leave mixed source bytes with old or new catalog heads. Before source writes, staging retains exact `o/` originals plus `recovery.json` containing source/draft bytes and previous/candidate catalog revisions/recipes. Recovery I/O failure retains that directory and reports its path. A crash also leaves staging on disk. Automatic startup recovery is not delivered: compare current bytes and catalog heads with the journal before manual reconciliation, preserve any later external edits, and recook the complete scene/kit closure. Do not blindly restore originals after a successful catalog commit. Old runtime packages/CAS leases remain immutable, but crash recovery is not qualified by the normal-failure tests.
