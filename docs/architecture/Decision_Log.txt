DARKANGEL ENGINE

Architecture & Decision Log

Version 0.1  |  Updated 7 October 2026



An opinionated, multiplayer-first, stylized 3D action-game engine built from proven frameworks and a custom gameplay/editor layer.



Purpose. This is the living source of truth for DarkAngel Engine architecture. Every major subsystem is marked as Locked, Provisional, or Open. Research rounds are recorded as decision records, and this document should be updated whenever a choice is locked or replaced.

Decision Status

TABLE

END TABLE




1. Engine Identity & Design Principles

Status: LOCKED

DarkAngel is not intended to replace Unity, Unreal, or Godot for every genre. It is an opinionated engine for stylized 3D action games, action RPGs, co-op combat games, and similar experiences.

Use mature open-source frameworks for low-level infrastructure. Spend custom engineering effort on integration, gameplay architecture, authoring workflows, world tools, networking semantics, and the editor.

Multiplayer is architectural, not a later conversion pass. Gameplay systems should declare authority, replication, prediction, and presentation expectations from the beginning.

Fast iteration is a first-class feature: very short native rebuild loops, script hot reload, asset hot reload, and live editor/game iteration wherever practical.

The engine should expose powerful primitives but provide first-class gameplay concepts such as characters, abilities, actions, encounters, checkpoints, world events, navigation, and world-space UI.

The editor and AI agents should manipulate the same command/data model rather than relying on UI automation.

Stylized/toon rendering is the default visual philosophy rather than a secondary mode attached to a realism-first renderer.

2. High-Level Architecture

Status: LOCKED

C++ owns the high-performance engine and editor foundation. Luau is the preferred everyday gameplay scripting language. Gameplay systems such as abilities, effects, Action Composer, characters, encounters and world state sit above the low-level runtime.

TABLE

Layer | Responsibilities

Foundation | Platform, jobs, files, memory, type metadata, serialization, asset IDs, modules, logging.

Runtime | ECS/world, renderer, physics, navigation, animation runtime, audio, networking, UI rendering, scripting host.

Gameplay | Ability/effect/tag framework, Action Composer, character motor, characters, AI, interaction, world state, encounters.

World | Streaming, terrain/mesh landscape, splines, vegetation/scatter, persistence, world events.

Editor | Scene viewport, hierarchy, inspector, asset explorer, specialized designers, debugger/profiler, AI command surface.

Status: LOCKED DAE-004

Decided / Current Direction

C++ implements engine primitives; scripts compose them into game-specific behavior.

Script categories: Entity Scripts, System Scripts and reusable Asset/Behavior Scripts.

Per-entity Update should be opt-in rather than automatically ticking every attached script.

Scripts hot reload with their dependents, preserving supported explicit state through staged migration.

Script-defined reflected ECS component types deferred

7. Animation & Action Composer

Status: LOCKED - DAE-007

Decided / Current Direction

Action Composer blocks should include animation, motion warp, hitbox, projectile, AOE, effect/event, VFX, SFX, camera, combo windows, invulnerability and movement policy.

Gameplay timing should not depend on a monolithic Animator-style state machine.

Locked implementation scope

Pinned Ozz runtime and offline tools; DarkAngel owns Animation Graph and Action Composer.

Selected aim/two-bone IK after blending; presentation IK does not move the gameplay capsule.

Ozz compression first; advanced streaming and alternate codecs require measured need.

Explicit pose layers, action arbitration and immediate gameplay cleanup on interruption.

Separate preview world using the same runtime; simulation-tick timing and required combat bones remain authoritative.

18. Decision Record DAE-001 - Foundation Metadata & ECS Reflection

Status: LOCKED - approved 7 October 2026; implementation validation pending

Question

What should DarkAngel use as the canonical reflection/type metadata foundation that powers ECS component inspection, serialization, network replication metadata, Luau bindings, save-game fields, undo/redo, and the AI/editor property API?

Research Findings

Flecs has a built-in Meta addon for reflecting component data. Reflected types are represented in the ECS world and can describe structs, members, enums, bitmasks, arrays/vectors and opaque types. Flecs also exposes serializer metadata/instructions that can drive custom serializers.

Flecs therefore covers a large part of the runtime reflection need for ECS components and aligns naturally with an ECS-first world model.

C++26 standard reflection is becoming real, but compiler support is still uneven in 2026. Current public support tables show only partial implementation in major compilers, so DarkAngel should not make its core toolchain depend on C++26 reflection yet.

reflect-cpp is a mature C++20/C++26 reflection/serialization library and is attractive for non-ECS data, but making it the canonical engine metadata layer would still require a separate metadata bridge for editor/network/Luau semantics.

Locked Decision

Use Flecs Meta as the low-level reflected representation for ECS component fields. DAE-002 will settle the detailed Flecs world model and integration boundaries.

Define a DarkAngel-owned metadata layer on top of the raw reflection data. DarkAngel metadata owns editor/network/save/script semantics such as Editable, Replicated, SaveGame, ReadOnly, Range, Category, Tooltip and AgentWritable.

Do not make C++26 reflection a hard dependency. The first implementation should work on a stable C++20/23 toolchain. C++26 reflection may later become a code-generation convenience when compiler support is mature.

Do not let Flecs JSON become the permanent save/asset file format by accident. DarkAngel should own versioned schemas and serializers so engine data can evolve independently from any one dependency.

Use code generation or registration macros initially to register DarkAngel component metadata. The generated registration should populate Flecs Meta and all DarkAngel metadata tables from one declaration source.

Target Developer Experience

Conceptual example (syntax not final):

DA_COMPONENT(Health)
{
    DA_PROPERTY(Edit, SaveGame)
    float Maximum = 100.0f;

    DA_PROPERTY(Edit, Replicated, SaveGame, AgentWritable)
    float Current = 100.0f;
};

One declaration should be sufficient to generate or register inspector fields, serializers, network metadata, Luau exposure, undo/redo property transactions and the editor/agent property API.

Decision Rationale

It prevents DarkAngel from having six incompatible reflection systems.

It keeps the public engine API independent of Flecs internals even if Flecs remains the implementation indefinitely.

It gives the editor, networking, scripting and persistence systems a shared type vocabulary from the first milestone.

It avoids depending on compiler features that are still moving.

Implementation Validation Spike

Register Transform, Health and NetworkIdentity components through the DarkAngel metadata macro/codegen path.

Inspect and edit them in a minimal reflection-driven editor panel.

Serialize/deserialize an entity to a DarkAngel-owned versioned format.

Generate a Luau type/API declaration from the same metadata.

Mark Health.Current as Replicated and prove the metadata can be enumerated by a networking stub.

Decision Record DAE 002 ECS and World Model

Status: LOCKED - approved 7 October 2026; implementation validation pending

Locked decision

Commit to Flecs as the ECS backend. DarkAngel owns the World, Entity, Component, Query and System APIs, stable identities, authored scene and prefab formats, and editor commands. Keep the adapter thin: native systems should retain efficient typed iteration rather than copying components through generic property calls. This boundary limits dependency leakage; it does not promise a cost-free backend replacement.

Alternatives and rationale

Flecs provides entity/component queries, relationships, prefab inheritance, Meta reflection and system pipelines with staged structural changes. These built-in mechanisms fit the planned editor, authoring and metadata architecture. EnTT is a credible alternative: its sparse-set ECS offers customizable storage, views/groups and snapshot loaders, while leaving the main loop and scheduling to the application. Choosing Flecs is a fit judgment, not a measured performance win. A custom ECS adds foundation work without a demonstrated need, so it is not recommended for the first slice.

Locked world boundaries

Worlds: maintain separate authoring, play and preview worlds. Starting play instantiates authored data into a fresh simulation world. Stopping play discards runtime mutations; applying selected changes back is an explicit editor transaction.

Scenes and cells: treat scenes as serialized content and streaming cells as load/unload partitions within a simulation world. Do not create a separate ECS world per cell. Local sessions may host separate server and client simulation worlds; headless worlds must not depend on rendering or editor services.

Identity: EntityHandle contains a world token and a generation-checked runtime identifier. Persistent entity IDs and Asset IDs identify durable content; Network IDs identify replicated spawns in a session. Map these identities explicitly rather than saving or transmitting raw Flecs IDs. Exact encodings remain open.

Components: use reflected data and explicit resource handles. Scope borrowed component access to a query or safe access interval; scripts and editor tools must not retain raw component pointers across structural changes. Validate required components through the shared creation and editing command layer.

Relationships: use Flecs hierarchy relationships internally, with DarkAngel-defined transform parenting and deletion semantics. Persistent or cross-cell references resolve through stable IDs and may be unresolved while content is unloaded. A transform parent relationship must not silently imply that every gameplay relationship deletes its target.

Prefabs: DarkAngel owns prefab assets, local entity identities and property override records. Use Flecs prefab/IsA mechanisms where useful, but mutable state such as Health, cooldowns and script state belongs to each instance. Shared configuration is read-only. Detailed nested prefab, variant and live propagation rules remain for the later scene/prefab decision.

Systems: DarkAngel owns explicit simulation phases and authority restrictions; Flecs provides execution/query mechanisms. Begin with single-threaded simulation, staged structural operations and defined merge points. Add parallel native systems after their access and external-library thread-safety contracts are known. Simulation timestep is a later decision.

Commands: editor and agent writes use validated undoable transactions. Runtime systems use typed access and staged commands, without generating editor undo history. Reflected writes must notify relevant consumers; arbitrary raw writes are not automatically observable UI, save or network events.

Validation before broad implementation

The first foundation spike must prove stale and wrong-world handle rejection, scene round-trip with reference remapping, two prefab instances with independent Health, authoring/play isolation, and defined visibility of staged changes. Exercise representative spawn/despawn and query workloads; record results without inventing performance targets. This recommendation does not imply networking, hot reload or streaming already work.

Decision Record DAE 003 Native Build Modules and Hot Reload

Status: LOCKED - approved 7 October 2026; implementation validation pending

Recommended toolchain

Use C++20, CMake and Ninja with checked-in configure, build and test presets. Start with Windows x86-64 and MSVC as the supported editor/runtime toolchain. Record exact tested tool versions in the bootstrap documentation and CI configuration when the skeleton is created; do not follow an unpinned latest release. Use separate build directories for Debug, RelWithDebInfo and Release. Keep optimized builds available for performance checks. Visual Studio or another IDE may consume the same CMake project; the command-line build remains sufficient for Codex.

C++20 is the initial project language level, not a permanent ban on newer features. Require a demonstrated benefit and a compatible dependency/toolchain set before raising it. A clang-cl preset can be added as a secondary check after the MSVC skeleton works. Clang documents clang-cl as an MSVC-compatible command-line interface; this does not justify mixing arbitrary compiler versions, runtime libraries or binary dependencies.

Dependency management

Use vcpkg manifest mode as the default dependency manager, with a pinned vcpkg checkout and registry baseline. A baseline establishes default/minimum versions, not an unconditional lock against transitive requirements; use explicit overrides when exact versions are required and record the resolved dependency set. For libraries whose upstream build or patch requirements are not served by an appropriate port, use one approved source route with immutable commit hashes or archive checksums. Record each exception centrally; do not acquire the same dependency through both routes.

Conan is a credible alternative with CMake integration. There is no measured speed comparison here. vcpkg is recommended for the initial Windows/MSVC workflow and one manifest-based dependency graph. FetchContent alone is another viable route for source integration, but leaves more packaging and shared dependency policy to our CMake code. Validate actual ports, licenses and build options as each subsystem is chosen; this record does not assert that every candidate library is already covered.

Module boundaries

Foundation: platform abstraction, logging, memory, files, jobs, IDs and canonical type metadata. No dependency on renderer, gameplay or editor.

Runtime: World/Flecs integration, asset services and adapters for physics, renderer, animation, navigation, audio, scripting and UI. Keep adapters in separate targets so a change does not rebuild unrelated source.

Gameplay: native ability, action, character and world frameworks depend on foundation/runtime interfaces. Ashen Roots supplies Luau scripts, authored assets and game configuration, with optional native extension targets only where necessary.

Editor and tools: editor-specific commands, inspectors, authoring and import/cook utilities depend on runtime APIs. Runtime and server code must not link editor functionality. Headless targets omit graphics and window initialization.

Targets: define separate editor, game runner, headless simulation/server and test executables. Share internal library targets. Introduce these targets progressively with the slice rather than requiring every subsystem to exist in the first commit.

These are ordinary CMake library and executable targets, not C++20 language modules. Start with static internal libraries and ordinary headers/source files. Use narrow public headers, forward declarations, private dependency includes and selective precompiled headers. Measure build times before adopting unity builds or compiler caches. The static-first layout reduces binary lifetime and ownership complexity; it does not itself provide native hot reload.

Iteration and hot reload contract

Luau and authored data: changes should be reloadable without rebuilding the native core. DAE-004 defines script state, callback and coroutine handling. Asset, shader and UI reload semantics belong to their subsystem decisions; these are requirements, not features already proven.

Native implementation changes: the baseline is incremental compile/link followed by process restart. Keep editor layout, selection and open asset state outside native object lifetimes so restart recovery is possible. Do not promise transparent preservation of a running fight.

Optional patching: Live++ is a licensed Windows development option, not a mandatory dependency or shipping requirement. Validate compatible build flags, compiler/linker settings and patch hooks before enabling it. Function changes may be patched, but layouts, virtual tables and resource registrations can require migration or restart.

Structural changes: restart is the default for changed component layout, reflected schema, ABI, allocator assumptions, third-party integrations or initialization contracts. Versioned disk schemas support loading saved data; they do not migrate existing C++ objects automatically.

Custom DLL reloading: defer it. If needed later, expose a versioned C-compatible entry point with explicit host ownership, registration tokens, shutdown and migration hooks. Stop jobs and calls, detach systems/callbacks, and release plugin-owned resources before unloading code. Recompiling and swapping a DLL alone is insufficient.

Multiplayer: do not independently patch authoritative logic during a connected test. Restart/reconnect the test session after native simulation changes; synchronized live logic updates require a separate networking design.

Why this recommendation

CMake presets provide a shared command-line and IDE entry point. Ninja is a supported CMake generator. MSVC keeps the first Windows workflow focused; clang-cl remains an available second compiler. Visual Studio Hot Reload requires particular debug/link settings and excludes layout changes, optimized debugging and updates to static libraries. Live++ supports broader patching, including optimized builds, but its documentation requires explicit migration for structural changes. This makes script/data reload plus fast native rebuilds the defensible baseline. It does not establish a seconds-level rebuild or reload guarantee.

Validation for the first skeleton

Prove a clean checkout configures, builds and runs a foundation test through presets on Windows without an IDE. Build the editor/runner shell and a headless target without graphics/editor dependencies. Verify the pinned dependency setup and a second no-change build. Measure cold build, no-change build and one-source-file incremental build on the development machine. Confirm edits do not recompile unrelated targets unnecessarily. Check restart recovery for editor state when that shell exists. Treat Live++ as a separate optional spike, not a gate on the first slice.

Deferred details

Exact tool versions, the initial dependency list, cross-platform CI, binary cache provider, standalone SDK packaging, native plugin ABI and custom DLL migration remain implementation or later decisions. Linux/headless portability should influence interfaces now, without claiming Linux editor support in the first milestone.

Decision Record DAE 004 Luau Integration and Script Hot Reload

Status: LOCKED - approved 7 October 2026; implementation validation pending

Language and embedding

Commit to Luau for everyday gameplay scripting, using its public VM and compiler APIs behind a DarkAngel ScriptRuntime. Pin compiler, VM and analyzer to the same tested release or source revision. Begin with interpreted bytecode; native code generation is an optional optimization after profiling. Compile source inside the trusted toolchain and load only matching generated artifacts. DarkAngel owns scheduling, lifecycle, bindings and reload behavior; these are not automatic language features.

Use one VM per world execution domain, not per entity. Separate authoritative simulation, client presentation and editor tooling domains, each with its own host capabilities and module cache. Server and client worlds never share a VM. Initial VM execution stays on its owning thread. Luau coroutines provide cooperative execution, not parallel CPU work; background native jobs return results through a scheduler queue. Per-module environments and read-only APIs limit accidental interference but do not establish complete isolation for untrusted extensions.

Script authoring model

Entity scripts attach to an entity and receive a context, serialized configuration and explicit instance state. System scripts register queries and scheduled work across entities. Asset scripts provide reusable conditions or behavior callbacks invoked by native frameworks.

Modules return immutable definitions or exports. Top-level evaluation must be free of gameplay mutations, subscriptions, timers and background work. Mutable shared state belongs to an explicit world/system service, not hidden module globals or persistent closure upvalues.

Update and fixed-tick registration are opt-in. Bindings receive world-scoped, generation-checked entity userdata and validated asset handles rather than raw pointers or 64-bit IDs converted to floating-point numbers.

Expose generated typed component accessors and registered service APIs for World, Physics, Abilities, Audio and UI. Native component schemas remain the first-slice canonical model. Scripts may store custom tables and serialized configuration; script-defined reflected ECS types are deferred.

Entity deletion, script disable and world shutdown release owned subscription, timer, task and resource tokens. A resource that must survive the script belongs to a native/world service with an explicit lifetime. Garbage collection is not the gameplay teardown mechanism.

Modules and tooling

Use statically resolvable string require paths with project/package aliases and relative imports. Resolve these to Script Asset IDs through the asset database. The editor analyzer and cooked runtime must use the same mapping. Require calls load definitions synchronously and do not yield. Reject dependency cycles and computed require paths in the first supported authoring model; load selectable behavior assets through an explicit host API. Own the dependency graph and generation cache, using Luau Require public resolver/cache APIs where suitable.

Strict type checking is the project default. Generate engine type definitions and API documentation from DAE-001 metadata plus explicit service/method descriptors, and load the same definitions into the analyzer and luau-lsp. Disable Roblox-specific defaults for DarkAngel projects. Runtime validation remains necessary because Luau types are checked statically, not enforced as host authority rules. Dynamic property-by-name tools may use a generic API, while gameplay should use typed accessors.

Reload contract

Reload is a generation change for the edited module and its transitive dependents. Re-evaluating dependents avoids leaving cached imported functions bound to old implementations. Engine subscriptions retain owner/generation identifiers; scripts cannot keep old function values inside persistent state. The reload set may be larger than one file, but does not restart the entire world.

Prepare: detect the change, resolve the affected dependency graph, type-check and compile candidates. Report syntax, type and import errors without replacing the active generation.

Stage: load candidate definitions into a separate generation cache with gameplay writes disabled. Clone each affected instance state using the supported value schema. Run a pure migrate(previousVersion, oldStateCopy) callback when the state schema changes, then validate the result. Resolve registration declarations into staged subscriptions without activating them.

Commit: at a simulation safe point with no affected script call executing, replace definitions and state, detach the old registrations, cancel old tasks and activate the staged registrations. A preparation or migration failure leaves the old code, state and tasks active.

Resume: run an optional post-reload hook through protected execution. Errors after commit disable the affected instance and report diagnostics; they cannot automatically undo prior gameplay mutations. Reloading the same generation must not duplicate subscriptions.

State boundary: preserve supported scalar values, value types, nested acyclic data tables and stable entity/asset references. Exclude functions, coroutine stacks, raw pointers and resource userdata. Validate unresolved references after restore. Native ECS gameplay state such as Health remains in the world and is not copied into script state merely for reload.

All prepare/migrate hooks must obey the restricted API, with no externally visible side effects. This is the locked protocol to prove in a spike, not a claim that arbitrary Luau objects can be cloned or that every reload is instantaneous. SaveGame fields are an explicit subset of reload state; durable saves store schema versions and stable references, not an entire VM heap.

Coroutines authority and errors

Provide host-managed tasks, simulation-time waits and event waits with owner cancellation tokens. Allow yielding only in scheduled task entry points; lifecycle, damage/ability validation and migration callbacks are synchronous. On reload, cancel suspended tasks rather than transplanting their execution stacks. Long-running gameplay must keep progress in explicit state and intentionally resume/restart from that state. Existing native abilities/actions keep their own execution state unless an explicit cancellation policy says otherwise.

Every native mutation checks the execution domain, entity validity and authority. Server scripts change authoritative gameplay; client presentation scripts issue allowed requests and manipulate local presentation. Permissions are host enforcement, not an isServer branch. Use simulation time and seeded host random services for simulation logic, without claiming cross-platform determinism or rollback support. Defer connected-session authoritative script reload until networking defines coordinated code updates; restart the test session initially.

Use protected calls, source/line diagnostics and stack traces. Fail a faulty instance/task without stopping unrelated scripts, with repeated errors suppressed. Catching a runtime error does not reverse mutations already applied. Interrupt budgets handle runaway Luau loops, while expensive native bindings need separate limits; memory quotas apply to a VM/domain rather than pretending shared allocations can always be charged exactly to one entity. Treat out-of-memory domain recovery as distinct from an ordinary script error.

Debugging and validation

The first slice needs clickable diagnostics, per-script execution timing, task/subscription inspection and VM memory metrics. Luau exposes breakpoint and stepping hooks, but DarkAngel must provide the debugger integration. Defer a full editor/DAP debugger until after the reload spike; preserve source names and debug information now. Do not equate language-server autocomplete with a runtime debugger.

Validate two independent entity instances, server/client separation, typed host access, stale handle rejection, cached-import dependent reload, failed compilation/migration retaining old behavior, state migration, no duplicate callbacks, cancellation of an event-waiting coroutine, entity-deletion cleanup and an interruptible infinite loop. Verify analyzer/runtime alias agreement and a cooked headless script load. Measure reload latency and allocation behavior on the development machine.

Decision Record DAE 005 Renderer Abstraction and Rendering Architecture

Status: LOCKED - approved 7 October 2026; implementation validation pending

Backend choice and ownership

Use DiligentCore as the graphics backend, pinned to a tested revision with required submodules and tools. Start with D3D12 on Windows and validate the same renderer on Vulkan early. Build only required targets; selectively reuse DiligentTools and DiligentFX where their contracts fit. DarkAngel owns the render scene, graph, materials, lighting and stylized passes. Diligent provides graphics mechanisms, not the Ashen Roots visual style or a finished game renderer.

Diligent exposes pipeline/resource signatures, compute, resource reflection and automatic or explicit transitions. bgfx is a credible alternative with compute and indirect drawing, but its view-based, sorted submission model and shader toolchain are a less direct fit for the proposed explicit graph. Direct D3D12/Vulkan offers full control but makes backend synchronization, allocation and portability DarkAngel work. This is an architectural fit judgment, not a benchmark claiming Diligent is faster.

Keep Diligent objects inside the rendering module. Expose DarkAngel mesh, texture, material and view handles to assets, gameplay and editor APIs. Avoid building a second complete graphics abstraction that mirrors every Diligent call; use small adapters at actual ownership boundaries. Native D3D12/Vulkan access remains a contained backend integration escape hatch.

Apple support is deferred by explicit scope decision and is not required for the current engine milestone. Diligent lists its native Metal backend under a commercial license; any future Apple target needs a separate licensing/backend evaluation. No mobile, browser or console support promise follows from the initial Windows decision. Query device features and formats; advanced capabilities such as bindless, mesh shaders and ray tracing are optional, not baseline requirements.

Render scene and frame ownership

Extract a render snapshot from the world after simulation updates: transforms, meshes, material instances, lights, cameras and animation outputs. Renderer code does not mutate gameplay ECS state or hold pointers into its component storage. Stable render handles and explicit asset generations connect snapshots to GPU resources. Multiple views share scene resources but own camera, visibility and view targets. The same path serves game, editor and previews; headless servers construct no graphics device.

Begin with one CPU owner for recording/submission and one graphics queue; compute passes execute on that queue. Background file reads and shader compilation may prepare candidates, with GPU creation/activation on the permitted owner. Separate render threading, parallel command recording and async compute require profiling and explicit scheduling contracts later. Bound frames in flight and reuse upload/frame buffers only after completion; retire replaced resource generations after their final GPU use.

Minimal explicit render graph

Build a small DarkAngel graph with declared passes, resource reads/writes, attachment load/store behavior, and imported versus transient resources. Compile dependencies, reject cycles and reads before initialization, track relevant subresources and emit transitions through Diligent. Start with a predictable pass list, one queue and pooled textures; defer physical memory aliasing and async scheduling. One layer owns resource state changes: graph-managed resources use explicit transitions with verification, rather than competing automatic state changes in arbitrary draw code.

Initial view passes: uploads; shadow maps; depth and optional normal/outline-mask prepass; light-list compute; opaque/masked stylized forward shading; sky and optional opaque screen effects; transparent geometry/VFX; integrated outline, fog and post stages as their inputs require; tone mapping; screen UI/editor overlays; present. View-local resources and per-view dependencies make this a graph rather than a single global sequence. Render-target UI is produced before scene materials that sample it, and world UI participates in the appropriate scene pass. Reject feedback cycles in the first slice.

Use single-sample scene targets initially, with a simple optional spatial anti-aliasing pass. Defer default TAA until motion vectors, history invalidation and stylized ghosting are validated. Optional MSAA needs an explicit resolve and depth/normal sampling design. Use linear HDR scene color, explicit texture color-space metadata and one output conversion. Screen UI follows scene tone mapping. Define reversed-Z scene depth with a zero-to-one clip-depth contract; test projection, winding, UV orientation and reconstruction on both backends. Shadow depth may use its own documented convention.

Lighting and material model

Choose clustered forward as the target: screen tiles plus depth slices assign local light lists, and opaque and transparent materials evaluate only relevant lights. A small forward light loop is acceptable for the first triangle/material proof, followed by a clustered implementation in the renderer spike. Build conservative full-frustum clusters so lights on transparent surfaces are not lost through opaque-only depth occupancy. Use explicit finite lighting range and a fallback for surfaces beyond it. Light-list limits require deterministic selection, overflow counters and visible diagnostics; silent truncation is unacceptable.

Separate light count from shadow cost. Begin with one directional light and cascaded shadow maps, plus bounded unshadowed point/spot lights. Add a budgeted spot-shadow atlas after that path works; shadowed point lights, virtual shadow maps and ray-traced shadows are deferred. Expose shadow distance, resolution, bias and caster budgets; test animated and alpha-masked casters. Start indirect light with authored ambient/hemisphere lighting and environment reflection. Lightmaps/probes and dynamic GI are later decisions, not requirements for this slice.

Author versioned Material Definitions and Material Instances. Definitions select a native shader family, parameter schema and render state; instances carry typed values and asset references. Initial families: StylizedLit, Unlit and TransparentVFX, with opaque/masked variants. Support ramps, shadow tint, rim, emissive and normal inputs; keep an optional specular lobe. Treat banding and colored multiple-light accumulation as an artistic policy validated on Ashen Roots reference scenes. A painterly finish requires authored texture and shading work, not merely a post filter.

Bound shader variants to declared features and cache their full keys. Use shared deformation and alpha-test rules in depth, shadow and color passes. Begin with depth/normal outlines and per-object width/color/mask controls; thin geometry and overlap need a visual test. Inverted-hull outlines are an optional family-specific path. CPU frustum culling, LOD selection, material sorting and instancing are the baseline. GPU culling/indirect submission, general material graphs, advanced decals, volumetric fog, water simulation and full vegetation rendering are deferred; preserve extension points for their subsystem decisions.

Shader build and reload

Use HLSL and a pinned DXC toolchain for D3D12 DXIL and Vulkan SPIR-V. Start from the common tested subset, with explicit resource signatures, buffer layouts and matrix conventions. Compile-time reflection validates host layouts and material schemas. Cache keys include source and transitive include hashes, entry point, defines, target/backend, compiler version, binding layout and relevant render state. Cook backend-specific shader artifacts and declared variants; shipped builds do not require source recompilation.

Diligent provides render-state packaging and a cache with shader/pipeline reload support. Evaluate these as backend utilities, while DarkAngel owns candidate validation and activation. A changed include rebuilds dependent shaders/pipelines. Keep the last working generation on compilation or pipeline-creation failure. Activate compatible candidates at a frame boundary and keep old objects until GPU completion. Resource-layout changes require rebuilding all affected bindings and migrating material data as one validated replacement; reject an incomplete migration. Offline packages do not eliminate driver-time pipeline creation or guarantee zero stutter; prewarm known scene variants and measure.

Validation and deferred choices

Spike gates: D3D12 and Vulkan render the same small scene with a moving/skinned character, masked foliage, overlapping colored lights, cascaded shadows, outlines and transparent combat effects. Test light-list overflow and transparent depth coverage; resize/minimize, multiple views, picking, render-target UI, failed shader reload, include reload and layout-change rejection/migration. Capture named passes and verify barriers/resource lifetimes with backend validation. Confirm headless builds have no graphics initialization.

Measure CPU extraction/submission, GPU pass timings, upload and VRAM use, variant counts, pipeline startup and reload latency. Record hardware, driver, resolution and scene density; include integrated graphics if available rather than inferring a hardware minimum from API names. Define budgets from the vertical slice measurements. Backend selection is locked; performance and portability remain implementation validation. Exact cluster sizes, formats, shadow settings, anti-aliasing quality and final art response are tuning outcomes.

Decision Record DAE 006 Physics Simulation and CharacterMotor

Status: LOCKED - approved 7 October 2026; implementation validation pending

Backend and movement ownership

Use a pinned Jolt Physics revision behind DarkAngel PhysicsWorld, body handles and query APIs. Each simulation world owns its physics system; scene/cell partitions contribute bodies to that system. Authoring and preview worlds remain separate. Use meters, seconds, kilograms and a documented Y-up/right-handed math contract, with tested asset/shader conversions. Keep Jolt identifiers and serialization internal; persistent and network identities remain DarkAngel-owned.

Build the native DarkAngel CharacterMotor on Jolt CharacterVirtual collision movement. It is controlled through queries rather than ordinary dynamic-body integration, providing suitable timing control for action movement. PhysX also supplies a viable kinematic controller; there is no measured performance claim here. Reuse Jolt collision handling before attempting a custom sweep solver. Ordinary dynamic bodies remain appropriate for props and ragdolls, not the default player movement authority.

DarkAngel owns input interpretation, acceleration, braking, gravity/jump policy, rotation, stance modifiers, movement modes and motion arbitration. Player commands and AI movement intents use the same motor API. Store desired and achieved movement separately, plus support, velocity, shape, mode and action identifiers. Only the motor writes a living character collision transform; teleport, respawn and reconciliation use explicit motor operations.

Fixed clock and update phases

Start with a 60 Hz authoritative simulation clock, independent of rendering. The tick duration is fixed for a session and versioned in configuration; do not change it automatically with frame rate. Use a monotonic tick index, timestamped input commands and tick-based gameplay timers. Rendering interpolates completed simulation states; camera/presentation prediction may reduce perceived delay without feeding interpolated positions back into collision.

Use an accumulator with a bounded catch-up work budget and explicit debt/overload diagnostics. A slow frame never becomes one oversized physics step. Retain outstanding simulation debt while limiting work per render frame; if a client falls outside retained history, resynchronize. Server overload is reported and handled by a session policy, not silent skipped gameplay ticks. Offline pause/debug stepping is explicit; multiplayer menus do not pause the authoritative world.

Initial phase contract: apply queued structural/physics changes and tick inputs; evaluate ability/action state and kinematic platform target velocities; compute movement requests and tick root-motion deltas; update virtual motors in stable character order against the start-of-tick world; run one Jolt physics step; read dynamic results and reconcile support/contact data; evaluate tick collision/hit/trigger queries and queued gameplay events; commit gameplay changes and publish snapshot/history. Mutations resulting from events enter their declared safe phase. No arbitrary ECS or Luau execution occurs inside Jolt callbacks.

The motor-before-physics schedule follows the Jolt character sample as the initial baseline, not a guarantee of perfect moving-platform behavior. Validate descending elevators, rotation and dynamic contacts before finalizing the implementation. A post-step support refresh must not move the character for a second full tick. Start with one physics collision step per tick and a single-thread execution path consistent with DAE-002. Extra collision substeps and internal physics workers are later measured choices; neither changes gameplay tick duration.

Collision representation and query contract

A virtual controller alone is not visible to ordinary physics queries. Use an inner/proxy body for query visibility and selected rigid-body interaction, plus Jolt virtual-character collision support for motor-to-motor collision. Define filtering so a character never collides with itself or resolves another character twice through both proxy and virtual paths. Combat hurtboxes are separately authored shapes tied to character identity; deduplicate results when a query encounters multiple representations.

Expose ray, shape-cast and overlap queries with layer, owner, trigger and backface policies. Return world-scoped validated handles, subshape/material data and hit fraction/normal. Use bounded collectors with overflow diagnostics and deterministic tie ordering where gameplay depends on result order. Queued collision events copy safe identifiers/data before the callback returns. Unify rigid-body and virtual-character event sources at the host level; a raw contact removal is not automatically a gameplay trigger exit, especially around sleep or destruction.

Cook collision meshes/shapes as versioned assets. Prefer simple/convex dynamic shapes and authored static meshes for caves and architecture. Filter movement blockers separately from targeting and damage recipients. Fast projectiles use tick sweeps and explicit impact policy; selected fast dynamic bodies use appropriate CCD. A dash/warp uses swept collision movement, not SetPosition through a wall. PhysicsWorld creation, streamed body insertion/removal and shape changes occur at tick boundaries; do not unload collision under active/predicted players.

Grounding platforms and shape changes

Tune slope limits, step height, ground snapping, skin/padding and recovery as motor settings. Use ExtendedUpdate as the starting implementation; enable stair stepping and floor adhesion only for modes that permit them. Jumping, launch and airborne dash must not be snapped down. Coyote time and buffered jump are explicit tick state, not inferred from presentation. Use bounded depenetration; an invalid spawn or irrecoverable overlap falls back to a validated safe pose with diagnostics.

Kinematic platforms are simulation-driven bodies with tick target transforms/velocities, never render-frame teleports. Track support identity, local contact point and platform tick state. Inherit contact-point velocity, including angular motion, once. Do not also parent/add the same platform displacement. Platform-induced yaw is a configurable gameplay policy. Jump/detach inherits a defined velocity once and clears support. Teleport, removal, crushing and blocked carry have explicit detach/recovery rules. Test both ascending and descending platforms; general moving-world/local-gravity support is deferred.

Slide/crouch switches a cached collision shape while preserving the foot position. Expansion requires clearance; remain in a low stance while blocked. Update proxy/hurtbox representation consistently after a successful shape change. Collider changes are ticked motor state and included in correction history. Keep separation and character pushing bounded; define player/ally/enemy collision policy independently from damage filtering. Use server-owned limits for impulses applied to dynamic props; replayed client movement never reapplies authoritative prop pushes.

Root motion actions and traversal

Action Composer produces tick-time motion requests; CharacterMotor resolves them against collision and returns achieved displacement. Define requests for desired velocity, additive impulse, bounded displacement/root motion, rotation and movement locks. One declared owner controls each channel, with explicit priorities/cancellation. Locomotion, actions and external forces cannot all overwrite velocity in unspecified order. A blocked lunge does not accumulate hidden displacement to apply later.

Root-motion deltas are sampled from authoritative action time or cooked curves at fixed ticks, independent of render-pose evaluation. Motion warping adjusts a bounded requested path toward a validated target, still collision-checked throughout. Visual animation/IK follows achieved motion; foot IK does not move the gameplay capsule. Animation details belong to DAE-007, but movement ownership is established here.

Traversal is a motor mode/action adapter: probes validate entry, required clearance and a swept path; motor executes collision-constrained movement with explicit entry/exit and interruption. Begin with the APIs needed for jump/dash/slide and leave vault/mantle/clamber as staged features. Do not rebuild the entire Unity traversal set for the first slice. Teleport is a separate validated discontinuity that resets support, interpolation and incompatible prediction history.

Prediction and physics scope

Use server-authoritative motor results with owner prediction and correction hooks. InputCommand and MotorState carry tick/sequence and validated movement parameters. On correction restore the acknowledged motor/action state, replay unacknowledged commands using the same fixed-tick motor path, and smooth only the visual offset. Remote characters and props interpolate authoritative snapshots. Position alone is insufficient: velocity, mode, shape, support, timers, action phase and relevant modifiers affect replay.

Replay requires a dedicated collision context with retained static collision versions and tick-indexed kinematic platform/obstacle states. Never rewind or mutate the live physics world during owner replay. Unpredictable dynamic bodies and other characters use authoritative collision proxies with correction; full coupled rigid-body rollback is deferred. History expiry or a topology/version mismatch forces resynchronization. Platform prediction and collision streaming are explicit acceptance gates; precise snapshot transport and lag compensation remain the networking decision.

Do not equate Jolt determinism with whole-engine determinism. Matching build/configuration, mutation ordering, query/event ordering, world history and host gameplay state all matter. Jolt physics snapshots omit virtual-character state unless it is saved separately, and they are not portable DarkAngel save games or network packets. Begin without requiring cross-platform lockstep. Save/restore and repeated motor replay are validation tools; enabling stricter deterministic physics builds is a measured later choice.

Validation before implementation commitment

Spike scene: stairs, seams, steep slopes, tight corners, low ceilings, elevator and rotating platform, movable crate, multiple characters and thin-wall dash. Test jump buffering, stance changes with blocked standing, knockback, collision-constrained root motion, proxy query visibility, duplicate-hit prevention, sensor events, safe spawn/teleport and support removal. Measure grounded jitter, achieved displacement, query overflow and CPU/allocation cost. Compare behavior at 30/60/144 rendering FPS with the same 60 Hz simulation.

Network spike: owner movement against static geometry and moving platforms under delay/loss; correction and command replay without duplicate actions, effects or prop impulses. Test missing history and streamed collision changes. Confirm headless movement uses no renderer or visual animation dependency. Record settings and hardware; measure before parallelizing. Backend, ownership and tick contracts are locked; movement feel, platform scheduling details and final budgets remain spike validation.

Decision Record DAE 007 Animation Runtime and Action Composer

Status: LOCKED - 7 October 2026

Library choice and ownership

Use a pinned ozz-animation revision for skeletal sampling, blending, masks, additive animation, local-to-model conversion and selected IK/motion utilities. DarkAngel owns graph execution, action scheduling, assets, sockets, retargeting policy and editor tools. Ozz is a low-level animation library, not a finished blend-tree system or renderer. GPU skinning belongs to the DAE-005 renderer. Build runtime libraries separately from offline conversion tools and samples.

ACL is a credible compression/decompression alternative to evaluate if measured clip memory, sampling cost or error warrants a change. It does not replace the proposed graph/action architecture. Begin with Ozz compression and optimization rather than combining two codecs immediately or writing a custom sampler. Keep clip handles and cooked asset metadata independent of codec-specific objects; no claim that Ozz outperforms ACL is made without Ashen Roots benchmarks.

The Animation Graph computes persistent locomotion/posture and pose composition. Action Composer runs discrete authored actions on the simulation clock and submits pose layers, motor requests and typed gameplay/presentation events. Ability System owns activation validation, costs, effects, tags and damage resolution. CharacterMotor owns collision movement. Visual animation callbacks never become the source of combat authority.

Assets and import contract

Define versioned Skeleton, Clip, JointMask, AnimationGraph and ActionDefinition assets. Skeletons carry hierarchy/rest transforms, stable named joint keys, sockets and a compatibility signature. Clip metadata records skeleton signature, duration, loop policy, additive reference, root-motion policy and codec/tool revision. Mesh skin indices and inverse bind matrices use an explicit remap to cooked skeleton order; reject mismatched hierarchies or missing required sockets.

Use glTF/GLB as the first supported skeleton/clip interchange, importing through the DarkAngel asset pipeline and Ozz offline utilities. Preserve original source assets and import settings. Optional FBX conversion is a separate tool dependency, not a runtime requirement. Normalize units, axes, rest pose, scale and root orientation; reject unsupported deformation/nonuniform-scale cases clearly. Validate skin weights and mesh/skeleton binding. Cook compressed clips, stripped-root poses and motion tracks as one compatible generation.

All human characters use one canonical shared skeleton, including its hierarchy, rest-pose contract, joint keys and sockets. Human meshes and clips bind to this skeleton and pass compatibility checks; runtime retargeting is not required. Unique non-human characters use dedicated skeletons and clips authored for those rigs, with no retargeting support. DCC conversion of external human clips to the canonical skeleton is an offline content step when needed. Do not add a general Humanoid/Rig mapping asset or runtime retargeting editor to this scope. Matching joint names alone does not establish skeleton compatibility.

Graph runtime and pose composition

Compile a small typed graph into an immutable evaluation plan, with separate instance state. Initial nodes: clip, one-dimensional blend, explicit two-dimensional locomotion blend, transition/state selection, masked blend, additive layer and action slot. Validate pose/skeleton compatibility and dependency cycles; state-machine transitions are explicit state, not arbitrary evaluation cycles. Sync groups/markers align locomotion clips. Parameters come from tick movement/action state through typed bindings, not reflection lookups in every pose job.

Begin with CPU sampling/blending and reusable per-instance buffers/contexts. Immutable clip data can be shared; mutable sampling contexts and transition state cannot be shared across characters or concurrent jobs. Use a declared layer order: base locomotion, full-body action override, masked upper-body action, additive reactions/aim offsets, then optional presentation IK. Define blend curves, mask weights and additive reference poses. Full-body and upper-body slots have explicit arbitration; higher layer order is not permission to take root-motion ownership.

Keep tick-authoritative pose inputs distinct from interpolated visual evaluation. Render poses may be sampled more frequently or culled; graph/action state still advances on ticks. Start with linear matrix-palette GPU skinning and a CPU reference for validation. Motion vectors and more advanced skinning are later renderer work. Joint attachments use validated socket keys and inherited transforms; sockets never depend on render-only object lifetime.

Action timeline and event contract

ActionDefinition contains stable block IDs, duration, typed tracks and declared slot/channel ownership. ActionInstance contains activation ID, definition generation, action clock, phase, active interval blocks, queued combo input and cancellation state. Initially support linear timelines and explicit combo transitions; defer arbitrary nested action graphs. Gameplay blocks cover hit/aim queries, projectile/AOE requests, effects/tags, invulnerability and movement policy. Presentation blocks cover clips, VFX, audio and camera. Gameplay requests are checked by the native owning framework.

Use a fixed-resolution integer action clock advanced from the 60 Hz simulation tick, with bounded validated playback-rate/time-scale values. Authoring displays seconds/frames but cooking records exact timeline units. Define time-zero entry explicitly. Forward advancement processes crossed markers and interval boundaries in stable time/track/block order, not equality against the current timestamp. Split at loop boundaries; support finite loop limits and reject invalid zero-duration loops. Reverse scrubbing is preview-only initially.

Markers dispatch once for their activation/block/loop identity. Interval blocks receive balanced begin/end, including cancellation cleanup. If playback crosses both ends of a hit window in one tick, retain that traversed interval for collision evaluation rather than dropping it. Sample tick-authoritative socket poses at the relevant action boundaries and sweep the active interval with a bounded subdivision/error policy. Report subdivision overflow; this is an approximation to validate, not arbitrary sub-frame physics accuracy. Seeking restores state without replaying past one-shot effects unless explicitly requested in a preview mode.

Fit DAE-006 phases: advance action state and resolve movement locks/root deltas before motor movement; derive collision-relevant poses/sockets from tick state; after motor/physics, evaluate active hit intervals against the authoritative collision context and emit validated gameplay requests. Apply final achieved world transforms to sockets. A newly activated action has an explicit start tick; events never execute in render sampling. Headless tests must cover this ordering.

Interruption combo and resource lifetime

Define a native arbitration policy for full-body/upper-body slots and movement channels. Priority, tags and authored cancel windows decide whether an action can replace another; equal priority uses a stable request order. Death/stagger cancellation is an explicit gameplay rule. On cancel release owned hit windows, movement locks, tag/effect tokens and persistent presentation handles, then choose the outgoing pose blend. A visual blend-out may continue after gameplay has stopped; it cannot leave damage or invulnerability active.

Combo windows consume buffered tick-stamped requests at defined transition points. Validate activation/cost through Ability System before accepting the next action. Never derive combo success from a rendered pose or an unbounded input queue. Hitstop/action slowdowns change a declared action-clock scale; networking and the global simulation tick continue. Specify whether motion/pose and owned intervals freeze, while cooldown/status clocks remain separately owned. The initial default freezes action motion and suppresses repeat hit evaluation during hitstop.

Prediction root motion and gameplay pose

Carry activation ID, action generation, clock/phase, rate, relevant graph state and gameplay block state in correction history. Owner prediction may play the action immediately; server acceptance/rejection reconciles the same activation. Replay recomputes state/motion without duplicating durable gameplay or presentation events. Use event identities to deduplicate predicted/confirmed VFX/audio. Remote presentation catches up to authoritative phase instead of blindly starting from zero. Wire protocol and lag compensation remain networking work.

Extract root translation/yaw into independent motion tracks and remove those channels from the sampled pose, preventing double motion. Track deltas across loops, seeks and rate changes explicitly. Use one declared motor motion owner: locomotion is velocity-driven initially; root-driven actions supply bounded deltas. Pose crossfades do not silently blend competing motor paths. Movement warping remains collision constrained and uses authoritative targets. A blocked delta is discarded rather than reapplied later.

Headless servers evaluate the pose and joint ancestry needed for gameplay sockets/hurtboxes whenever combat requires it. First spike may sample a full CPU pose; optimize a reduced gameplay rig only after validating equivalence. Visual distance LOD/off-screen culling never disables damage timing, root tracks or required bone evaluation. Use the tick gameplay pose for authoritative weapon sweeps; render-only foot/aim IK is excluded. Any future gameplay-affecting IK must run from authoritative inputs on the server too.

IK reload preview and validation

Use Ozz two-bone and aim jobs for optional presentation IK after base blending, with rig-defined chains, limits, pole vectors and weights. Apply local corrections and rebuild affected model transforms. Start with one foot/hand or aim demonstration; full-body IK, physics animation and ragdoll blending are deferred. IK follows CharacterMotor achieved motion and cannot move the gameplay capsule.

Preview worlds run the same graph/action code with simulated clocks and mock sinks for damage/spawn requests. Provide play/pause, tick-step, scrub, masks, sockets, root path and active-window inspection. Scrubbing cannot mutate the live world. Clip/action edits create validated generations; running authoritative actions retain their original definitions until completion/cancel. New activations use the replacement. Compatible graph changes may migrate at a safe point; skeleton/layout changes reset affected previews and require controlled reinitialization. Network sessions require matching cooked generations.

Spike gates: import a skinned character with idle/walk/run and one root-driven attack; verify bind pose/remapping, locomotion synchronization, upper-body masks, additive reaction and optional IK. Validate tick hit windows through a socket, loop root accumulation, blocked lunge, cancel/death cleanup, buffered combo, hitstop, crossed-window handling and two independent instances. At 30/60/144 rendering FPS and with rendering disabled, gameplay event/motion traces should match for identical tick inputs.

Test predicted acceptance/rejection and replay without duplicate damage, projectiles or VFX; late remote phase; failed reload retaining old assets; live action generation pinning; preview scrubbing without gameplay effects. Measure sampling/blending/skinning costs, transient allocations and clip memory. Validate compression error at weapon tips, hands/feet and root tracks, not just average joint error. Set budgets from the slice. General action graphs, motion matching, advanced streaming and parallel evaluation are later measured extensions. Retargeting is outside the locked character-rig scope.

Decision Record DAE 008 Gameplay Ability Framework

Status: LOCKED - 7 October 2026

Research basis and implementation direction

Build a native DarkAngel framework using GAS concepts as architectural references, not an Unreal dependency or a port of the Unity implementation. Epic separates abilities, attributes, gameplay effects and cosmetic cues; effect definitions are immutable and runtime specs carry application data. Its API distinguishes activation checks from cost/cooldown commitment. These boundaries support the existing DarkAngel ownership decisions.

The engine-agnostic UGAS specification is a useful additional reference, but is currently a draft. It is not a production C++ runtime or evidence of compatibility with the existing Unity system. Do not claim full UGAS conformance. Adopt a documented DarkAngel subset; keep schemas and behavior under DAE-001 metadata. The contracts below are locked DarkAngel design choices, not assertions that Epic or UGAS implements them identically.

Ownership and runtime state

One AbilityState per gameplay owner contains granted ability specs, activation records, attributes, owned tag contributions and active effects. Players and NPCs use the same command API; input and AI supply requests. Separate gameplay owner/credit identity from the current character avatar so respawn and projectile attribution need not depend on a destroyed character. Network ownership is a separate permission check. Begin with straightforward per-owner state behind the DAE-002 ECS facade; avoid one polymorphic heap object per effect or a second ECS.

Definitions are shared immutable assets; granted specs hold level, source and input/slot bindings; activations hold mutable state and a unique ID. Concurrent use is an explicit definition policy, default one active execution per granted spec. Handles include world/owner generation and are checked after despawn. An ability activation launches or observes a DAE-007 action. Action Composer owns timeline windows and pose slots; Ability Framework owns requirements, spending, effects and outcome validation. CharacterMotor consumes movement policy and bounded force requests.

Atomic activation and commitment

Use Request -> Validate -> Commit -> Active -> End or Cancel. CanActivate is a read-only advisory query returning typed failure reasons. At commit, recheck grant, ownership, alive/blocker tags, cooldown group, resources, target requirements and action-slot eligibility against current tick state. Prepare the action start and native state changes before publishing any of them. Commit cost, cooldown, activation tags and action ownership together, once per activation/commit ID. A failed prepare spends nothing and leaves any previous action intact. Successful replacement cleans up the outgoing action before starting the new one.

Default: pay cost and begin cooldown when activation commits; cancellation after commitment does not refund either. An authored deferred commit marker is optional for charged/cast abilities: reserve required resources and the relevant cooldown/slot claim at start, then revalidate and atomically consume at that marker. Pre-commit cancellation releases reservations. Explicit policies govern refunds, channels and per-step combo costs; no automatic inference from animation length. Each combo step is a separately validated commitment linked to its parent. Resource availability subtracts all outstanding reservations.

End and Cancel are idempotent. Activation-owned subscriptions, reservations, tag tokens, movement locks, transient tasks and action windows are released through native cleanup even if a script fails. Death, despawn and grant removal use explicit cancellation rules. Effects/projectiles that should outlive their caster have their own lifetime and durable attribution; cancelling an ability does not silently remove an already applied Burn. Instant damage and spent resources are not undone by ordinary cancellation.

Attributes and calculation contract

Define stable Attribute IDs and reflected schemas with defaults, units, bounds and replication visibility. Use finite floating-point scalar values initially, with stable evaluation order and authoritative correction; do not promise bit-identical cross-platform lockstep. Separate resource attributes (Health, Stamina, Essence) from derived statistics (MaxHealth, MoveSpeed, DamageScale). Resource changes are explicit deltas to stored values, not temporary multiplicative buffs to Health. Modifier removal recomputes a statistic from its base and remaining contributions rather than trying to invert prior arithmetic.

For derived statistics, evaluate (Base + sum of flat additions) * product of named channel factors + sum of post additions, then choose any explicit override and clamp. A channel factor is max(0, 1 + sum of signed bonuses in that channel); the asset must name a channel. Two +20% bonuses in one channel give x1.40; separate channels give x1.44. Override winner is highest authored priority, then the latest stable application sequence. Reject non-finite magnitudes and invalid bounds. Show the complete breakdown in the inspector. This is a DarkAngel formula, not a claim of GAS arithmetic parity.

Magnitude sources initially cover constants/level curves, typed supplied values and declared source/target attribute captures. Capture timing is explicit: source power may snapshot at cast/projectile spawn, target defenses are normally read at impact. Derived-stat dependencies form a validated acyclic graph. Changing MaxHealth clamps Health to the new range; preserving a percentage is an explicit gameplay transaction. Clamp dependent resources before publishing notifications. Costs use resource deltas and availability checks, independent of derived-stat aggregation.

Complex calculations are registered native evaluators with read-only typed context and an output command buffer. Begin with a damage evaluator: validate hit identity and target eligibility; resolve immunity, defense and damage type; produce health/stagger/status/force requests; apply the bounded transaction; emit an attributed result. Combat formulas remain game data/code choices. Do not accept damage amounts or successful hits from client input. Luau can compose abilities and request effects through DAE-004 checked bindings; predictable calculations use the native subset initially. No mutable world access, wall-clock reads or ambient randomness in replayable evaluators.

Tags and effect lifetime

Cook a registered hierarchical GameplayTag dictionary with stable persistent keys and compact runtime indices. Support exact and ancestor matching plus All/Any/None queries. Separate asset classification, actor state, immunity and event identifiers. Every state-tag contribution has an owner token; releasing one source cannot clear another source of the same tag. Maintain descendant-aware queries without treating parent counts as independently removable contributions. Unknown tags fail asset validation. Export tag constants/types to C++ and Luau; avoid per-tick string lookups.

EffectDefinition specifies instant, finite or until-removed lifetime; application and ongoing requirements; granted tags; modifiers or executions; stacking rules; attribution; and cosmetic cue bindings. EffectSpec carries validated inputs/captures and a pinned definition generation. ActiveEffect carries handle, source credit, start/end ticks, next period and contributions. Instant effects apply a transaction without leaving a live modifier. Finite buffs remove their contributions at expiry. Periodic effects execute resource/damage transactions; stopping Burn prevents future ticks but does not restore lost Health.

Ongoing requirements initially use an explicit Remove or Suppress policy. Suppression removes modifier/tag contributions and pauses executions while lifetime continues; resumption does not replay missed periods. Evaluate requirements against external tag state excluding the effect's own contributions, and validate self-dependent rules. Changes pass through a bounded work queue, not recursive callbacks. Application immunity, cleanse/removal and death persistence are distinct rules. Default active effects clear on target death; equipment grants are re-established by the character lifecycle. Persistent exceptions are authored explicitly.

Stacking and tick scheduling

Do not use one global stacking mode. Each definition chooses its aggregation key (definition plus source, or definition on target), maximum count and one initial policy: independent instances; refresh a single instance; replace a single instance; or capped count. Counted stacks explicitly choose linear magnitude scaling and one shared timer. Define refresh/extend/no-change duration, reset/preserve period, overflow reject/refresh and all-at-once expiry. Per-stack timers, queued effect chains, strongest-wins selection and arbitrary overflow graphs are deferred. Attribution for merged target-wide stacks must be explicit; start Burn per source so cooperative damage credit is preserved.

Example slice policies: repeated Burn from one caster refreshes one per-source timer and preserves its period, without increasing tick damage; different casters have independent Burn instances. A dodge invulnerability token ends with its action interval. Stagger uses a game-owned severity/pressure resolver producing one controlled state transition, rather than accidental stacking of blocker tags. Equipment buffs remain tied to equipment handles. These are validation defaults for the spike, not final Ashen Roots balance values.

Use the 60 Hz simulation clock for cooldowns, durations and periods; UI converts ticks to seconds. Effects are active over [start, end), with default first periodic execution at start + period and no execution at end. Optional execute-on-apply is explicit. Before activation, process expirations, due periodics and resulting death/blocker state. After motor/physics, resolve action hit requests in stable order; a death transition cancels owned actions immediately and invalidates later requests from that activation. Revalidate target liveness on every request. DAE-007 hitstop does not freeze cooldown/status clocks.

Schedule effects by due tick with stable owner/effect/command sequence. Do not iterate unordered maps to decide outcome order. Notifications run after committed transactions and can enqueue subsequent commands, with bounded cascade depth/work and diagnostics. A multi-tick catch-up processes simulation ticks rather than collapsing status ticks into one large delta. No silent dropping of due damage. Establish limits for active effects, pending requests and reaction chains; reject invalid asset configurations and report exhaustion.

Target data and prediction boundary

TargetData is a bounded typed value: self, entity reference, point/direction, or server query result, with aim snapshot, simulation tick and source activation. Entity references use DAE-002 checked identity, not raw pointers. Validate finite values, ranges, ownership, target rules and world visibility as appropriate. Client point/direction represents intent; the server reconstructs or validates gameplay queries. Hit contexts include activation/block/window/target identity for repeat policy and deduplication. Lag-compensation history and wire serialization belong to DAE-009; bake schema/enum versions instead of copying in-memory layouts.

Predict only an explicit owner subset first: action presentation, reversible activation tags/movement policy, local resource reservations or cost deltas, and cooldown display. Server owns target health, damage/status results, periodic damage, inventory and authoritative spawned objects. Each activation and each deferred commitment has a correlated operation ID; combo children record parent dependency. Keep authoritative state separate from pending owner operations. Acceptance alone does not mean a replicated baseline already includes the predicted cost: retire an operation only when its rejection or authoritative inclusion is known, then rebuild the owner view from the baseline and remaining operations.

Rejection removes only that operation and invalidates/replays its dependent children; never restore an old absolute Health/Stamina snapshot over newer server state. Re-run requirements against the corrected baseline, preserving stable input/operation order. DAE-007 action history supplies phase and event identities; DAE-006 supplies motor correction. Deduplicate confirmed cues/projectile ghosts and damage commits. Bound histories and define an explicit resync on overflow. Single-player and host still use the same commit path. A local fake-authority harness validates these contracts before DAE-009 selects transport/protocol.

Cosmetic cues carry stable event/lifetime identities and begin/update/end or one-shot semantics; they cannot apply damage. Persistent status presentation is reconstructible from replicated state for late joins. Owner receives reconciliation data; observers receive needed attributes, public tags, action phase and cues, not private ability/task internals. Seed any authoritative random outcomes from server-owned state; client-selected seeds cannot decide crits. Predicting arbitrary combat executions and cross-target rollback is deferred.

Authoring reload and acceptance gates

Use reflected versioned AbilityDefinition, EffectDefinition, AttributeSchema, TagRegistry and TargetingProfile assets, with ActionDefinition references. Start with schema-validated JSON source and cooked native data; the Ability Designer edits those same fields. Diagnose missing IDs, invalid periods, cycles, reservations, contradictory tags and unsupported prediction flags before cooking. Active abilities/effects pin generations until they finish; newly created instances use validated replacements. Network sessions require matching cooked gameplay generations. Runtime tags and attribute schema changes require controlled reinitialization; general live network migration is deferred.

Inspector/debugger should answer: why activation failed; who owns each tag; what changed an attribute; which cost/cooldown committed; which stack policy applied; and which predicted operation remains pending. Record attributed tick traces with IDs and before/after values. UI and AI subscribe to committed changes. Keep arbitrary visual ability graphs and a general asynchronous task VM deferred; provide native handles for action completion, input release, timers and typed events with automatic cleanup. Luau extends server-side composition through the established host contract.

Spike: one melee combo, one projectile, Burn, temporary slow, dodge invulnerability, stagger/death and an equipment stat modifier shared by player and NPC. Verify simultaneous requests cannot overspend; duplicate commits charge once; failed action preparation leaves the previous action intact; deferred cancellation releases claims; removing one tag owner preserves another; modifier removal restores the correct stat; and per-source Burn gives correct attribution and period/expiry behavior. Test death during a hit-request batch, interruption, source destruction, cleanse, suppression and MaxHealth changes.

Validate two overlapping predicted costs, acceptance before baseline catch-up, rejection of a combo parent, out-of-order/duplicate confirmations and history overflow without double spending or repeated cues. Compare identical tick traces at 30/60/144 rendering FPS and headless. Check failed reload, generation pinning and script-error cleanup. Measure allocations, due-effect scheduling and bounded cascade cost at the slice's expected actor/effect counts. These are required implementation checks, not completed runtime results.

Decision Record DAE 009 Networking

Status: LOCKED - 7 October 2026; implementation validation pending

Transport and session boundary

Use the pinned native EOS C SDK for online play: EOS Connect for product-user identity, EOS Lobbies for lobby membership/discovery and EOS P2P for peer connectivity with Epic-hosted relay fallback. The user selected online P2P from the first networking milestone. Epic offers these game services without royalty or hosting fees and supports custom engines. The host still runs the authoritative simulation; the relay forwards traffic rather than supplying game-server compute. Use an EosTransport adapter and EosSessionProvider behind DarkAngel interfaces; no Unreal dependency.

Keep GameNetworkingSockets as a sibling GnsTransport adapter for offline LAN/direct-IP and headless direct-IP tests, with LocalSessionProvider for local membership. Single-player uses LocalSessionProvider plus an in-process LoopbackTransport. All adapters share one wire schema, replication, validation and prediction runtime. Do not tunnel GNS inside EOS, duplicate reliability layers or expose EOS/GNS handles to gameplay. Transport callbacks, IDs and diagnostics are translated at the adapter boundary. Offline paths do not initialize EOS or wait for its login/services.

EOS online membership uses Connect Product User IDs, mapped to opaque DarkAngel Participant IDs and player slots. Supported external identity providers can supply Connect authentication; Epic friends/social functionality is a separate Epic Account Services integration and is not required for the initial lobby search/join flow. Create/join/search/leave use EOS Lobbies; lobby attributes advertise host identity, protocol/content hashes, map and capacity but never replace the gameplay handshake or server authority. Accept only authorized lobby peers, handle login expiry/refresh and membership changes, and validate the host connection explicitly. The same participant identity remains distinct from network entities and persistent save IDs.

EOS relay policy starts with AllowRelays: attempt direct connectivity and fall back to relay; include ForceRelays in acceptance testing and expose routing diagnostics. Epic documents that forcing relays hides peer IP addresses with added latency. EOS service access requires online authentication/connectivity; a local packet route must not be treated as proof of fully offline session creation. Fresh-start, internet-disconnected EOS LAN has not been verified in this research, so guaranteed offline LAN uses GNS. If a supported EOS offline mode is later validated from a cold start, it may replace that adapter without gameplay changes. LAN identities are session-local and cannot claim EOS account privileges.

Authority and execution domains

SessionCoordinator selects one explicit mode: Local, LAN or OnlineEOS. SessionProvider handles membership/discovery/identity; NetworkTransport handles endpoints and bounded delivery; ReplicationRuntime handles authoritative state and commands. A session owns its server world, local client and connection epochs. Mode selection is fixed at session creation; adding an adapter requires conformance tests, not branches in gameplay systems. Local and LAN host/join are first-class supported modes, not error fallbacks requiring an EOS lobby.

Use one authoritative 60 Hz server simulation, owner prediction and interpolated observers. First target is four-player co-op plus a small PvP arena, not deterministic lockstep or peer-owned gameplay. Server owns AI, world state, damage, physics props and progression. Clients send bounded input/intent; they cannot write replicated Health, transforms, inventory or encounter state. Ownership transfer is a server operation with a new ownership epoch that invalidates stale commands.

Listen host runs distinct server and client worlds, consistent with DAE-002. Its local player uses the same serialized command/replication path through LoopbackTransport, without a second authority write or duplicated presentation. Single-player is a private one-player local host/lobby: no public socket, EOS lobby, login or internet dependency. It can optionally create a fresh online/LAN session later through an explicit session transition and synchronized bootstrap; transparent mid-match transport migration is deferred. Provide a dedicated headless-server executable using the same runtime; direct-IP mode is sufficient initially. A player-hosted server remains trusted for its session, so it cannot guarantee fairness against a malicious host in competitive PvP.

Receive and decode into bounded queues, then apply messages only at explicit simulation phases. Network callbacks never mutate ECS or call Luau. Before each tick: accept validated commands and apply authority changes; then run DAE-006/007/008 phases. After committed gameplay, capture replication state and enqueue outbound data. Pump EOS asynchronous work and notification cleanup through its adapter, with token refresh and SDK shutdown explicitly owned there. Library internal threading does not change DarkAngel single-threaded simulation ownership. Disconnect and shutdown release SDK messages, notifications and owner resources predictably.

Schema identity and message classes

Derive generated codecs and descriptors from DAE-001 metadata, with explicit wire field IDs, widths, units, enum values, bounds and replication audience. A reflected field is not automatically replicated. A component declares server authority, owner correction, observer interpolation or local-only handling through a registered policy. Specialized motor/action/effect state has explicit descriptors; do not pretend arbitrary ECS state is safely replayable. Never serialize pointers, object padding, native enum layouts or raw Flecs/Jolt memory.

Handshake negotiates an exact protocol version, gameplay schema/tag dictionary hash and cooked gameplay content manifest. First slice rejects incompatible versions with clear reasons rather than promising mixed-version play. Packet envelopes carry session/world/connection epochs, message kind, bounded payload length and sequence. NetworkEntity ID plus generation is distinct from local Entity ID and persistent world/asset ID. Maintain an explicit mapping, tombstones and checked references; respawn, world reset and interest re-entry cannot revive stale entity state.

Define three logical traffic classes: realtime inputs/snapshots; reliable ordered lifecycle/control and gameplay receipts; and reliable bounded bootstrap chunks. NetworkTransport advertises payload capacity, delivery/order capabilities and queue diagnostics. Each adapter maps these classes to its supported packet/channel semantics; EOS channels are not assumed to provide GNS lane priorities or independent ordering domains. Verify the pinned C SDK headers and behavior before choosing the mapping. Apply application-level scheduling, sequence/revision checks and bounded reordering where needed. GNS may use its lane scheduler. Budget bulk work below gameplay and prevent control bursts from starving realtime updates. There is no assumed order across traffic classes. Unresolved lifecycle/baseline dependencies are bounded or discarded with resync; no arbitrary method RPC or remote script evaluation.

Server RPC equivalents are registered typed commands with direction, owner permission, payload limits and rate rules. Ability requests, input edges, interactions and equipment changes call native validation. Command IDs yield idempotent terminal receipts. Reliable delivery is not permission and does not establish exactly-once gameplay by itself. Cosmetic one-shots may be unreliable with event-ID deduplication; persistent world/status state must be reconstructible independently of one-shots.

Input clock and acknowledgements

Sample owner inputs at 60 Hz and initially transmit at 60 Hz, bundling a small recent command window. Initial server snapshots are 30 Hz; rates are measured starting settings, not universal performance guarantees. Each command has an input sequence, intended server tick, normalized movement/aim, held bits and uniquely identified press/release/activation edges. Repeat unreceipted edges within bounded deadlines, with duplicate suppression; movement samples may be superseded. A transport packet ACK is not proof that an input or ability commitment executed.

Server consumes at most one movement step per player per simulation tick. It bounds future lead, queues a small jitter window and rejects expired/invalid commands; sending more packets cannot increase simulation time or movement speed. Missing input uses a short bounded held-state continuation, then neutral movement and release/cancel policy so a disconnected player does not keep sprinting/channeling. Expired edges receive rejection receipts. Resends never replay an already consumed edge or retroactively execute expired input.

Estimate server clock offset and jitter using timestamps/RTT plus snapshots; bound prediction lead and adjust smoothly. Keep server execution tick, input sequence, owner prediction tick and observer render tick as separate values. A correction includes the authoritative tick and which input/operation IDs it covers; track rejected/consumed gaps explicitly rather than guessing from the largest received sequence. An operation receipt carries acceptance/rejection and authoritative inclusion revision for DAE-008. Histories and wrap-safe sequence comparisons have bounded windows; session epochs make old-session packets invalid.

Replication baselines and entity lifecycle

Start with full typed snapshots to establish correctness, then add per-connection acknowledged-baseline delta encoding. Glenn Fiedler's compression reference explains why the sender needs a baseline the receiver actually possesses. Here, an application ACK means a complete snapshot was decoded and retained, not merely that transport bytes arrived. Do not delta against the last snapshot sent. A baseline carries its interest/control revision; the client does not ACK a snapshot with unresolved lifecycle dependencies.

Spawn/enter-interest establishes prefab/asset generation, ownership, cell and initial state through reliable lifecycle messages. Despawn/leave-interest produces a reliable revision and tombstone. Snapshots include required lifecycle revision; out-of-order snapshots cannot resurrect a removed entity. Re-entry has a fresh replication incarnation and full state. Entity references may resolve later only within a bounded queue; gameplay cannot run against unresolved targets. Server replication state is distinct from authoring persistence.

Maintain a bounded baseline ring per connection, periodic keyframes and explicit missing-baseline resync. Bootstrap/keyframes may be chunked, but realtime snapshot chunks form one bounded atomic revision with a timeout; ACK only complete decoding and never apply half an owner correction. Packetize below the active adapter's verified payload limit, including DarkAngel envelope overhead; do not assume GNS fragmentation or large-message semantics exist in EOS. Chunk counts, totals, memory and timeouts are validated before allocation. Under bandwidth pressure prioritize owner correction and nearby combat, split work into budgeted coherent updates and drop obsolete unsent snapshots. If backlog exceeds limits, resync or disconnect explicitly.

Begin with validated float transforms and simple field masks; introduce field-specific quantization only after measuring acceptable error. Quaternion normalization, finite-value checks and bounds are mandatory even before compression. Owner state includes motor, action and ability correction bundles; observers get transforms/velocity, action phase, public attributes/tags and required world state. Inventory, private costs and internal effect bookkeeping are owner/server data. Global encounter/altar/checkpoint facts have explicit session interest.

Owner replay and observer presentation

Store a bounded owner history of motor mode/velocity/ground/support state, action phase/root state, relevant ability operations and input. At an authoritative correction, restore a coherent bundle, retire only operations included in that baseline, and replay remaining accepted input order using the same native prediction subset. DAE-008 speculative resource/tag contributions remain separate from authoritative state. Rejection invalidates dependent combo actions; replay does not duplicate damage, projectiles, inventory changes or presentation cues.

DAE-006 character replay uses a separate historical collision context: static cooked collision and timestamped proxy state for relevant platforms, doors and other actors. Moving support history includes transform/velocity and support identity; DAE-007 root requests replay against the achieved motion rules. Do not replay old movement against current platform positions or cosmetic interpolated colliders. Jolt's state recorder covers physics-owned state under documented constraints, not every gameplay mutation. Restore DarkAngel-owned state explicitly; full coupled dynamic rigid-body/world rollback remains deferred.

First prediction gate covers static-world movement, root-driven action and deterministic moving platforms. Dynamic props and other players remain server-owned proxies and can produce corrections; no perfect client prediction guarantee for pushes or mutually coupled collisions. Relevant history loss, schema/generation mismatch, teleport and streamed-cell changes force an explicit resync rather than unbounded replay. Use server correction for gameplay transform immediately; smooth only the visual/camera offset with bounded limits, snapping on teleports or large corrections.

Observers interpolate timestamped snapshots on a delayed render clock, with a bounded jitter-adaptive buffer. Begin testing around 2-3 snapshot intervals, then tune using measured underruns and latency. Blend position/orientation and sample replicated action phase at that same render time; a late action does not blindly start from zero. Extrapolate only a short configured interval, then hold/recover explicitly. Reset buffers on teleport, ownership change and re-entry. Observer interpolation never changes authoritative collision or action clocks. Predicted owner is not delayed by the observer buffer.

Combat latency and bounded rewind

Prediction and lag compensation solve different problems: owner prediction makes input immediate; historical server queries decide whether an allowed attack hit what the client saw. Keep a small server history of hurtbox poses, lifetimes, relevant immunity/dodge intervals and moving blockers in a query-only context. Select a query time from a validated command/view timestamp and bounded latency estimate; the client cannot select arbitrary past targets or inflate its interpolation delay. Never move live bodies backward or replay past damage into the current world.

Initial candidate settings: retain 500 ms of query history and cap permitted rewind at 150 ms. These are spike values to compare, not researched optimal constants. Query historical hurtboxes and relevant blocker state consistently; also reject hits obstructed by present-world blockers as a conservative first policy. Teleports, despawns, cell transitions and missing history cut continuity. Require valid target identity/alive state now, check authored defenses at the query time, and apply a deduplicated outcome now. Do not recalculate all prior damage/death ordering.

Enable bounded rewind first for an explicitly designated instantaneous ranged query. Default melee sweeps, travelling projectiles and AOE execute on server action/simulation time. Do not generically backdate a rejected/late attack, fast-forward a projectile through unvalidated history, or use a client-rendered sword pose as evidence. Historical melee requires coherent attacker action/socket phase and defender dodge history; make that a separate PvP spike before enabling it. Measure attacker responsiveness versus defender fairness and document the chosen policy per attack family. The arena is a validation environment, not a claim of finished competitive netcode.

Interest late join and world streaming

Start with arena-wide interest for correctness. Then use a spatial/cell relevance set with hysteresis and per-connection budgets, always including the owner, party/global session state and nearby threats; do not cull an incoming projectile or damage source solely because its owner is distant. Visibility for replication is not rendering visibility or client authority. Prioritize combat state and active moving supports. Same-world cells remain DAE-002 partitions, not separate network simulations.

Late join uses Handshake -> ContentReady -> Bootstrap -> CatchUp -> Ready. Server captures a revisioned baseline of relevant entities, current effects/actions, doors/platforms, encounter progress and shared checkpoint state. Buffer bounded changes after that revision while the client loads/cooks nothing on trust. Apply and acknowledge the baseline, catch up changes, then enable avatar control. If catch-up exceeds retention, restart bootstrap. Reconstruct ongoing effects and action phase without replaying old damage or cosmetic one-shots.

World/cell activation carries a server epoch and content hash. Clients preload and acknowledge required collision/assets before the server permits entry/control there; stalled loading uses a defined barrier/safe position rather than prediction through missing collision. Cell exit invalidates replication/history references and applies reliable lifecycle changes. First slice keeps the party in one active region; independently roaming streamed parties and cross-region combat are deferred. Durable save state remains host/server-owned through the future persistence decision, never inferred from network ACKs.

Disconnect cancels held inputs and cleans connection-owned resources. Support fresh rejoin through full bootstrap; preserve an online player slot only through a valid EOS identity/session claim and explicit grace policy. Session-local LAN IDs cannot reclaim online account state. EOS service/network failure produces an explicit status and retry/exit policy rather than silently downgrading identity or moving an online match to LAN. Offline LAN and single-player remain separately launchable while EOS is unavailable. Transparent reconnect with retained prediction history, mixed EOS/GNS remote clients in one session and host migration are deferred. If the listen host exits, the match ends even if EOS can transfer lobby ownership; lobby migration is not simulation/save authority migration.

Diagnostics and acceptance gates

Network debugger exposes RTT, jitter, loss, send backlog, bytes by message/component/entity, snapshot size, baseline age/resyncs, interpolation underruns, prediction lead/replay count and correction magnitude. Show input execution/receipt timelines, activation dependencies and historical versus current hit queries. Capture bounded versioned input/message/tick traces with private credentials excluded; replay harnesses are local diagnostics, not a complete deterministic replay product. Apply packet size/count, decode-allocation and command-work limits before expensive validation.

Required first-networking spike: pinned Windows EOS C SDK plus GNS direct adapter; EOS Connect login/refresh, lobby create/search/join/leave, P2P acceptance and forced-relay traffic across different internet connections; four-player host topology with local host on loopback; explicit EOS service failure; fully offline LAN host/join from a cold start; and single-player from a cold start with EOS unreachable. Also validate headless direct-IP, root attacks/combo/Burn/projectile ghosts, moving platform, doors/encounter/checkpoint state, active-effect late join, interest re-entry and content mismatch. Verify SDK payload limits, ordered/reliable semantics, chunk loss, queue saturation and direct versus relayed diagnostics. Inject RTT 0/50/150/250 ms, loss 0/2/5%, jitter/duplication/reordering and burst loss through transport or the common harness; coverage points require measured pass thresholds.

Verify no double costs/damage/cues; missing input releases; out-of-order receipt/baseline consistency; lifecycle snapshots crossing reliable lanes; failed decoding and unknown fields; baseline eviction/chunk loss; death/teleport/ownership epoch; disconnect during bootstrap; replay on a moving platform; and bounded history overflow. Compare gameplay outcomes at 30/60/144 rendering FPS and headless. Stress bandwidth with many irrelevant entities and bulk bootstrap while a fight continues. Record CPU/memory/bandwidth and combat correction/fairness traces; no runtime checks or WAN service validation have yet been completed by this research.

Decision Record DAE 010 Unified Runtime UI

Status: LOCKED - 7 October 2026; implementation validation pending

Backend and ownership

Recommend upstream RmlUi behind DarkAngel UI APIs, pinned to a tested release and exact dependency revision. Use its RML and RCSS document layout, styling, data binding and navigation rather than developing a new layout engine. RmlUi is MIT licensed and generates rendering work for an application-provided backend. The release history now includes native D3D12 and Vulkan examples; they are implementation references, not a reason to bypass DAE-005 DiligentCore. Online documentation follows master, so verify all chosen APIs against the pinned headers before implementation.

DarkAngel owns UI document assets, instances, view models, surface placement, input routing, localization resources, commands, reload and diagnostics. Use upstream through public interfaces; do not start an engine-specific fork. Dear ImGui remains the editor shell candidate. A runtime UI preview can be embedded in that editor without replacing editor docking or inspectors. The dedicated server does not initialize RmlUi, fonts, window input or GPU resources.

Authoring and reusable documents

Author RML documents, RCSS styles and reusable templates, with a reflected DarkAngel UI asset descriptor for model schema, dependencies, default dimensions and permitted presentation modes. Resolve document, style, image and font references through the asset system; development uses source assets and shipping uses packaged dependencies. DAE-011 settles database/import/cook storage details. Treat RML/RCSS as the supported RmlUi dialect, not browser HTML/CSS compatibility. Publish and validate a supported property/widget profile against the pinned build.

Start with reusable buttons, sliders, lists, tabs implemented within the validated profile, text fields, tooltips, bars, cooldowns and modal dialogs. Keep stable authored element IDs for focus and transient state recovery. Source editing, dependency-aware reload, a preview and the RmlUi debugger are the initial workflow; a visual drag-and-drop UI designer, browser JavaScript, SVG/Lottie plugins and arbitrary custom element packs are deferred. Dynamic lists require bounded item counts; paginate or implement explicit virtualization before large inventories or lobby lists.

View models and command boundary

RmlUi bindings update dirty variables and support registered scalar, struct and array types. Its documented dirty tracking is at top-level variable granularity; do not assume member-level invalidation. Generate registration glue for explicitly exposed DAE-001 presentation schemas. Bind stable UI-owned storage or checked accessors, never pointers into movable Flecs component storage. Create models before loading dependent documents, verify names/types, and retain their backing storage until all documents and model handles are released.

Present committed client state through read-only view models; expose editable local settings and drafts through separate writable models. Health, inventory and lobby membership cannot become authoritative through a two-way binding. Gameplay buttons enqueue typed commands through DAE-008/009 validation, with operation IDs and pending/accepted/rejected presentation. Predicted costs or cooldowns may be shown from the existing prediction model, but UI must not invent a second prediction ledger. The same path applies to the local host.

Update view models from revision/change notifications, batch top-level dirty marks, then update active contexts once per presentation frame. Moving anchors and displayed timers have targeted presentation updates; no full ECS scan or string-path lookup per element each frame. UI events can edit local drafts immediately but queue world mutations for the next permitted simulation phase. RmlUi DOM work stays on one owning thread initially. Event subscriptions, checked entity references, contexts and commands have explicit owner cleanup on screen close, world unload and disconnect.

Use C++ event/model adapters and a narrow generated Luau UI facade for screen orchestration and typed callbacks, consistent with DAE-004. Do not enable RmlUi's optional ordinary Lua plugin as a second gameplay VM. Scripts receive generation-checked UI handles rather than raw DOM pointers. Reloaded handlers lose ownership and are removed; formatting functions are pure and bounded. Bindings change data, not arbitrary DOM structure owned by a data-for view. Escape player names and other external text; dynamic markup is restricted to trusted authored assets.

Surfaces placement and visibility

One UIDocument asset and model contract supports Screen, WorldAnchor and WorldSurface presentations, with independent state for each instance. Screen mode uses the viewport UI context for menus/HUD. WorldAnchor projects entity/socket anchors into that viewport for health bars, names and prompts, sharing a bounded context and pooled instances rather than a context or texture for every character. Clip behind-camera/off-screen anchors and apply distance, priority and visibility policies. This is a world-anchored overlay, not a depth-writing mesh.

WorldSurface initially renders the same document system into a bounded off-screen texture and composites it onto a planar world quad. The renderer owns its transform, depth test, transparent ordering, size and texture resolution; documents do not contain world coordinates. Standalone render-target output uses the same surface mechanism. RmlUi documents contexts for world interfaces but leaves surface transforms and pointer projection to the application. Direct rendering of arbitrary document geometry into the 3D scene and interaction on curved surfaces are deferred.

Specify occlusion explicitly: screen HUD ignores world depth, WorldAnchor can use a budgeted cached line-of-sight query with bounded staleness, and WorldSurface respects scene depth. Hidden or occluded targets never accept a new pointer press; interactive world surfaces use a fresh hit/visibility check for activation. Server validation still governs world interaction range and permission. Pool and cap visible anchors, contexts, render-target dimensions and refresh work. Shared atlases and cross-surface instancing are future optimizations; sharing a document asset does not imply one draw call.

Rendering integration and resource lifetime

Implement a Diligent-backed Rml::RenderInterface for compiled indexed geometry, external/generated textures, scissor, element transforms and clip masks. Preserve paint order; merge only adjacent compatible work. RmlUi 6 conventions include premultiplied sRGB colors and generated-texture orientation that must be handled explicitly. Match a reference renderer for translucent edges, font coverage, texture flips and nested transformed clipping. Do not assume rectangular scissor is sufficient for rounded or transformed clipping.

Keep screen UI in a defined display composition stage after scene tone mapping and before presentation. Establish one documented conversion path for RmlUi color/alpha into the DAE-005 target space, including unpremultiply/convert/repremultiply where required; never decode premultiplied sRGB as ordinary straight-alpha color. World UI textures have explicit color-space metadata and material conversion rules. Initial display output is SDR, without a promise of finished HDR UI handling. Off-screen passes use dedicated targets and avoid reading and writing the same texture concurrently.

Translate render callbacks into frame-owned draw work with copied or retained CPU data and generation-checked GPU handles. Release requests retire resources only after queued frames and GPU fences finish; do not retain RmlUi geometry spans after their documented release. Device loss, resize and reload invalidate the relevant generations. Begin with basic images/text, transforms, clip masks and opacity; filters, backdrop blur, complex masks, gradients/custom shader decorators and box shadows requiring layers are deferred until their backend features and budgets are implemented. Unsupported properties produce authoring diagnostics.

Input focus and scaling

Route actions through UIInputRouter with explicit screen/modal stack and one keyboard/controller focus owner per local viewport. Mouse, keyboard and controller use remappable Navigate, Confirm, Cancel, Tab and Scroll actions; map controller navigation to RmlUi key navigation with dead zones and bounded repeat. RmlUi supplies spatial navigation and explicit directional targets, but DarkAngel owns controller mapping and modal policy. Author visible focus, initial/default focus and stable return focus; recover when an item disappears, becomes disabled or a modal closes. Test sliders, lists and nested scroll regions rather than assuming auto navigation crosses every container.

Consume a physical action once. Modal UI blocks gameplay independently of the backend event result; normalize RmlUi input return values at the adapter because false can indicate consumption. Opening a menu cancels affected gameplay held actions through the normal input path; closing it does not turn a held Confirm into an attack. Keep UI responsive while simulation is locally paused; an online pause menu blocks that player's gameplay input but does not stop the host simulation. First slice has one local player per viewport; split-screen and multiple simultaneous UI pointers are deferred.

Map screen/window coordinates, viewport offsets, DPI scale and any letterboxing into the context's coordinate system using the same transform as rendering. For WorldSurface, raycast the eligible planar quad, convert its local coordinates to normalized UV then document pixels, and select the nearest permitted surface behind the screen/modal stack. Explicit pointer capture owns a press through release; cancel capture on hidden/destroyed surfaces or focus loss without transferring the press to another target. Use platform text events, not key-to-character guesses; clipboard and IME/text-input handling are platform adapter responsibilities with acceptance tests.

Localization accessibility and animation

Use UTF-8, localized string keys, parameterized messages and locale-aware number/time formatting owned by DarkAngel. RmlUi exposes translation hooks and font loading/fallback; bundle licensed fonts and verify glyph coverage, including names and accented Latin text. Default FreeType is the initial font engine. Unicode encoding and fallback fonts do not guarantee correct complex-script shaping. HarfBuzz is an upstream sample/custom font-engine path; right-to-left and complex-script production support require a separate shaping/bidi/font/input spike before adding those locales.

Provide UI/text scale, safe-area margins, controller-visible focus, readable contrast and redundant non-color status cues. Reduced-motion mode disables decorative movement/transitions. These are initial usability requirements; native screen-reader/platform accessibility bridges are deferred and must not be implied by HTML-like markup. Use RCSS transitions/animations for presentation and unscaled UI time; they do not trigger authoritative ability timing or determine when a gameplay command commits.

Reload diagnostics and acceptance gates

Reload RML/RCSS/templates as a validated dependency generation. Stage hidden replacement contexts/documents with fresh models, versioned resource URLs and inert command handlers; capture parser/binding/profile diagnostics and exercise layout before committing at a UI frame boundary. A non-null document alone is not proof that every binding/style is valid. Preserve compatible explicit view-model drafts, focus by stable ID and scroll positions; rebuild DOM rather than migrating raw element pointers. On failure keep the active generation. Cancel captures and retire old handlers/resources on commit. Do not globally clear shared caches while live documents depend on them; validate cache isolation with the pinned API.

The first spike must build pinned RmlUi/FreeType with Windows MSVC and the Diligent D3D12 adapter, plus early Vulkan parity. Show HUD health/stamina/cooldowns, main/pause/settings menus, keyboard remapping, EOS lobby create/search/join status and errors, an inventory list, pooled anchored enemy bars and one interactive world panel using the same document system. Preview against fake view models without a gameplay session. Validate headless launch without UI dependencies being initialized.

Check mouse/keyboard/controller switching, modal click-through prevention, held-input cancellation, capture loss, nested scroll focus, viewport resize/DPI/UI scale, long localized text, fallback glyphs, text input and IME, occluded world interaction and stale entity cleanup. Verify predicted/confirmed HUD state after ability rejection and reconnect bootstrap. Stress many anchors and repeated open/close plus good/bad dependency reloads; measure CPU layout/binding time, draw calls, GPU time, target/atlas memory and handler/resource counts before setting numerical budgets. Runtime benchmarks, visual parity, cold-start packaging and the custom backend have not been implemented or validated by this research.

Decision Record DAE 011 Asset Database Import and Cook Pipeline

Status: LOCKED - 7 October 2026; implementation validation pending

Source identity and generated state

Recommend three explicit layers: source-controlled authoring files and metadata; a rebuildable local SQLite asset index; and immutable derived artifacts in a content-addressed cache. DarkAngel owns asset identity, import contracts, dependency edges, manifests and runtime residency. SQLite is an embedded transactional index, not the only surviving copy of GUIDs, tags or authoring settings. Deleting the index/cache must preserve every reference and allow a clean rebuild from source. The runtime uses a cooked registry and does not require the editor database.

Use UUIDv4 AssetIds in a 128-bit representation, serialized in one canonical textual form in source metadata and fixed-width bytes in cooked records. An AssetId identifies logical content, not its path or current hash; it remains distinct from DAE-002 EntityId/PersistentId and DAE-009 network identity. Imported external files have adjacent versioned JSON .daimport metadata containing source UUID, importer/settings, authored tags and stable subasset mappings. Native DarkAngel JSON assets embed their own UUID/type/schema version and do not require a second competing identity sidecar. Never regenerate an existing ID merely because import failed.

A source can yield several independently referenced meshes, materials, skeletons or clips. Persist subasset UUID mappings using explicit stable importer keys, with source-object IDs where available. Raw array order, display name or glTF node index alone is insufficient. Reconcile reimports; ambiguity, duplicate names or structural replacement requires an explicit remap rather than silently assigning an old reference to different content. Removed subassets leave reported missing references. An imported asset copied as new content receives new source/subasset IDs; a reference to the original remains unchanged.

Asset moves and filesystem reconciliation

Editor moves/renames preserve UUIDs and move adjacent metadata with external sources. Relative glTF buffer/image paths are source dependencies and must be preserved or explicitly rewritten as part of a validated operation; GUID safety does not repair broken external URIs automatically. Normalize paths under declared project/package mounts, reject case-only ambiguities and case-colliding names, and define URI handling independently of Windows path spelling. Database scan detects duplicate IDs, orphan sidecars, missing source files and broken dependencies; never silently merge duplicate UUIDs.

Missing metadata requires explicit import/adoption. If the index remembers an ID, propose recovery with evidence; after index deletion a lost sidecar cannot be faithfully inferred from file bytes. Commit source and metadata together, retaining readable stable JSON ordering and migrations. Source-control policy excludes database, WAL files, caches, thumbnails and worker staging. Large source binaries can use the project's Git LFS policy; publishing or installing a repository policy is separate work. Deletion reports reverse references and requires an explicit resolution rather than path-based redirection.

Database services and ownership

Use a pinned maintained SQLite build with versioned tables for assets/subassets, source locations, settings fingerprints, dependency edges, import states, artifact variants and diagnostic records. Rebuild authoring tags, collections and package declarations from source-controlled metadata/project files. Expose typed AssetService queries and mutations to editor/agents; filesystem browsing is a view over indexed assets, not the reference model. Saved searches can filter type, tags, package, status and dependency relationships without loading resource payloads.

Use one AssetService coordinator as the database writer; workers return results rather than writing SQLite directly. Local WAL mode permits concurrent index reads while writes commit, but SQLite permits one writer and WAL is unsuitable for a shared network-filesystem database. Each checkout uses its own local index and cache. Bound transactions, handle busy/disk-full errors, own checkpointing and recreate derived state after recovery failures. SQLite transactions do not atomically commit filesystem blobs and source files together; the asset publication protocol below handles those boundaries.

Importer and dependency graph

Register importers by type, version and supported source profile. Import uses declared options and pinned tools, emits typed intermediate data, discovers exact inputs and dependencies, then produces target artifacts with diagnostics. Importer and cooker stages can share one executable initially but remain distinct contracts. A dependency records its kind: content used to build an output; required runtime reference; optional runtime reference; or editor-only reference. Changes propagate according to kind: changing a texture need not rebuild mesh bytes that only store its AssetId, but it invalidates packaging and the relevant live resource.

Enforce an acyclic build graph and show the full cycle on failure. Runtime reference cycles are separate from build cycles: permit only explicit soft-reference patterns, use checked handles and avoid recursive synchronous loading. Traverse their packaging closure with a visited set. A supposedly optional dependency is not silently dropped when a build root requires it; missing required refs fail cooking. Dynamic asset lookup from Luau or string keys must use explicit cook roots/labels or generated registries so reachability is not guessed from native code.

File watchers only request reconciliation. Debounce partial writes, periodically scan for missed events and hash actual bytes instead of relying on timestamps. Import operates on an immutable input snapshot. Worker reads of extra inputs are reported and included in the final dependency closure/key; undeclared or unstable inputs invalidate the job. If files/settings change while a job runs, its result is superseded and cannot overwrite a newer generation. A no-change reconciliation schedules no redundant conversion.

Worker execution and cache keys

Provide a headless AssetTool CLI with Scan, Validate, Import, Cook and Package operations using the same contracts as the editor. Run conversion in a bounded pool of child worker processes with versioned job/result messages, cancellation, timeout, memory/work limits and per-job staging directories. The coordinator schedules dependencies and commits results; workers do not mutate worlds, invoke editor UI or upload GPU resources. Process separation provides crash containment, not a claim of a security sandbox. Native importer registration/build changes require restart; source/settings reload remains incremental.

Use SHA-256 fingerprints for immutable artifact bytes and build recipes. A recipe covers exact source/dependency hashes, canonical importer settings, tool/dependency revisions, engine/type/cook schema versions, target platform/architecture/backend, quality and compression profiles, and relevant build flags. Include clip ranges, skeleton signature, texture color/alpha policy and shader defines where applicable. Logical AssetIds remain independent of these hashes. Keep diagnostic timestamps, machine paths and worker completion order out of artifact payloads and deterministic manifest ordering.

Pin deterministic CPU conversion settings initially; GPU-assisted compression and tool nondeterminism are opt-in only after measured reproducibility. Cold and warm cooks must produce identical payloads/manifests for the same recipe on the supported pinned build environment. Cross-toolchain and cross-platform byte identity is a validation requirement before advertising it, not an assumed consequence of hashing. A valid cache entry records dependency provenance and verified output hashes; mismatches fail and rebuild rather than returning corrupt data. Remote/shared caches and distributed builds are deferred.

Initial geometry and animation profile

Start with glTF 2.0 .gltf/.glb static and skinned triangle meshes, skins and transform animation, parsed through pinned MIT-licensed cgltf. It supports those source structures and separate buffer loading, but parsing is not the complete import contract. Run cgltf validation plus DarkAngel bounds/profile checks; use the official Khronos validator for development/CI fixtures. Record all external buffers/images. Reject unsupported required extensions and report unsupported morphs, cameras/lights, materials or transforms rather than quietly importing incorrect content. A glTF scene is an import hierarchy, not an automatically authoritative DarkAngel world/prefab.

Normalize once into the engine's documented coordinate, unit, tangent and UV conventions across mesh vertices, normals, node transforms, bind matrices, animation and collision. Validate finite values, accessor ranges, topology, degenerate geometry, material slots and skin weights. Preserve authored normals/tangents when valid; define and pin the tangent-generation convention when they are absent. Validate renderer influence limits and report any configured weight reduction/error. Nonuniform or negative scale in rigs is rejected unless the tested normalization path handles it. Do not independently bake skin or animation transforms into inconsistent spaces.

Use pinned MIT-licensed meshoptimizer offline for validated vertex/index remapping, cache/fetch optimization and optional authored LOD processing. Keep material boundaries, vertex attribute seams and skinning streams coherent; do not optimize transparent triangle order arbitrarily. First runtime representation is explicit indexed meshes and conservative bounds for DAE-005 CPU culling, including animated bounds. Automatic aggressive simplification, quantization, meshlets and specialized compressed mesh decoding are deferred until visual/error and performance tests justify them. Collision is a separate cook product rather than inferred from visual LOD.

Feed normalized skeleton/clip intermediates into the pinned Ozz offline builders established in DAE-007. All human skins/clips must match the canonical skeleton's hierarchy, bind/rest contract and checked bone mapping; matching names alone does not prove compatibility. Non-human assets use explicit rig signatures and clips without retargeting. Cook root-motion tracks, clip IDs/ranges, interpolation/resampling policy and required combat-bone metadata consistently with Action Composer. Test glTF STEP/LINEAR/CUBICSPLINE behavior or reject unsupported modes. Existing Ozz converters are references; keep one DarkAngel normalization contract instead of a second importer with different axis or skeleton rules.

FBX is not required for the first import milestone. The reviewed ufbx loader is a credible later offline adapter for mesh/skinning/animation evaluation, feeding the same intermediates and rig checks; it does not introduce another runtime asset format or retargeting promise. Until that adapter passes fixture tests, use an explicit reviewed glTF export workflow for FBX/DCC sources. The asset service interface remains independent of both parser choices.

Textures shaders and native data

Use pinned MIT-licensed DirectXTex in the Windows tool target for PNG/JPEG through WIC, TGA/HDR decoding, mip generation and block compression. It is principally a content-processing dependency, not the runtime GPU API. Store explicit dimensions, mip layout, semantic format, color-space and alpha metadata with cooked image payloads; the loader maps verified formats into Diligent. DDS can be an internal texture artifact container initially, behind the versioned DarkAngel texture descriptor. No native Direct3D upload helper bypasses Diligent.

Choose texture profiles by semantics: sRGB color/emissive; linear normal/mask/data; signedness and channel use explicit. Candidate desktop profiles are BC7 color, BC5 normals, BC4 single-channel masks and BC6H HDR, with RGBA/uncompressed paths where needed. Check format support and quality on the D3D12/Vulkan target; unsupported formats select an explicitly cooked fallback rather than runtime re-encoding. Generate color-correct mips, normal-aware mips and tested alpha-coverage handling. DAE-010 UI assets use a matching premultiplied color/alpha profile with verified edge quality. Do not infer normal-map green-channel convention from file extension.

Compile HLSL through the pinned DAE-005 DXC toolchain with transitive include hashes, backend defines, reflection/layout checks and cook profiles; package the required DXIL/SPIR-V variants. Native materials, abilities, effects, Action Composer and UI descriptors use DAE-001 versioned source schemas with generated validation and cooked data. Luau source/dependency graphs use the DAE-004 pinned compiler/runtime contract. Jolt collision is built using the pinned DAE-006 target/settings and validated serialization compatibility. Audio/navigation/VFX cooks use registered extension points; their detailed codecs and schemas belong to later decisions.

Artifact publication and runtime reload

Workers write complete outputs to staging; the coordinator verifies size/hash/schema/dependencies, publishes immutable blobs on the same local volume, then transactionally records their recipe/provenance and logical-generation mapping. Publish a new manifest only after every required blob is available. Crash before index commit leaves harmless orphan blobs for later collection; index entries referencing missing blobs trigger repair. Reconcile source/sidecar moves via a journal and full scan rather than pretending database transactions cover filesystem changes. Last-known-good preview may remain available with an explicit stale/error status; cook/package cannot silently ship it as current content.

AssetRef stores typed logical identity; resident AssetHandle also identifies a loaded generation. Asynchronous I/O and CPU decode have bounded queues and explicit states: Unloaded, Loading, Ready, Failed and Retiring. GPU upload occurs through renderer-owned work; collision/animation/script activation obeys each subsystem's safe boundary. Never resolve a resource by synchronously importing on a simulation tick. Optional presentation can use documented placeholders; missing required collision/gameplay assets prevents ContentReady/control. Runtime shipping loads cooked data, not source importers or an editor SQLite index.

Hot reload stages a coherent dependency generation, validates it, then commits at the appropriate frame/tick boundary. Renderer resources retire after GPU fences; actions/abilities and Ozz evaluation pin their compatible generation; UI uses DAE-010 staged document replacement. Skeleton/schema/collision changes may require a preview/session restart. In network sessions, gameplay-affecting asset reload is disabled until an explicit future coordinated protocol exists; cosmetic reload is allowed only for proven non-gameplay changes. Hashes do not make cross-client activation simultaneous. A failed reload keeps the active generation without hiding diagnostics.

Cook roots packages and multiplayer manifests

Cook from explicit build roots: bootstrap, maps/cells, gameplay registries, UI, package entry points and dynamically selected content labels. Produce a deterministic typed registry mapping AssetIds and target variants to immutable blobs, hashes and dependencies. Separate a backend-independent gameplay compatibility manifest from platform render-artifact hashes, so compatible D3D12 and Vulkan clients do not fail DAE-009 merely because shader bytes differ. Gameplay signatures include rig/action/ability/tag/collision contracts and relevant source/cook recipe versions. Server-only packages omit presentation payloads while retaining the same gameplay compatibility identity.

First distribution is a cooked manifest plus loose immutable artifact files behind AssetStore; a packed archive backend, chunk compression, patching and delivery services can be added later without changing asset references. Do not prematurely invent a proprietary compression format. Packaged native schemas and third-party payload versions are explicit, with bounded decode lengths and corruption diagnostics; runtime migrations are not substitutes for an explicit incompatible-content rejection. Headless cook works from clean source without an editor-created database or internet downloads.

Engine/project/package assets occupy declared mounts with globally checked UUIDs. Package manifests pin version/content hash and declare roots/dependencies; installed packages are read-only. Project overrides are explicit references/remaps, never path shadowing or duplicate-ID load-order precedence. Imports into writable project content assign new IDs while references can continue to point to package assets. Cache garbage collection traces published manifests, in-flight jobs and active pinned generations; it does not remove live artifacts solely by last-access time. Thumbnail/preview outputs are independently rebuildable editor artifacts.

Acceptance gates

The first spike registers/imports a static prop, canonical-human skinned mesh and clip, non-human rig, texture/material, shader, collision, ability/action JSON, Luau module and UI document through the CLI and editor service. Test source/subasset renames, file-array reorder, ambiguous reimport, copy-as-new, duplicate UUID, missing sidecar, external glTF dependencies, bad rig/weights/interpolation and unsupported extensions. Delete index/cache and rebuild without changing references. Changing a texture should rebuild its content/needed products without needlessly recooking unrelated mesh bytes.

Compare cold/warm/repeated cooks and parallel worker order; change importer revision, settings, include files and target profile to confirm correct invalidation. Interrupt workers, edit sources mid-job, fill disk, corrupt blobs and crash between blob publication/index/manifest commit; recovery must keep an explicit consistent generation. Load a packaged slice on a clean Windows machine without source or database, validate early Vulkan variants and a headless gameplay-only package, and confirm DAE-009 compatibility manifests match appropriately. Exercise failed/successful reload, active action generation pins, UI drafts and GPU fence retirement; never activate stale collision or duplicate handlers. Measure conversion, scan/query time, cache size, peak memory and runtime stalls before declaring budgets. None of these import/cook/reproducibility or runtime acceptance checks has been implemented by this research.

Decision Record DAE 012 Scenes and Reusable Entity Assemblies

Status: LOCKED - approved 7 October 2026 after reuse review; implementation validation pending

Locked direction and alternatives

Use a DarkAngel-owned authoring graph compiled into Flecs entities: reusable assemblies, entity templates and separate configuration assets. Reuse Flecs prefab instantiation and explicit component override facilities behind DarkAngel-owned schemas and spawn plans. Borrow useful workflows from Unity, Godot and Unreal. The editor presents a familiar hierarchy and contextual editing, but components remain ECS data evaluated by systems. This extends DAE-002 prefab ownership; it does not replace Flecs with a Node or Actor runtime.

Unity provides linked prefab instances, nested reuse and variants. Its current documentation identifies position-based collection overrides and base changes masked by overrides; unused overrides can survive removed targets or renamed fields. Unity has supported inherited-child deletion and prefab replacement since 2022.2, so those are not current missing features. Replacement defaults to name-based matching. Keep linked reuse and override inspection, but make stable identity and explicit reconciliation central to DarkAngel.

Godot offers reusable scenes and a tree that makes visual structure and composition approachable. Its own scene-organization guidance recommends self-contained scenes and warns that hierarchy-dependent paths can break during refactoring. Its node-alternatives guidance also recommends lighter objects/resources for suitable data. Borrow reusable scene composition and parent-provided dependencies; an authored hierarchy need not imply a runtime node for every setting or a per-node update callback.

Unreal separates non-spatial ActorComponents from spatial SceneComponents, offers configuration Data Assets and reusable multi-Actor Level Instances, and supports external Actor files for collaborative editing. Borrow these distinctions and in-context assembly editing. Blueprint class inheritance is not our default variation mechanism: differing stats, loadouts or visuals should usually be configuration or composition, without adding a new behavior class. Retain native systems and Luau behavior under the already locked contracts.

These sources establish mechanisms and documented failure cases, not comparative productivity benchmarks. The contract below is locked after the open-source reuse review. A custom authoring compiler, patch policy and editor remain necessary; their implementation and acceptance validation are pending.

Open source reuse assessment

Flecs is the primary implementation building block already selected in DAE-002. Its Prefab/IsA mechanisms provide instantiation, hierarchy support and explicit owned component overrides. Reuse these where they match the compiled plan, instead of implementing a second ECS or duplicating low-level component storage. Flecs Script offers a separate entity/template authoring language; do not introduce it as a competing gameplay language or replace DAE-004 Luau. DarkAngel still owns persistent identity, migration, patch provenance and editor transactions.

O3DE supplies a complete open-source prefab implementation with templates, instances, links, JSON patches and propagation. Its documented integration uses AzToolsFramework, entity serialization and editor ownership services. It is useful as a reference for resolver/propagation design, but extracting it into our Flecs world would require adapting those interfaces and semantics. No extraction/build feasibility has been demonstrated; do not take the entire engine framework as a scene-library dependency for the first slice.

OpenUSD provides a domain-extensible composition engine with layers, references, variants and sparse opinions. It is a real alternative, not merely a mesh loader. Its namespace editing can repair paths and use relocates for composed rename/reparent operations; do not dismiss it as lacking refactor support. Adopting it would change our JSON authoring contract and require custom gameplay schemas, persistent-ID mappings and editor/runtime adapters. Defer it as an optional later DCC interchange adapter rather than the initial gameplay scene authority. This fit/cost judgment is architectural inference, not a measured integration benchmark.

General C++ JSON libraries such as nlohmann/json provide parsing, serialization and RFC 6902 diff/patch helpers. Reuse a pinned maintained JSON library for mechanics; nlohmann/json is a candidate, not a newly locked dependency. Generic positional JSON patches do not implement our stable-item identity, schema migrations, conflict-aware rebase or semantic merge. Keep those policies above the JSON library. No reviewed candidate supplies the whole required workflow as a demonstrated standalone drop-in; lock the owned authoring contract while reusing suitable low-level facilities.

Authoring concepts and composition

Use one versioned authoring-graph schema for scenes and reusable AssemblyAssets. A scene contains placements and world-specific bindings; an assembly contains a reusable arrangement of one or more entities, nested assembly mounts and declared inputs/exports. They share editing and compilation semantics. An assembly has a placement pivot without requiring a dummy runtime entity solely to carry editor grouping. A scene may be extracted into an assembly through a validated identity/reference remap. Streaming cells, scheduling and saved-state partitioning remain later decisions.

An EntityTemplate defines one entity's component defaults and required configuration references. An AssemblyAsset composes templates, owned entities and nested assemblies. Configuration assets hold typed immutable data such as enemy definitions, ability sets and loadouts. Assemblies expose typed parameters, entity exports, attachment sockets and event/command bindings as explicit contracts. The containing scene or assembly supplies contextual dependencies; a reusable gate cannot quietly require an object named GateController somewhere above it.

Prefer composition and presets for routine variation. Optional variants have exactly one base and explicit patches; nested composition is not multiple inheritance. Validate both base and nested-assembly graphs for cycles. Show the full inheritance/composition dependency chain and value origins. Deep chains warrant diagnostics and review rather than becoming the expected content organization. The first slice needs a single variant level; deeper chains are an extension to validate before enabling.

For Ashen Roots, a Character assembly combines the motor/ability entity with a replaceable humanoid visual assembly and exported sockets. An EnemyDefinition supplies stats, abilities, AI configuration and equipment. Melee and ranged enemies reuse this assembly with different definitions. All human visuals must match DAE-007's canonical skeleton; unique non-human assemblies use their own rig and clips. No inferred retargeting is introduced. A separate Encounter assembly binds its exported completion event to a gate command through its containing scene.

Keep editor organization, transform parenting, lifetime ownership and gameplay references as separate relationships. Folders do not require transform entities. Spatial reparenting does not silently change ownership or invalidate every logical reference. Deletion previews the explicitly owned subtree and incoming references; required references must be resolved. A gameplay unit can include auxiliary presentation entities without requiring a native Actor subclass or treating every visual attachment as an independently replicated unit.

Stable identity and reference boundaries

Every authored entity, nested mount and overridable collection item has a stable local UUID or declared immutable key. Components and fields use DAE-001 stable type/property IDs. Nested targets use the mount-ID chain plus local entity ID, never display names, serialized array positions or transform paths. Renaming, list reorder and spatial reparenting within the same ownership scope preserve identity. Moving content across an assembly boundary is an explicit extraction/remap operation, not an accidental reinterpretation of old IDs.

A placed instance has its own stable placement ID. Its persistent entity mapping includes placement and nested local identity, preserving DAE-002's distinction between AssetId, authored local identity, PersistentId, runtime entity handle and NetworkId. Compact cooked mappings must detect collisions and retain enough identity to diagnose them; do not freeze a hash algorithm in this decision. Duplicating a placement allocates new placement identity while keeping its definition-local IDs and remapping internal instance references. Dynamic spawns use the existing server/runtime identity policy; persistence is explicit.

References distinguish same-assembly entity targets, typed AssetRefs, declared exports and scene-provided bindings. Cross-scene references are explicit soft links with a missing/unloaded policy; their cell-resolution details remain open. A reusable asset cannot embed a hard reference to a particular scene object. Nested private entities are inspectable, but outside consumers bind exported contracts instead of reaching into arbitrary implementation children. Refactoring an export uses stable IDs and migration/remap diagnostics.

Overrides that survive source edits

Store typed patch operations: SetProperty, Add/RemoveComponent, Add/RemoveEntity, ReparentTransform, BindInput and ReplaceSlot. Removal is an explicit tombstone. Collection edits address item keys, with relative ordering operations referencing stable neighbors. Raw-index patches are forbidden for reusable authored collections; replacing an entire collection is a distinct operation that clearly hides later base additions. Schema-defined fixed vectors remain values rather than pretending each coordinate is an independently identified list object.

Resolve schema defaults and entity-template defaults, then recursively resolve assembly definitions, then their variant patches, then each containing mount's parameter/binding edits and explicit local patches, and finally scene-placement edits. Each mount layer affects only that mount's declared contract; it cannot override unrelated siblings. Parameter assignments are resolved before explicit property patches at that layer. Reject ambiguous competing assignments within a layer. Single-base ancestry and scoped mount layers give an ordered provenance trace rather than relying on file load order or arbitrary multiple-inheritance precedence.

For every edited property, show effective value, source layer, overridden value and navigation to its definition. A base edit does not silently discard an intentional instance override: report the masked change. Distinguish inherit from explicitly pinning a value, even when a pinned value currently equals the base. This prevents both accidental redundant patches and unwanted loss of author intent. Placement transform belongs to the placement record rather than appearing as unexplained prefab dirtiness.

Rebase against the prior resolved-base fingerprint. Stable-field renames retain IDs; incompatible field types require a declared migration. Removed targets/items, invalid bindings and competing structural edits produce actionable conflicts, not name/index retargeting. Preserve unresolved patch data in a reported quarantine for recovery, but block the affected cook until explicitly repaired or discarded. Quarantined references are not effective runtime dependencies and cannot silently drag unused assets into a package. Effective patches and their dependency closure are validated by DAE-011.

Replacement uses declared slot contracts and export IDs. Swapping a human visual preserves the character placement identity and reconnects compatible rig/socket exports. Internal private children need not share names. Any incompatible exports require an explicit remap preview or rejection. Name similarity may suggest a mapping to a user, but never silently establishes persistent identity. Linked instances remain editable without needing to unpack them merely to make a supported composition change.

Editing safety and source collaboration

The editor always names the active edit destination: scene placement, variant or assembly definition, with its asset path and scope. In-context editing supports visibility and interaction aids, but saving local edits and promoting them upstream are separate commands. Promotion selects specific patches and a destination, previews affected assets/placements using reverse dependencies, validates bindings, and commits an undoable transaction. Avoid an ambiguous Apply All default spanning several nesting levels. Scene-only references cannot be promoted into reusable definitions.

Editor UI and agents call the same typed authoring commands with validation, undo records and asset-version preconditions. Preview a multi-asset change against an isolated authoring transaction before committing source. Autosave supports recovery drafts; shared-definition publication remains a visible save/commit operation. Concurrent changes reject stale preconditions and request reconciliation. Undo is bounded by the transaction history; source control remains the recovery mechanism for older committed history.

Use DAE-011 versioned JSON source with canonical ordering and stable-keyed records. For scenes, start with a scene manifest plus separate top-level placement/owned-entity records so independent placement edits avoid rewriting a monolithic scene file. A compact assembly file is suitable for small reusable assets. The graph semantics are identical regardless of storage partitioning. Membership/order is explicit; display names do not become filenames used as identity. Source validation detects partial submissions and dangling references. Multi-file edits use a journal/recovery protocol, not a claim of filesystem-wide atomic save.

Provide a semantic diff showing component/property and identity changes, and a three-way merge service keyed by IDs. Independent property edits may merge; deleting a target while another branch edits it is a reported conflict. Preserve unknown authoring fields for forward recovery, but fail cooking required unknown component/schema data. Stable IDs reduce refactor and merge hazards; they cannot automatically decide two conflicting designer intentions. Full source-control hosting/integration is outside this decision.

Cook and runtime behavior

Resolve templates, assemblies, parameters and effective patches offline into a validated spawn plan and dependency manifest. Flatten editor folders and inheritance scaffolding unless a runtime relationship is needed. Include source identities/provenance in editor diagnostics, with compact runtime mappings. Validate component requirements, transform/ownership cycles, binding types, skeleton contracts and headless stripping. DAE-011 owns cache keys and publication; DAE-009 gameplay compatibility covers the resolved gameplay plan rather than editor filenames.

Instantiation reserves all required entity handles, populates owned mutable components, wires relationships/references, prepares resources/scripts and activates the complete group at an explicit update boundary. Stage failures before activation; clean up prepared handlers/resources on failure and expose no half-initialized group to gameplay. Initializers may not publish gameplay side effects before commit. Health, cooldowns, action state and script instance state are instance-owned. Flecs Prefab/IsA sharing is permitted only for explicitly immutable defaults/configuration; authored inheritance never accidentally shares mutable state.

Authoring preview propagation reevaluates unoverridden fields and reports conflicts. Play still starts from a separate world under DAE-002; applying changes back selects authoring-owned fields explicitly, never current health, network state or script caches by default. Structural assembly reload initially restarts the affected preview/session. Active resource generations, action pins and network-session gameplay reload restrictions follow DAE-007/008/011. An assembly is not a network transport object or an implicit streaming cell.

Do not introduce arbitrary editor construction callbacks that execute gameplay on every property change. Initial procedural tooling can generate a validated authored graph from typed inputs and a seed, with bounded work and declared dependencies; cook consumes its outputs. General construction graphs, arbitrary runtime assembly mutation, multi-base variants, automatic deep private-child patching and extensive procedural tooling are deferred. A complete editor feature set is not required to validate the source/compiler contract through the CLI.

Luau scripts attached to world entities

Provide an editor Add Script action and drag/drop attachment for a Luau ScriptAsset on an authored entity, including entities inside reusable assemblies and individual scene placements. Store a native reflected ScriptBindings component containing a stable attachment ID, typed ScriptAsset reference, enabled flag, execution domain/phase and typed configuration values. Several attachments are allowed; their IDs survive reorder and support independent overrides/removal. Module paths are resolved through DAE-004/011 asset identity, never hidden filesystem or hierarchy-name lookup. Script configuration fields use declared schemas and stable property IDs, so the Inspector can edit, validate and serialize them.

A reusable module exports a factory that creates a fresh state object/closure for each attachment on each runtime entity. The module may share immutable code/defaults, but mutable angle, timers, subscriptions and tasks belong to the attachment instance. Use the existing one-VM-per-execution-domain model, not one VM per object. The host context supplies a generation-checked entity handle, validated properties and allowed engine APIs. Referenced objects are injected through typed bindings and assembly exports. Attaching a script does not define a new reflected ECS component type; ScriptBindings is native, consistent with DAE-004.

Lifecycle covers prepared initialization, activation, enable/disable, subscribed events, optional fixed-simulation or presentation updates, and destruction. Exact public function names are an implementation detail. Preparation may validate and allocate private state but cannot publish gameplay effects; activation occurs only after the assembly commits. A native scheduler registers only requested callbacks in explicit phases with stable ordering, execution budgets and authority checks; Inspector ordering is not an implicit global update order. Deterministic gameplay ordering must be declared where dependencies exist. Disable/destruction cancels owned tasks and event handlers; failed creation/reload cleans up prepared instances under DAE-004.

A Spinner example exposes Axis and SpeedDegreesPerSecond, attaches to the selected object and accumulates angle from elapsed time in instance state. A decorative spinner requests a presentation callback and writes an approved local visual transform; it does not mutate the authoritative collision or character root. A rotating hazard/platform requests a fixed-simulation callback and routes movement through the server-authoritative transform or Jolt kinematic-motion API in its permitted phase. Clients receive replicated/interpolated state, not competing authoritative updates. Validate conflicting transform writers instead of relying on whichever callback ran last. This distinction is explicit in the attachment descriptor and Inspector.

Play and optional preview instantiate fresh script state in separate worlds; ordinary editor selection/property edits do not execute gameplay. Edit-time behavior is opt-in, capability-limited and isolated in a preview world. Exposed configuration may be promoted through selected authoring patches; runtime tables, current angles and task handles are not serialized into assemblies by default. Save-state scripting is explicit and versioned. Reload prepares replacement instances, migrates only declared state and swaps at a safe boundary with cleanup/rollback; network gameplay reload remains restricted by DAE-011.

Add acceptance checks for two Spinner placements using the same module with independent state and different speed overrides; disable/re-enable, delete/recreate, reorder/remove attachments, stale handles, missing scripts and incompatible property migrations. Verify decorative callbacks cannot alter authoritative physics, and a scripted rotating hazard behaves coherently on the host, remote client and headless server. Reload must preserve declared state once, remove old handlers/tasks and retain the prior generation on failure. These are required implementation checks, not completed tests.

Acceptance gates and implementation order

First implement schema/identity/patch resolution and a headless validate/resolve/spawn-plan tool, then basic hierarchy/Inspector editing, provenance and selected promotion, then in-context previews and collaboration tooling. Prove two character instances have independent health, cooldowns and Luau state; replace a canonical-human visual and preserve socket bindings; compose an encounter and gate without hierarchy-name lookup. Run the same resolved gameplay assembly in single-player, network host/client and headless server domains.

Test base property changes with inherited, overridden and pinned-equal values; nested variants; item insertion/deletion/reorder; renamed fields/entities; spatial reparent; extraction; duplicate placements; removed component/entity; incompatible rig/export and explicit slot remap. Deleted targets must not redirect patches, and unresolved records must fail cook visibly. Test three-way merges, partial file submissions, stale edit preconditions, undo/redo, failed promotion and journal recovery. Compare repeat cooks, validate presentation stripping and exercise initialization rollback. No editor, compiler, merge or runtime acceptance tests have been implemented by this research.

Decision Record DAE 013 Editor Commands Undo and Inspection

Status: LOCKED - approved 7 October 2026; implementation validation pending

Locked direction and reusable tooling

Recommend a native EditorService with typed inspection queries and authoring transactions, shared by panels, gizmos, specialized designers, CLI tools and future agent adapters. It owns authoring state, validation, command history and change notifications independently of UI widgets. Use DAE-001 reflection and DAE-012 stable identities/patches rather than a second editor object schema. Continue the Dear ImGui docking direction, reuse an upstream DiligentTools ImGui renderer where compatible, and use ImGuizmo for transform interaction. Headless authoring commands do not depend on a window, GPU or Dear ImGui.

Qt provides the command pattern, undo stacks, grouped macros, compression and clean-state tracking; these are useful reference concepts. QUndoStack is a Qt Gui/QObject API, so adopting it solely for history would introduce another framework without resolving our authoring identity and multi-asset rules. Godot associates scene and global histories with edit contexts, and its documentation acknowledges that inferred contexts can be wrong. Unreal uses scoped transactions and UObject::Modify to capture changed objects. Borrow explicit transactions and grouping, but capture validated authoring deltas centrally instead of requiring every widget to remember an object snapshot call.

Dear ImGui supplies docking and interactive widgets, and ImGuizmo supplies matrix-based translation/rotation/scale controls. DiligentTools supplies a Dear ImGui implementation for the selected render API. Reuse these facilities with pinned compatible revisions; do not roll custom docking or transform handles in the first slice. DarkAngel still owns selection, property semantics, transactions and scene identity. Integration, backend compatibility and usability have not been measured. This research does not claim that any widget library supplies our complete editor command/history service.

Authoring model and command boundary

EditorService operates on versioned in-memory authoring documents backed by DAE-011 source assets. Each document has an AssetId, schema version, monotonic edit revision and saved content fingerprint. DAE-012 entity/mount/attachment IDs address authored objects; component type and property IDs address fields. Editor authoring data is authoritative for edits; Flecs authoring/preview worlds are materialized views with explicit safe synchronization. Runtime EntityHandle and component addresses are not persistent editor references.

Every content mutation is a typed command: create/delete/duplicate entities, add/remove components or Luau attachments, set property intent, change keyed collection items, reparent spatial or ownership relationships, bind exports, replace slots, promote selected patches, and change import settings or move assets through AssetService. SetProperty specifies inherit, pinned override or local assignment as appropriate; writing an effective value alone cannot express every prefab intent. Required components, dependency closure, reference types, package writeability, rig contracts and transform/ownership constraints are checked before commit.

A command request records operation UUID, schema/type, target documents and stable object/property keys, expected revisions, arguments and origin. Handlers are statically registered native code initially, with generated typed request/result metadata. Validate command schema and bounded payloads before resolving targets. A matching retry UUID with the same canonical request returns the retained result rather than duplicating a placement or attachment; reuse with different arguments is an error. Keep a bounded result cache and report expired retry guarantees. This is session idempotency, not permanent exactly-once execution across crashes.

Expose Prepare/Validate and Commit operations with structured diagnostics, affected targets and before/after previews. Preparation computes the complete change set against an immutable revision snapshot; commit rechecks all affected document versions. Start with conservative whole-document revisions rather than speculative field-level conflict merging. Missing objects, stale revisions, unsupported schema or incompatible bindings reject the entire batch visibly. Undo and redo are new validated history operations; they do not reuse a creation request UUID.

Transactions and publication

Apply a successful transaction to an isolated authoring overlay, validate its combined result, then publish the changed document generation as one logical in-memory commit. A batch may create an entity, attach a script and set its properties without exposing an intermediate invalid authoring state. Failed preparation or commit leaves authoring state/history unchanged. Publish one consolidated change record after commit; subscribers never see half a batch. Queue preview-world structural synchronization at an explicit boundary under DAE-002 rather than mutating an iterated Flecs world from an Inspector callback.

Saving is separate from committing an edit. Save validates and serializes affected documents through DAE-011/012 source services. A saved fingerprint is associated with the exact content written, even if newer edits arrive while I/O is pending. Multi-file source publication uses the existing journal/recovery protocol; it is not a claim of atomic filesystem replacement across all assets. Failure retains unsaved authoring state and diagnostics without marking it clean. Import/cook jobs are derived effects scheduled from committed/saved inputs; late results cannot overwrite newer generations.

Long-running commands return job tickets and prepare data in bounded worker tasks. They cannot hold a mutable document/world lock while importing, waiting for GPU work or running an arbitrary script. Cancellation before publication discards staging; commit rejects results prepared against obsolete revisions. Resource failures keep the last valid preview with a reported error. Where publication needs fallible work, prepare it before exposing authoring changes, or retain an explicit derived-preview error state; do not pretend an already committed external effect can always be rolled back.

Undo history and gesture semantics

Start with one bounded workspace authoring history ordered by commit, recording the complete cross-document transaction once. History displays a readable label, origin and affected scenes/assets; Ctrl+Z names the operation it will reverse even when another panel is focused. A filtered scene view can show related entries but cannot secretly undo an older transaction out of order. Independent per-document histories with coordinated cross-asset undo are deferred because they need dependency-aware ordering. This sacrifices some per-tab undo convenience for a clear first implementation.

History stores normalized forward and inverse authoring patches, including deleted entity/component/attachment data, relationship order, references and override intent. Undo validates the inverse against expected current content and applies it as a new monotonic revision; it never rewinds a revision counter. Redo reapplies recorded values and IDs, not the original UI gesture, random generation, Luau execution or import job. Restored authored entities preserve their authored identity, but recreated runtime objects receive valid new generation-checked handles. Reverse deltas must include every implicitly generated authoring change, such as required components.

One drag, text edit or multi-selection operation should normally be one history entry. BeginGesture captures original values and target revisions, UpdateGesture changes an isolated preview overlay, CommitGesture creates one validated transaction, and CancelGesture restores the pre-gesture view without an undo entry. Coalesce only compatible edits from the same gesture/targets/schema/intent; never merge across another user/agent edit, a save checkpoint or a transaction boundary. UI frame count is not history granularity. Semantic no-ops create no entries, while intentionally pinning an inherited equal value remains a real change.

Keep per-document saved fingerprints rather than deriving all dirty indicators from one global stack index. Undo after saving can make an asset dirty again; returning to byte-equivalent canonical content can make it clean. Bound history by memory and retained payload bytes, not only command count; keep large deleted-source payloads in managed local recovery storage. Source control remains long-term recovery, not unlimited session history. Persist recovery drafts/journal, but defer persistent undo across editor restarts. External file edits/reloads establish an explicit history barrier or conflict; never overwrite them by blindly applying an old inverse.

Filesystem move/import-setting operations participate through AssetService with prepared inverse metadata and retained content as needed. Deletion is recoverable editor trash initially. Derived caches, thumbnails, import output generations and rendering resources are regenerated, not copied into undo history. Commands with irreversible external effects are distinct jobs and cannot advertise ordinary undo. Git publishing, deployment, network messages and gameplay execution are not ordinary authoring transactions. Selection, navigation, layout and viewport camera changes use separate UI state rather than cluttering content history.

Safe inspection and property editing

Inspection returns bounded typed snapshots keyed by document/object/type/property IDs with document and schema revisions, values, validation, editability and DAE-012 provenance. The UI edits local draft values and submits commands; it never holds a raw Flecs component pointer across structural changes or writes directly through a reflected pointer. Publish value/structure change notifications after commits; panels refresh only affected data, with paging/filtering for large hierarchies. A stale target becomes a missing-object state rather than accidentally resolving a recycled entity handle.

Generate ordinary property widgets from DAE-001 metadata: primitive types, units, ranges, enums, typed AssetRefs, stable entity bindings and keyed lists/maps. Custom widgets receive immutable inspection data plus a command sink, preserving the same validation/history path. Show mixed values for multi-selection and edit the explicitly selected compatible fields in one transaction. Respect read-only/runtime-only/package fields. Structural constraints and cross-field validation occur on the combined candidate result; a numeric slider alone cannot establish gameplay validity.

The Inspector shows edit destination and value origin: template, assembly, variant or placement, with actions to inherit, pin, revert or promote selected edits. Editing nested private content selects its definition scope rather than silently creating an outside private-child patch. The asset picker validates expected type and availability. ScriptBindings exposes module, enabled state, execution domain and declared typed Luau properties; attaching a Spinner and changing speed uses the same commands and history as native components. Script state, tasks and callbacks remain runtime-owned under DAE-004/012.

Runtime inspection uses world-qualified handles and safe-phase copied snapshots labeled with domain, tick/frame and resource generation. Authoring, preview, client and server views are explicit; play values do not silently overwrite source. Begin read-only runtime inspection. Future debug mutation uses an allowlisted authority-aware command queue with its own execution trace, not authoring undo or arbitrary native-memory writes. Explicit apply-back converts selected authoring-owned play fields into validated authoring transactions; runtime health, network ledgers and script tables are excluded by default.

Selection picking and transform tools

Selection stores stable authored targets plus an explicit view/world context. Maintain primary and multi-selection, validate targets after deletion/reload and keep locked Inspector views scoped. CPU/editor picking is sufficient initially; optional GPU picking must include viewport request/frame identity and reject stale results after scene/world changes. Presentation helpers map back to selectable authored objects deliberately. Selection bounds and gizmos consume copied transforms, not cross-frame component addresses.

Wrap ImGuizmo matrix edits in Begin/Update/CommitGesture. DarkAngel defines local/world modes, pivot policy, snapping, multi-object transforms and parent-space conversion. Capture the original world transforms; each preview derives from those originals rather than accumulating floating-point deltas. Validate singular parent transforms and decomposition/shear limitations; reject unsupported authored transforms instead of silently damaging a hierarchy. Reparent can offer preserve-world-transform as an explicit validated operation. Physics preview rebuilds at its safe boundary; gizmo dragging does not bypass authoritative runtime movement.

Editor shell extensions and deferred work

Use a pinned Dear ImGui docking build in one native editor window initially, with the compatible DiligentTools renderer/platform integration evaluated in the first spike. DarkAngel owns keyboard focus, shortcut routing, drag payload types and application state. When editing text or manipulating a gizmo, route shortcuts to that active interaction before global history. Persist per-user layout/camera/preferences separately from source assets; workspace reset must not alter content. Docked panels are editor UI; DAE-010 RmlUi remains game UI and preview content.

Panels, property drawers, gizmos and specialized tools register with native editor registries and consume EditorService. Extension commands declare schemas, affected-target validation and change capture; they cannot bypass history by receiving mutable document access. Start with statically linked native extensions and restart on native changes, consistent with DAE-003. Optional Luau preview tools obey isolated capabilities rather than running editor mutations through gameplay scripts. Native plugin hot reload, multi-window viewports, collaborative live editing, branchable/selective undo and polished custom designer surfaces are deferred. Agent transport, discovery and permission policy belong to DAE-014; this decision supplies its shared typed core.

Acceptance gates

First spike supports hierarchy selection, a reflection Inspector, ImGuizmo transform editing, and headless commands over one scene with two linked character placements and Spinner attachments. Verify identical normalized results from UI and CLI commands; no-op, multi-edit, gesture cancel, save/dirty changes, undo/redo, deletion/restore and explicit patch promotion across two assets. Every operation preserves IDs and provenance, restores references and obeys DAE-012 override intent. Measure latency and history memory with a representative large scene before assigning budgets.

Inject invalid properties, incompatible refs/rigs, duplicate request UUIDs, stale revisions, worker cancellation, file-save failures, external edits and preview reload failures. Test all-or-nothing authoring batches, history barriers, bounded recovery storage and journal restart repair. Delete/recreate entities during Inspector refresh and complete delayed picking after world replacement; no stale pointer or handle may reach a different object. Test text-field shortcut capture, gizmo focus, DPI/scaling, D3D12 and early Vulkan backend rendering. A headless command test must load no editor GPU/UI dependencies. None of these command/history/inspection or widget integration checks has been implemented by this research.

Decision Record DAE 014 AI Agent Interface

Status: LOCKED - approved 7 October 2026; implementation validation pending

Locked direction and protocol reuse

Recommend an optional DarkAngel AgentBridge exposing curated MCP tools over stdio, backed by a versioned native JSON-RPC 2.0 command/query endpoint. The C++ EditorService from DAE-013 remains the authority for inspection, validation, editing, undo and job control. The bridge translates protocols and schemas; it does not maintain another editable world or implement gameplay policies. Agents use the same operations and constraints as human tools. Shipping games and dedicated servers do not require MCP, an LLM SDK, Node.js or the bridge.

Use the official TypeScript MCP SDK in a separately packaged development-tool process, with pinned SDK/runtime/dependency versions. The current official SDK catalog lists TypeScript and other supported languages but does not list C++; this does not imply that community C++ implementations cannot work. A native C++ MCP dependency could remove the sidecar runtime, but would require its own support/conformance evaluation. A TypeScript bridge reuses protocol maintenance and keeps those changes out of the engine ABI. It adds a development-tool packaging dependency; validate distribution and startup rather than assuming it is free.

Target the published MCP 2026-07-28 revision through the SDK, with an explicitly tested compatibility profile for older hosts where needed. Current transport documentation uses per-request metadata and differs from older connection-scoped initialization/session semantics. Do not hand-code an obsolete lifecycle or assume generic JSON-RPC alone is MCP. Stdio remains a standard transport. MCP supplies tool discovery, schemas and structured results; its annotations describe behavior but do not enforce DarkAngel authorization. These are researched protocol facts; the bridge choice and contracts below are DarkAngel recommendations.

Keep JSON-RPC as the native development endpoint and MCP as one adapter, not two independent command systems. JSON-RPC request IDs correlate transport replies; operation UUIDs from DAE-013 deduplicate mutations. Notifications have no response and therefore cannot be the application mutation interface. JSON-RPC batches do not imply transactional ordering or atomic edits: an authoring transaction is one explicit request containing a validated command batch. Headless CLI tests can exercise the native service without MCP.

Local connection and project identity

On Windows, connect the bridge to the editor or explicitly started headless AgentHost through a local named pipe. Generate a unique endpoint per running host; supply connection details through an editor-issued descriptor bound to project identity, host instance and a revocable authorization context. Verify project/host identity before serving requests and show it in every result envelope. Multiple running projects must not be selected by whichever process happens to respond first. The bridge is launched by its MCP client and attaches to the selected host; it does not silently spawn a new engine/world.

Set an explicit pipe security descriptor for the intended user and reject remote named-pipe clients; default named-pipe access is not the intended policy. Use an ephemeral credential/authorization context and do not expose it in logs or tool results. This protects accidental or unintended connections, not against arbitrary malicious code already running with full access as the same user. Core IPC uses bounded length-framed UTF-8 JSON messages, independent of the SDK's stdio framing. SDK-facing stdout contains protocol messages only; diagnostics go to stderr or the editor log.

No listening HTTP server is required in the first slice. Remote operation, shared hosts and Streamable HTTP are future adapters requiring explicit deployment and authentication design; localhost alone would not establish client identity. Keep host authorization in the native service even when the bridge applies additional checks. Revoke access on user disconnect, host shutdown or policy change. An application authorization context is distinct from the MCP protocol's transport/session model.

Discovery schemas and bounded inspection

Generate command/query schema descriptions from DAE-001/013 declarations and export a versioned capability catalog. Include stable command/type/property IDs, human descriptions, units, enum values, constraints, reference types, required execution scope and supported schema versions. The bridge builds deterministic curated MCP tool definitions with input/output schemas from that catalog. Do not expose thousands of raw setters or an unrestricted execute-anything tool. Editor-only native extension commands become agent-visible only after explicit registration in the allowed catalog.

Initial tool families cover project/capability description; indexed asset and authored-entity search; typed inspection/provenance; edit preparation and commit; history inspection/undo; job launch/status/cancel; and viewport focus/capture. Use typed discriminated command unions for batches, not source code to evaluate or arbitrary property-path strings. UUIDs and stable target references are canonical strings; 64-bit integer/revision fields use schema-declared lossless encoding rather than assuming JavaScript numbers preserve all C++ integer values. Validate payload lengths, enums and unknown fields before forwarding.

Queries return paginated/filterable results with stable IDs, display names, source locations, revisions and structured diagnostics. Cursors are bound to a query snapshot/generation; invalidated pagination reports stale data rather than mixing two world states. Read only requested components/fields and use bounded dependency/provenance traversal. Reference display names are hints, never authority for committing to a target. Multiple equally named objects require an exact selected ID or a returned candidate list, not automatic fuzzy mutation.

Expose larger immutable snapshots, diff reports and captures through bounded application resource references with project, generation and expiry. Resource reads enforce the same scope as queries; arbitrary filesystem URIs are not a bypass. A response records operation/transaction ID, project/host, domain, observed revisions, status, changed targets and diagnostic codes. Tool/domain failures are structured tool errors; malformed protocol/schema requests use protocol errors. Avoid requiring an agent to scrape logs for success or inspect every object to discover changes.

Prepared edits and shared undo

Agent edits use PrepareEdit followed by CommitEdit. Preparation is non-mutating: it resolves exact target IDs, validates the complete batch and returns a server-held plan with opaque plan ID, content digest, affected documents, expected revisions, normalized changes, prospective IDs and diagnostics. The agent can show or inspect that concrete diff. Planning reserves proposed identities without publishing entities; an expired/cancelled plan creates no authoring state. Bound plan memory and lifetime, and invalidate affected plans after relevant source/schema changes.

Commit accepts the prepared plan ID plus an operation UUID and checks authorization, digest/context and every expected document revision again. It cannot replace the prepared batch with unreviewed client-supplied data. A successful commit is one DAE-013 authoring transaction and one workspace undo entry labeled with its agent origin. A stale plan returns a conflict requiring a new prepare; never quietly redo target resolution or apply it to a newer object. Session retry deduplication follows DAE-013; reconnect/crash recovery must query known operation status or report uncertainty before trying to create again.

Source saving is an explicit operation or a declared save-after-commit policy. Results distinguish CommittedUnsaved, Saved, SaveFailed and derived Preview/Cook errors; a save error does not pretend the successful in-memory edit vanished. Undo is authorized authoring mutation and targets the current workspace history head, with its expected transaction ID; agents cannot silently rewind an unrelated recent human edit. Redo restores recorded data. Out-of-order selective reversal remains deferred under DAE-013.

Example: an agent finds a prop by indexed metadata, inspects its exact placement and revision, prepares attachment of a Spinner ScriptAsset with Axis/SpeedDegreesPerSecond, then commits once. The same ScriptBindings Inspector displays that attachment and the edit appears in human history. Optional script creation/editing is a typed source-asset operation with UTF-8 size/schema/compile diagnostics and DAE-011 identity; it is not arbitrary filesystem write access. Runtime script tables and authoritative physics state are not authoring patch targets.

Access policy without repeated routine prompts

The editor grants capabilities for a selected project/host and intended scope. Distinguish inspection, authoring edits, jobs, preview/play control and optional runtime debug commands. Support an inspection-only connection and a user-authorized project-edit session. A granted edit session permits validated routine edits within that scope without repeated confirmation for every property. The editor shows active grants, agent origin and recent transactions and can revoke them. Preparing a diff is required by the mutation contract; requesting human approval for each prepared edit is a configurable policy, not the default for already authorized routine work.

Grants can restrict writable assets/folders, command families and job profiles; native handlers enforce them on every request. Read-only package mounts and protected source scopes remain enforced by AssetService. Asset descriptions, script comments and imported metadata are content, not permission grants or executable instructions. MCP read-only/destructive/idempotent annotations accurately describe tools but cannot confer access. Do not offer arbitrary shell execution, arbitrary native code evaluation, pointer writes, unrestricted Lua evaluation, credential retrieval or implicit repository publishing as editor tools.

Build tests and preview control

Use allowlisted job profiles for validate, import/cook, navigation bake, compile and test; pass typed targets/configuration rather than shell command strings. The JobService uses existing DAE-011 worker limits and pinned tools, reports queued/running/completed/failed/cancelled states, and returns bounded diagnostics/artifact references. Building or running project code is execution and requires the corresponding job scope; read access or script-edit access alone does not authorize it. Requests cannot fetch new toolchain dependencies or alter build scripts merely by naming a job profile.

Tie each job to a source/schema generation and isolated workspace/staging output. Worker completion cannot activate stale outputs. Report cancellation as best-effort until a terminal state is known; terminate the child process when the profile supports it and clean staging safely. Transport disconnect does not reliably prove whether an edit/job committed. Application job status survives the bridge connection while the host lives; recovery across host restart uses explicit stored job outcomes or reports unknown, not invented success. Initial polling is sufficient; MCP-specific task extensions are optional later adapters.

Preview/play operations explicitly select a new preview world or play session and provide start, stop, pause and bounded step controls. Use DAE-002 separate worlds; never convert the editable scene into the running world. Headless test profiles support gameplay without renderer/UI dependencies; rendered play profiles expose screenshots only where a renderer exists. Native authority restrictions still apply to any debug command. Joining an external online lobby, sending messages, deployment and publishing are outside ordinary local preview control and require separately defined explicit capabilities.

Vision focus and runtime evidence

Semantic inspection is the primary interface. Focus/select/frame commands assist a human or agent without changing content history. Viewport capture requests specify viewport ID, world/domain, camera, resolution and relevant scene revision; the renderer returns image plus frame/tick metadata and optional object-ID mapping. Queue capture/readback through renderer ownership and report pending/unsupported honestly. Headless hosts return Unsupported for screenshots rather than fabricating a visual. A stale capture cannot establish the current target revision for a commit.

Screenshot coordinates can suggest a selection through the normal picking service but cannot directly address a persistent mutation. Resolve a picked result to a stable authored ID, inspect it and prepare an edit. Image outputs obey bounded sizes and declared presentation settings; comparisons record camera, lighting/time and resource generation. General desktop control, OCR-driven editing and screenshot-only world manipulation are unnecessary for this engine API. Runtime inspection reports the selected server/client/preview world and tick; it does not merge data across domains.

Implementation order and acceptance gates

First implement native discovery, search/inspect and prepare/commit over the local IPC adapter using DAE-013 services. Then add the official SDK bridge and one real supported MCP host, followed by job and viewport adapters. Pin/test the intended current protocol and any older compatibility mode separately. Extension registration and schemas must be identical for UI/CLI/agent operations; protocol adapters cannot introduce a hidden validation bypass. Model vendor integration, embedded chat UI, automatic planners, cloud orchestration and collaborative multi-agent editing are deferred.

Prove a client discovers schemas, locates duplicate-name props safely, attaches two independent Spinner instances and changes one speed, with one human-visible undo entry and correct saved source. Inject expired plans, stale revisions, cross-project descriptors, revoked scope, retry UUID reuse, dropped replies, malformed payloads and unsupported schema/protocol versions. Verify no duplicate entities or silently retargeted edits. Test a denied job scope, successful/failing headless jobs, cancellation, bounded logs, correct source-generation results and bridge restart during an active job.

Validate stdio framing/log separation, pipe access restrictions, wrong-host rejection, capability filtering, pagination invalidation and safe resource reads. Capture the intended viewport/world, reject delayed stale picking and confirm headless screenshots return Unsupported. Compare agent and native command outputs and undo records; inspect/edit tools must not execute scripts or launch builds implicitly. SDK packaging, host compatibility, command adapters and these acceptance checks have not been implemented by this research.

Decision Record DAE 015 Terrain Splines and Vegetation

Status: LOCKED - approved 7 October 2026; implementation validation pending

Locked direction and scope

Use a mesh-first hybrid: native terrain authoring assets and tools produce spatially partitioned cooked triangle meshes, dedicated collision and navigation inputs, and batched vegetation instances. Imported arbitrary 3D meshes, convenient heightmap/grid creation, authored sculpt modifiers and validated solid-mesh cuts can all feed that runtime contract. Caves, overhangs and stacked surfaces are first-class geometry; a single height per X/Z coordinate is not the canonical terrain model. Volumetric authoring can be added behind the same cook interface without requiring a runtime voxel database.

Locked scope: Ashen Roots needs designed terrain and editor sculpting; player digging, arbitrary runtime topology changes and continuously deformable terrain are deferred. Adding gameplay terrain destruction requires revisiting the representation, collision/nav rebuild and replication/persistence protocols. Scripting a moving platform or cutting a tree is separate from remeshing the ground. No editable-terrain networking protocol is included in this decision.

Alternatives and source findings

Heightfields are convenient for outdoor sculpting but cannot alone express several surfaces above one horizontal coordinate. Unity documents terrain holes plus separate geometry for cave/overhang effects, and Unreal Landscape documents fitting meshes into holes. These are valid hybrid workflows, but requiring every cave to be a special exception would not meet our general 3D terrain direction. A heightmap is an import/create option; its generated mesh can join cliffs and cave geometry.

Unreal's current Mesh Terrain documentation demonstrates imported meshes, sculpting, section splitting/stitching and compiled sections; the feature is explicitly Experimental. It supports the separation of editable terrain and compiled runtime meshes as a useful design precedent, not proof that DarkAngel can adopt Unreal's implementation or match its production behavior. We would build our terrain asset/tool layer on the locked renderer and asset pipeline.

Smooth voxel/SDF terrain naturally supports carving and topology changes. Godot Voxel Tools provides smooth SDF terrain and Transvoxel meshing/LOD, but it is a Godot module, not a demonstrated standalone DarkAngel library. Transvoxel supplies an algorithm and lookup data for different-resolution transitions, not the complete storage, editor, collision, streaming and replication systems. Choose that path if editable volumes are a core gameplay requirement; otherwise it expands the first implementation substantially. Block voxels are a different visual/authoring model and are not the recommended Ashen Roots terrain.

OpenVDB is an open-source C++ sparse-volume library with mesh/volume conversion tools. It is a strong candidate for later editor/offline volumetric sculpting, not a complete terrain engine. Manifold is an open-source C++ solid-triangle-mesh geometry library supporting Boolean operations and material/property mapping. Evaluate Manifold first for bounded terrain cuts/unions in cooker workers; preserve an optional OpenVDB generator interface. Library suitability, performance and integration are recommendations pending spikes; neither is a newly validated production dependency.

Terrain source and geometry tools

A TerrainAsset has a stable AssetId and versioned JSON recipe referencing source geometry, material/biome definitions, partition settings and keyed ordered modifiers. Source meshes retain DAE-011 identity and can come from glTF or native primitive/grid generation. Modifiers have stable IDs and declared bounds/dependencies; vertex sculpt strokes store typed brush input, coordinate frame, falloff and affected source scope. Keep source intent separate from immutable generated geometry. Large checkpoint/paint payloads are versioned source blobs or derived cache entries according to whether they are reproducible; never hide irreplaceable edits in a disposable cache.

Provide selection/gizmos, add/remove/modify geometry, mesh sculpt displacement, surface painting and explicit solid union/subtraction operations. Solid Boolean inputs must satisfy the backend's topology requirements and have consistent winding/scale; ordinary open surface meshes remain usable as rendered/collision terrain but cannot silently be treated as closed solids for cuts. Conversion/capping/repair is explicit and previewed. Reject invalid cuts and retain the last valid result; do not accept a hole in the render mesh without corresponding collision changes.

Compile recipes using DAE-011 bounded workers and exact tool/input hashes. A brush gesture previews in isolation and commits once through DAE-013, with DAE-014 preparation available to agents. Geometry changes invalidate affected render/collision/nav/scatter products and their neighbor dependencies. Spatial brush bounds reduce candidate work, but a Boolean operation's actual changed topology may extend further; compute the real dependency region instead of assuming a brush radius proves locality. Defer arbitrary procedural graphs and a full DCC replacement.

Start the vertical slice with imported arbitrary 3D terrain and one native closed-solid cut through Manifold evaluation, so a playable cave/arch is demonstrated before expanding sculpt tools. Native grids/heightmap imports are conveniences. An optional later SDF generator must declare voxel scale, finite detail/error limits, signed-input requirements and meshing settings, then emit the same validated mesh products. Source generators are not selected per rendered frame. Do not add mandatory OpenVDB/NanoVDB runtime dependencies merely to load a cooked hillside.

Partitions LOD and surface identity

Cook terrain into bounded mesh partitions with full 3D bounds and local coordinates, stable logical patch IDs and adjacency metadata. Do not equate terrain partitions, render LOD clusters, collision bodies, nav tiles and DAE-016 streaming cells. A cave can span several partitions and share a region with terrain above it. Exact cell sizes, large-world origin policy and streaming schedule remain for DAE-016; this decision requires independent products, dependencies and explicit readiness.

For the first slice, use fixed validated mesh partitions with optional offline meshoptimizer LODs, CPU bounds/cluster culling and existing DAE-005 instancing. Begin with one render LOD where necessary to prove geometry correctness. When enabling independent LOD selection, preserve shared boundary positions/topology, normals and material continuity; evaluate border-preserving simplification and measured error instead of assuming arbitrary separately simplified chunks join. Fixed detailed boundary rings may be a first compromise, with their vertex cost measured. Transvoxel is not required for premeshed partitions.

Protect gameplay-significant cave openings, ledges and walkable silhouettes from excessive simplification. Collision detail is cooked independently and never selected by the viewing camera's render LOD. Include normal/tangent/material discontinuities in simplification tests and avoid smoothing away the stylized shape language. Terrain detail uses existing material families, with bounded per-partition palettes/weights and optional triplanar mapping for steep or generated surfaces. UV/triplanar scale and normal conventions are declared cook/material settings, not inferred per mesh.

Surface paint records its selected source/patch scope and spatial projection/brush intent rather than raw output triangle indices. Topology edits may require re-evaluation or explicit reproject/remap diagnostics; paint must not migrate invisibly to an opposite cave wall. Surface material/biome channels are separate from geometry and gameplay surface classification. Required footstep/friction/hazard classifications belong to the gameplay cook signature; purely visual blending can remain presentation data. Stacked surfaces must be selectable and paintable independently.

Collision navigation and activation

Reuse Jolt static MeshShape products behind DAE-006 collision APIs. Cook collision from approved geometry with deliberate simplification/error settings, material IDs, sidedness and internal-edge checks. MeshShape is a triangle-based shape; do not assume the renderer's triangle winding or hidden faces automatically produce correct player collision. Validate walking inside caves, overhang undersides, exposed edges and partition seams with CharacterMotor. Static terrain is not an arbitrary dynamic rigid-body triangle mesh; moving solid objects follow the existing body/motor rules.

Bake navigation inputs from the same approved gameplay geometry and explicit walkability/area/link metadata. Recast accepts triangle geometry and rasterizes it during navmesh generation, so runtime terrain need not remain a voxel field for navigation. Its final integration, agent settings and stacked-layer navigation belong to DAE-017. Terrain edits report stale nav data and prevent declaring an invalid slice ready. Traversal links, climbable surfaces and water restrictions are authored metadata, not guessed from visual materials.

Editor geometry rebuild stages coherent render, collision and required nav/scatter generations. Preview swaps at subsystem boundaries; failure preserves an explicitly stale last-valid preview. Shipping terrain is cooked immutable content initially. DAE-009 ContentReady requires necessary gameplay collision; cosmetic placeholders cannot stand in for missing cave floors. Network clients/server use the same gameplay manifest and approved collision identity; platform render LOD/artifact differences do not establish separate gameplay worlds. Live terrain topology reload in network play remains disabled.

Splines and terrain interaction

Splines are reflected native assets/components with stable curve, knot and segment IDs, cubic Bezier positions/tangents, optional width/profile/roll and explicit local/world transforms. Sampling settings and seeds are versioned. Editing produces a deterministic sampled path with arc-length data and continuous orientation frames, including a declared treatment of closed-loop twist. Zero-length segments, cusps, self-intersections and degenerate profiles are diagnosed. Generated segment placement IDs derive from stable logical segment identity and declared sample keys, not current editor selection order.

Typed spline generators produce roads/paths, fences/walls, pipes and river geometry or placed assembly instances. Each declares dependencies, collision policy, navigation influence and scatter-exclusion regions. First support mesh sweeps and repeated placements plus explicit endpoint/junction assets. General road intersections and automatic watertight networks require a separate robust generator; do not claim that two overlapping ribbons make a valid junction. Width, UV distance, banking and profile variation are inspectable source properties.

Terrain deformation from a spline is an explicit scoped modifier with projection direction, falloff and target surface/solid. It is not an automatic effect of drawing a path. An ambiguous projection over a cave/bridge requires selecting the intended surface; no global downward ray should flatten every stacked layer. Apply valid source/solid modifications before partition cooking, with junctions and affected products included in the dependency closure. A river spline can generate water presentation and gameplay volumes; hydrology, erosion, fluid simulation, buoyancy and flood propagation are deferred rather than implied by a water mesh.

Biomes scatter and interactive vegetation

Biome definitions are typed assets with weighted vegetation sets and conditions such as density, slope, elevation, surface class and exclusion regions. Support both surface paint and explicit 3D volumes so cave interiors/ceilings are not forced into a single outdoor height mask. Scatter layers reference stable prototype AssetIds, layer IDs, seeds and versioned sampling recipes. Regenerate deterministically in cooker workers, storing approved placement transforms/IDs; clients do not independently regenerate authoritative objects from floating-point noise at load time.

Separate dense decorative scatter from gameplay entities. Grass and non-interactive foliage live in batched instance buffers grouped by prototype/material and spatial bounds, without an ECS entity per blade. Initial culling is CPU cell/cluster culling feeding DAE-005 instance draws; GPU-driven culling/indirect draw compaction and impostor systems remain deferred. Prototype render LODs are cooked and validated, with alpha/transparency/shadow/wind policy matching the renderer. Wind is presentation, not authority for collision or traversal.

Give interactive candidates stable ScatterInstanceIds independent of compacted buffer indices. A recipe revision defines its candidate-key space; filtering/density changes should preserve surviving candidate identity, while a changed generation algorithm requires an explicit compatibility/remap decision. Cooked placement records, not a seed alone, establish authoritative positions. Important props may be promoted to ordinary DAE-012 placements with their own persistent identity; promotion removes the matching decorative record without creating duplicate render/collision ownership.

Trees, harvestables and obstacles have explicit gameplay collision/entity policies. Use simplified collision shapes where appropriate, and spawn full simulation entities only where interaction/lifetime requires them. Server-owned cutting/harvesting records the stable instance state and updates visibility/collision through validated gameplay operations. Save format and streamed-state restoration are DAE-020/016 responsibilities; define the identity hook now without inventing that protocol. Grass bending can be visual-only. Falling trees and moving branches cannot keep an obsolete static collider while appearing elsewhere.

Acceptance gates and staged delivery

Build a representative hillside with an overhang, an arch and a cave below a walkable surface; include a narrow passage, sharp ledge and material-painted cave wall. Verify imported/native solid operations, invalid Boolean diagnostics, source undo/redo, stable paint scope and cold/warm recipe builds. Exercise CharacterMotor across cave entrances, internal edges and partition boundaries. Measure edit latency, peak cook memory, triangle counts, artifacts and collision cost at intended world detail before selecting partition/detail budgets.

Test adjacent partitions at supported LOD combinations for gaps, shading/material seams and lost entrances; verify collision/nav remain camera-independent and coherent after rebuild. Add a road/fence/pipe spline and river presentation, with degenerate/closed curves, a cave-adjacent deformation target and an explicit road junction. Scatter an outdoor biome plus a distinct cave biome, regenerate/filter layers without retargeting interactive IDs, promote one tree and cut another under server authority. Test failed worker jobs, stale results, packaging/headless collision and DAE-009 content readiness. Required navigation validation continues in DAE-017.

The initial required capability is authored 3D mesh terrain with coherent collision, spline generation and batched scatter; advanced volumetric sculpting, gameplay digging/destruction, erosion, dynamic nav rebuild and GPU foliage systems are deferred. Manifold integration, meshoptimizer LOD quality, terrain authoring tools and all acceptance/performance checks remain unimplemented by this research. If real-time terrain editing becomes required, revisit this decision rather than assuming the deferred voxel path is already provided.

Decision Record DAE 016 World Streaming

Status: LOCKED - approved 7 October 2026; implementation validation pending

Locked direction and first slice scope

Use a DarkAngel-owned streaming coordinator over DAE-011 asset loading and DAE-012 cooked spawn plans. One gameplay WorldSession contains one Flecs simulation world and one live Jolt PhysicsWorld, with separate historical/query contexts already required by DAE-006/009. Regions and cells are content and lifetime partitions, not separate ECS, physics or network simulations. Content residency, server simulation activity, client replication interest and render visibility are distinct decisions.

Preserve DAE-009: the first co-op slice keeps the party in one coordinated active region, which may contain multiple cells. Author bounded regions for districts, caves or arenas; stream nearby cells and preload a connected next region. Region handoff waits for the required party readiness and occurs outside active cross-region combat. Independent distant party exploration, cross-region fights and distributed server authority are deferred. Local single player uses the same coordinator and readiness path without remote acknowledgements. Headless hosting loads gameplay products without GPU dependencies.

Alternatives and reusable infrastructure

Unreal World Partition uses streaming sources to request cells and distinguishes loaded from activated content. Its documentation describes destination preloading before teleport and bundling actors that reference one another. Borrow sources and readiness queries; diagnose dependency expansion rather than letting ordinary links silently pull whole districts into memory. Unity Entities sections can load separately but restrict entity references to the same section or section 0, and instantiated prefabs inherit section lifetime unless changed. Borrow explicit ownership while avoiding silent reference loss and accidental deletion of moving actors.

Godot exposes threaded resource requests and readiness polling; obtaining an unfinished threaded load can still block. Asynchronous byte loading therefore does not by itself guarantee hitch-free entity construction, physics insertion or GPU upload. DarkAngel must measure and budget those integration stages. These are design precedents, not comparative benchmarks of the engines.

Reuse Flecs generation-aware entities and deferred structural commands, Jolt body/shape APIs, existing asset handles and worker infrastructure. Detour provides synchronous tile add/remove operations; it does not schedule disk reads or coordinate AI lifetime for us. Tiled navigation integration is a candidate retained for DAE-017. Static cooked tile streaming need not require DetourTileCache, whose rebuild/obstacle facilities should be evaluated only against the navigation requirements.

PhysicsFS provides archive/search-path file access, not ECS, collision, multiplayer readiness or state ownership. Keep loose immutable artifacts initially under DAE-011; consider an archive reader during DAE-021 without adopting path shadowing as gameplay identity. Microsoft DirectStorage offers Windows storage/decompression infrastructure but likewise does not provide world-lifetime policy; retain as a measured future I/O backend rather than requiring it for the first slice. No reviewed facility supplies our complete Flecs/Jolt/Luau/state/network contract as a demonstrated drop-in. This is a fit judgment, not proof that no other implementation exists.

World manifests cells and ownership

A versioned WorldAsset manifest names stable RegionIds and CellIds, full 3D bounds, adjacency/transition gates, root services, source-placement ownership and cooked product/dependency hashes. UUID identities survive rename, edits and repartition; spatial indices accelerate lookup but coordinates are not identity. Regions contain authored cells with optional deterministic spatial assignment during cook. Begin with one simple bounds index and authored region gates; portal/occlusion-driven policies may be added later without changing IDs.

Use complete bounds rather than a ground-height-only grid, so stacked city floors, caves and bridges can be authored independently. Bounds may overlap and an actor or terrain product may span several cells. Each placement has exactly one lifetime owner; additional intersected cells acquire explicit residency dependencies, never duplicate the entity or collider. Keep assemblies requiring atomic creation in one activation group. Large content must be split deliberately by cook or assigned a bounded group, with diagnostics for worst-case dependency cost.

Terrain mesh partitions, render clusters, collision bodies, navigation tiles and streaming cells remain separate units under DAE-015. A cooked product may be shared by several cells. Deduplicate by asset/generation and retire only after all live, staged, GPU and history users release it. Static resource lifetime follows leases, not a recursive delete of editor grouping or transform parenting. Scene roots, session state, players and world services have explicit persistent residency policies.

Sources budgets and staged activation

Streaming sources request a target product set and priority: gameplay players request a collision/simulation safety neighborhood; camera/view sources request presentation content; encounters, moving supports and in-flight actions acquire required pins; teleport/checkpoint travel requests the destination closure. A camera never causes server AI to start or collision to disappear. Server activity uses authoritative sources; clients cannot directly authorize cells by claiming a distant camera or teleport.

Use Unloaded, Loading, Resident, Preparing, Active and Retiring states, plus explicit failure/cancellation status. Resident means validated required artifacts are in memory, not that gameplay exists. Preparing builds staged entities and subsystem resources, applies state, wires required references and prepares scripts without ticking gameplay. Active publication occurs at a named simulation boundary after prerequisites succeed. Server Active, connection readiness and local presentation readiness are tracked separately.

I/O and CPU decode run in bounded background work using immutable results and request generations; runtime loading reads cooked artifacts and does not invoke source importers. The main simulation thread owns Flecs mutations and live Jolt/nav changes. Renderer-owned upload work observes its own budget and fences. Track outstanding bytes, decode memory, prepared entity/body counts, upload bytes and integration time. Share asset requests and cancel obsolete demand; completions from a cancelled/superseded generation cannot activate a cell.

Spread preparation across frames while staged objects remain invisible to normal queries, callbacks and replication. Keep final publication groups small enough for measured tick budgets. If a group is too costly, require cook-time splitting or use an explicit loading transition rather than exposing half an assembly or claiming every activation is nonblocking. Failure unwinds the staged group and preserves the old active region. Script activation side effects occur only after commit under DAE-012 lifecycle rules.

Use an inner required neighborhood, a larger preload neighborhood and a larger unload threshold or minimum residency duration to prevent boundary thrashing. Derive lookahead from approved movement/projectile speeds, braking/transition distance and measured slow-load latency, with authored overrides. Cell size, radii, concurrency and millisecond/byte limits are spike parameters, not universal constants. Under pressure discard optional presentation/preloads first; deny new mandatory admission when its closure cannot fit. Never evict player support or pretend a collision placeholder is valid ground.

References pins and safe retirement

Cross-cell object references serialize stable placement/PersistentIds with the correct world identity. Resolution reports Loaded with a generation-checked handle, Unloaded, Missing or incompatible state; it never silently substitutes a similarly named object. A soft reference does not load its target. Systems can observe resolve/unresolve notifications at safe boundaries, with cancellation when the owner retires. Gameplay state facts such as an unlocked distant gate live in the session state service and can be applied when that gate later activates.

A required live reference is an explicit bounded dependency or residency lease. Validate cycles, collapse intentional cycles into activation groups and report expanded closure sizes during cook. Joint constraints, moving-platform support, active encounters and action-required objects must declare lifetime needs. Leases have owners/reasons and inspectable release rules; timeouts diagnose or cancel work according to gameplay policy, never blindly remove collision under an occupant. Unbounded transitive pins and hidden automatic loads fail validation.

An unload request enters Retiring only when no new work is admitted and required pins can be released. Quiesce affected simulation and nav work; prepare and validate persistent deltas before irreversible cleanup. At one tick-boundary commit, update the authoritative state ledger, cancel owned scripts/tasks/actions, issue lifecycle removals, unregister references and remove bodies/entities. Retain immutable collision/history generations and GPU resources until their independent users/fences release them. A failed capture or preflight leaves the cell active and resumes admitted work; failures after commit use explicit recovery and do not claim an automatic rollback. Unload does not run death/loot/reset behavior; distinguish streamed deactivation from gameplay destruction.

Physics sleep is not permission to unload. A sleeping body can support a player or belong to a constraint island. Keep awake bodies, moving supports, interacting actors and constrained groups active until an explicit policy permits migration or dormancy. Prevent new motion, projectiles and AI paths from entering an unready area through native readiness-aware boundaries. Long actions acquire required cells before admission; a failed extension follows an authored stop/cancel/impact policy within ready space. Do not freeze a remote fight halfway through it just to meet memory limits.

Moving objects dormant state and restoration

Separate authored home placement, current spatial residency and persistence identity. A mobile NPC, dropped pickup or prop changes runtime cell ownership at a tick boundary while retaining its live handle, PersistentId and network identity; it is not destroyed and respawned at each crossing. Before transfer, the destination required products are ready. Update a global authoritative ownership/state index atomically so unloading the original home cell cannot delete the moved object and loading home cannot recreate a second copy.

The host/server owns a session state ledger keyed by PersistentId or DAE-015 ScatterInstanceId. It stores declared versioned component deltas, removed-object tombstones, spawned-object records and current residency. Restore base cooked data, apply the latest ledger state, resolve dependencies, then activate once. Preserve doors, loot, cut trees and encounter progress across cell cycles. Authored checkpoint/rest reset is a separate explicit state operation, not a side effect of loading. DAE-020 defines disk format, migration and crash durability; an in-memory unload capture alone is not a durable save.

Each component declares reset, preserve or explicit elapsed-time reconciliation semantics. Initial dormant actors do not run AI, physics or arbitrary Luau callbacks; preserve timers/state and resume under a declared policy, with no generic catch-up damage or missed one-shot replay. Selected global services may advance session facts independently of cell residency. Offscreen strategic simulation is deferred. Dynamic objects must reach an approved quiescent state or stay pinned, with declared saved motion/support fields rather than backend BodyIDs.

Navigation prerequisites are declared per activation group/agent type. Publish or remove candidate Detour tiles only while affected queries are quiescent; paths carry the relevant nav generation and are invalidated/replanned when topology or residency changes. Do not retain polygon references as persistent save identity or allow an agent to follow a corridor into missing tiles. Keep the active safety neighborhood and in-use links pinned; DAE-017 defines stacked layers, links, agents and behavior authoring. No dynamic terrain rebake is added by this streaming decision.

Multiplayer readiness travel and history

Extend DAE-009 cell messages with WorldSession identity, CellId, server activation epoch, required gameplay-content hash and a per-connection entry/bootstrap revision. Preload acknowledgements refer to that exact tuple. An old ACK, delayed spawn or snapshot cannot resurrect a retired cell or satisfy a new entry. Connection relevance changes do not change the global server activation epoch. Client unloading a visual cell is not a server despawn; interest entry/exit uses existing entity-lifecycle and baseline rules.

For the first slice, server simulation residency includes the coordinated party neighborhood plus declared gameplay pins. Clients may use different visual residency but receive owner-required collision before control/entry; required nav is loaded on the authority that uses it. A slow client remains on a validated safe side of a transition while other already-active simulation continues. A transition timeout produces retry/cancel or the existing disconnect policy, never authority transfer or silently continuing without collision. Size/bootstrap budgets and fresh late join use DAE-009 bounded catch-up.

Teleport or region travel prepares the destination closure, captures a coherent state baseline, waits for required party client readiness, then commits the relocation and fresh owner/interest epochs at a tick boundary. Keep the origin safe until commit, reset interpolation/prediction and revalidate supports. Cancelled/failed travel releases only its own leases and leaves players in the origin. Within-region streaming likewise uses explicit cell transition resync when prediction topology changes, rather than replaying old commands against new geometry.

Historical collision and lag-query contexts retain exact referenced products/proxies for their bounded DAE-006/009 windows. Live retirement may remove bodies while retained immutable shape data remains usable in the isolated history context. Eviction, epoch mismatch or missing history requires explicit resync/query rejection; do not expand history without bound or rewind the live world. Network ACKs govern transport/readiness, not persistence commits. Reliable removal and stale-message handling must pass across separate transport lanes.

Coordinates and large world limits

Streaming controls residency; it does not remove floating-point precision limits. Jolt documents optional double-position mode and query base offsets; its broad phase still has float precision limits. Godot documents precision tradeoffs and additional multiplayer complexity from origin shifting. These support explicit coordinate policy, not a claim that either automatic rebasing or double precision solves all rendering, navigation and protocol issues.

For the first slice, use one fixed simulation origin per WorldSession and the existing float gameplay/replication path. Keep cells, Jolt queries and navigation in that common frame; meshes retain local vertex coordinates. Declare and validate a finite supported session envelope during cook and runtime, including movement, raycast and effect extents. Start precision tests at the origin and up to 2 km away as a candidate envelope, tightening it to measured combat/traversal error limits. Do not present Jolt documentation ranges as a DarkAngel guarantee.

No per-cell origin shifts, floating-origin updates or mandatory double-precision Jolt build are introduced initially. Content beyond the validated envelope requires an explicit world travel/loading boundary with a new WorldSession origin/epoch and safe teardown/bootstrap; it is not seamless distant co-op. Persistent location records identify the world/region and declared coordinate frame rather than assuming one unbounded float map. Larger seamless worlds require a follow-up coordinate decision covering native position types, renderer-relative transforms, nav frames, physics settings and network history together.

Acceptance gates and delivery order

First prove three adjoining cells in one region plus a gated next region, including a cave below a surface cell. Exercise slow I/O/decode, cancelled and stale completions, missing/corrupt gameplay artifacts and oversized activation groups. Measure read/decode/preparation/integration/upload time, tick spikes, peak temporary and resident memory, dependency closure and thrashing. Verify required collision is never removed under a character and preparation never exposes half-wired entities or runs Luau early.

Cycle cells repeatedly with a changed door, looted chest, defeated encounter and cut tree; restore without reset, duplicate spawn or replayed cue. Move an NPC/prop across cells, unload its home and verify identity and state remain singular. Test unloaded soft targets, required-reference cycles, constraint/support pins, task cleanup and failed capture. Invalidate a nav corridor during retirement and require safe replan/stop. Run exact cases headless and with optional rendering assets unavailable.

Validate local loopback, offline LAN and EOS co-op with slow clients, late join, travel cancellation, disconnect during prepare, delayed ACKs/snapshots and repeated entry epochs. No client predicts through missing collision; origin remains valid on failed travel; streaming changes produce bounded resync without duplicate actions. Precision gates cover character jitter, thin colliders, root motion, ray/hit queries, nav seams, UI anchors and rendering at the candidate envelope limits.

Implement manifest/ownership/state interfaces, synchronous safe activation and retirement first; then bounded asynchronous loading, preparation budgets, multiplayer readiness and editor diagnostics. Expose region/cell state, required-product status, source bounds, expanded dependencies, pin reasons, generation/epoch, queued bytes and transition errors through DAE-013 EditorService and DAE-014 queries/jobs. The editor can load selected regions without running gameplay; authoring transactions remain separate from runtime state.

The coordinator, state ledger, network protocol extensions and these acceptance checks have not been implemented or benchmarked by this research. Independent distant parties, cross-region combat, background world simulation, automatic HLOD/occlusion streaming, archive/DirectStorage optimization and seamless floating-origin worlds remain deferred. DAE-017 completes navigation/AI policy, DAE-020 persistence durability and DAE-021 packaging.

Decision Record DAE 017 Navigation and NPC AI Authoring

Status: LOCKED - approved 7 October 2026 with agent-editable assets and Luau node extensions; implementation validation pending

Locked direction and system boundaries

Use pinned Recast for offline navigation baking and Detour for tiled runtime queries/corridors behind DarkAngel NavigationService. Use native NPC profiles, behavior trees for behavior orchestration and a utility selector for eligible combat choices. Evaluate and adopt BehaviorTree.CPP 4.x as the executor behind a narrow adapter, subject to the Windows build, simulation-clock, interruption and instance-cost gates below. Its integration is not yet validated; do not implement a second general-purpose tree executor merely to avoid an adapter.

NPC decisions run on the authoritative host/server. Clients reproduce replicated movement, actions and public state; they do not independently choose attacks or replicate full blackboards/trees. A tree issues movement, targeting and ability requests through the same native APIs as other gameplay. CharacterMotor owns final motion and Jolt collision; Action Composer owns action timing; DAE-008 owns legal activation, cost, tags, interruption and damage. Navigation and AI do not overwrite transforms, move collision bodies directly or inflict damage from decision callbacks.

Decision paradigms and reuse findings

A hierarchical state machine is a strong fit for long-lived modes and explicit transitions. Unreal StateTree combines selectors with hierarchical states, tasks and transitions, and selects states on demand. A behavior tree expresses reusable priority/fallback sequences and running tasks; Unreal demonstrates event-driven reevaluation and observer aborts. Neither approach is automatically event-driven or cheap merely because of its name. Pick one primary authored orchestration model initially rather than maintaining equivalent state-machine and behavior-tree graph products.

Choose behavior trees with explicit commitment and cancellation contracts for ordinary enemies, with utility scoring inside combat and tactical-position nodes. Utility compares the suitability of eligible actions; it should not replace clear authored lifecycle rules or score illegal abilities into validity. Game AI Pro describes integrating utility decisions into an existing behavior tree. GOAP can generate multi-step plans from action preconditions/effects, as demonstrated in the F.E.A.R. paper, but adds planner/world-model authoring that the first combat slice does not yet require. Defer generic GOAP/HTN planners and a second StateTree-style editor; retain a behavior-driver interface so a later boss or NPC can use another policy.

BehaviorTree.CPP is an MIT-licensed C++17 library with typed ports, reusable subtrees, nonblocking stateful actions and transition logging. Its core execution is single-threaded; a blocking node stalls the tree. Running tasks and halt hooks map well to native gameplay requests, provided we supply their clock, cancellation and authority policy. Build it statically through DAE-003; disable optional Groot network and SQLite logger integration initially, while respecting actual dependencies of the pinned version. ROS, native hot-loaded plugins and the library scripting DSL are not engine gameplay requirements.

Recast/Detour is modular C++ under the Zlib license; use offline Recast and runtime Detour rather than importing a whole engine navigation subsystem. DetourCrowd updates and owns agent positions, conflicting with motor-owned root motion, knockback and collision feedback. Do not make it the combat-character mover. Evaluate its separate obstacle-avoidance query helper for desired velocity, with DarkAngel providing neighbors/boundaries and always passing the result through CharacterMotor.

Groot2 is a useful optional external editor/debugger with free and paid feature tiers, not a demonstrated source component for embedding into our Dear ImGui editor. Its public repository contains releases/issues information rather than the editor implementation. The older open-source Qt Groot editor documents compatibility with BT.CPP 3.8 and is in maintenance mode; do not choose an older executor solely to reuse it. Build our integrated authoring/debug views on DAE-013 commands, optionally reuse maintained graph-canvas UI facilities after a separate fit check. No graph-canvas dependency is selected by this research.

Navigation assets baking and stacked surfaces

A NavigationBakeAsset references the approved DAE-015 gameplay geometry, explicit walkable/excluded surfaces, area/cost definitions, navigation bounds, typed links and versioned AgentProfiles. Profiles define radius, height, climb, slope and traversal capability matching the actual motor/capsule. Cook geometry with border padding and measured voxel/detail settings; publish tiles through DAE-011 only after validating seams, clearance and dependency hashes. Rendering LOD never changes navigation. Use separate baked data for materially different clearance profiles instead of assuming one small-agent bake works for a giant NPC.

Recast uses spans/compact heightfields and exposes layered construction, so caves and bridges are not represented as one height per horizontal location. Validate stacked floors and low ceilings from our actual mesh inputs. Keep Detour tile coordinate/layer keys distinct from DAE-016 CellIds; a streamable cell acquires the tiles needed by its active agents. Stable authoring IDs and nav generation track provenance, while runtime polygon references are short-lived backend handles, not PersistentIds.

Projection onto navigation uses bounded horizontal and vertical search, the actor foot position, capability/filter and current floor/connectivity context. Reject an implausibly distant or opposite-level nearest polygon instead of snapping an actor from a bridge into a cave. Spawn gizmos may offer an explicit validated snap preview; runtime path acquisition does not teleport the motor. A spawn must also pass collision clearance, overlap and streaming readiness checks.

Queries corridors and movement feedback

NavigationService returns a versioned request handle and explicit Pending, Complete, Partial, Unreachable, Invalidated, Cancelled or BudgetExceeded outcome, with diagnostics for missing tiles, buffer/node limits and filtering. Arrival has horizontal/vertical tolerance and capability requirements; reaching the end of a partial corridor is not reaching the requested target. Choose hold, replan or failure according to the task, without a tight retry loop. Targets are stable identities or validated points with a declared update threshold, not stale pointers.

Use bounded Detour sliced path searches and a fair queue on the simulation thread initially. Each in-flight sliced search owns its query object, filter and nav generation; do not mix unrelated queries into its state. Cap active requests, iterations, node pools and output lengths, expose saturation and cancel stale requests after actor death, goal change or cell retirement. Publish results at a safe phase after checking request/actor/nav generations. Worker pathfinding may be added later against immutable/versioned snapshots with its own query instances; never mutate live nav data concurrently.

Follow a corridor through desired planar movement and facing requests. CharacterMotor resolves acceleration, gravity, root motion, slopes, collision and achieved displacement at 60 Hz. Feed the actual foot position and velocity back into the corridor follower; do not keep moving an invisible navigation proxy while the body is blocked. After knockback, traversal or a teleport, reacquire a nearby valid corridor under bounded rules or report failure. Use progress/time diagnostics, cooldowns and limited alternate goals for stuck recovery rather than transform snapping.

Local avoidance and global routing are separate. Evaluate DetourObstacleAvoidanceQuery for nearby desired-velocity sampling and begin with bounded separation/corridor steering. Filter neighbors by relevant height/floor and physical interaction so agents on opposite cave layers do not repel each other through the ceiling. Motor collision remains the final safety mechanism. Root-motion attacks, dodges and involuntary movement have declared avoidance policy; steering cannot distort an authored attack arbitrarily. Measure deadlocks in narrow passages and use explicit yield/priority rules where needed.

Doors dynamic obstacles and traversal links

Use stable NavigationLink assets with endpoints, direction, agent capabilities, cost, availability provider and native traversal action. Doors/gates control authored links or deliberately partitioned polygon flags where appropriate; validate that the closed route has no alternative polygon connection through the doorway. Link traversal acquires a task/streaming lease, checks availability and collision, requests the appropriate motor/action behavior and reports actual completion. A link is graph connectivity, not automatic animation, teleport or a guarantee that all agents can traverse it.

First slice navigation covers grounded walking with validated steps/slopes and explicit door/gate links. Add jumping, vaulting, mantling and moving-platform links only as their CharacterMotor/action execution passes its own gates. Airborne knockback and ordinary player movement need not stay glued to a navmesh. General arbitrary moving-platform navigation, flying/swimming volumes and cross-region routing are deferred, consistent with DAE-016 party scope.

An avoidance obstacle does not automatically alter route connectivity. Small transient obstacles use steering and motor checks; a blocking door or gameplay wall needs a declared routing response. Initially replan to known alternatives or report Blocked/Unreachable when no supported route remains. DetourTileCache is an optional future carve/rebuild adapter, not an implied capability of loading static tiles. If used later, publish coherent revisions, cancel affected searches and respect obstacle/update limits. Dynamic Earth Wall placement cannot be treated as a cosmetic obstacle; verify stop/replan behavior before shipping that ability with NPCs.

NPC profiles perception and decision scheduling

An NPCProfile references behavior, nav/steering profile, sensing settings, targeting policy, movement/stance configuration, ability set and utility considerations. Configuration is immutable shared asset data; target memory, task handles, cooldown bookkeeping and blackboard values belong to each actor. Reuse native team/target filters and ability tags. Conditions such as death, stagger and disabled simulation are authoritative lifecycle gates outside slow decision polling; the tree cannot override them.

Perception is a native bounded service using spatial candidates, distance/FOV checks and budgeted Jolt LOS queries. Store observed target identity, last-seen position/tick, confidence/expiry and declared damage/hearing events. Distinguish currently visible, remembered and invalid targets. Profiles declare retention hysteresis, reaction delay, forget/search timeout, leash and return-home policy. Recheck target alive/team/readiness when acting. AI observes approved public gameplay evidence, never hidden future player input or private client prediction state.

Run movement/actions at the fixed simulation rate. Begin ordinary sensing/decision comparisons around 10 Hz with stable staggered scheduling, plus queued completion/target/lifecycle events that request reevaluation at a safe simulation phase. Death/stagger cleanup still happens on the next simulation tick independently of that rate. Bound per-tick node visits, decisions, LOS and tactical/path queries; expose starvation and maximum service delay. Numbers are candidate budgets to measure, not proven performance or latency promises.

For BT.CPP, drive an explicitly bounded one-pass tick such as tickExactlyOnce through the adapter. Do not use tickWhileRunning, sleeps or unbounded wakeup-retick loops on the simulation thread. All waits/cooldowns use simulation ticks; replace or exclude built-in wall-clock/timer nodes that do not meet this rule. Stateful leaves issue a request once, then poll/receive its completion. Async means returning Running while gameplay progresses, not a new thread for every NPC.

Behavior assets typed state and interruption

Use a versioned native BehaviorAsset in JSON with stable node IDs, native node TypeIds or script-node definition AssetIds, typed ports, explicit child order, subtree AssetIds and typed blackboard declarations. Validate control cycles, subtree recursion, missing ports, incompatible defaults and maximum expanded graph size. A cook adapter emits validated BT.CPP construction data/XML and a stable debug identity map; XML names and library-generated UIDs are not durable authoring identity. Backend strings are generated from typed IDs so renaming a key is reference-safe.

Expose a small supported node set initially: sequence, fallback/selector, selected reactive controls, condition, simulation wait/cooldown, subtree, move, face, select target/position, request ability and utility selection. Document restart versus resume and abort semantics for each control. Avoid unrestricted parallel composites; movement/action channels have explicit ownership and compatible concurrent requests. Conditions read declared state, while outputs/commands occur in named phases. The authoring graph cannot access arbitrary native functions or the library scripting DSL.

Each agent has its own tree instance/typed blackboard; immutable definitions may be shared. Blackboard entity values are generation-checked DarkAngel references, with DAE-016 unloaded handling. Distinguish constant profile input, per-instance memory and transient query/task data. Prevent sharing mutable keys unintentionally between subtrees/actors; use explicit parameter bindings. A task generation owns movement/path requests, subscriptions and optional reservations, all released on halt, failure, disable, streaming retirement or destruction.

Halt requests cancellation through the relevant gameplay service exactly once. It does not automatically make an uninterruptible ability cancellable: DAE-008 decides legal cancellation and forced interruption. If a decision branch loses ownership while its action must finish, clear only its owned requests, observe authoritative completion and prevent a competing action from starting. Dead/staggered behavior gates use the native action/ability lifecycle. No stateful leaf submits a new attack on every Running tick or duplicates activation after a delayed completion.

Custom Luau tasks use DAE-004 ScriptAssets and the DAE-012 per-object instance/lifecycle model, with typed properties, a restricted task context and start/update/halt hooks. They return Success/Failure/Running and submit approved commands; task state is per agent/task, budgets and cleanup remain native-enforced. Ordinary tasks cannot yield an uncontrolled coroutine into the executor or write motor/physics/ability internals. Optional long jobs use native handles with cancellation and stale-generation rejection.

Behavior reload stages and validates a new generation. In local preview/play, halt the old instance, migrate only declared typed state or restart at a defined entry, then activate once; failed preparation retains the prior version. Do not serialize running tree stacks, path polygon refs or backend task objects into save files. Network gameplay reload remains restricted by DAE-011. Dormant streamed NPCs restore declared memory under DAE-016/020 and do not tick offscreen or replay missed attack events.

Agent editable behavior and script defined nodes

Behavior topology, ordered children, reusable subtrees, port bindings, blackboard declarations, profile parameters and utility curves are source-controlled, versioned JSON assets. Node-definition descriptors and Luau source are likewise editable assets. Graph positions/layout are separate editor metadata; agents do not need screenshots or a graphical editor to author behavior. Serialize authored configuration and declared persistent memory, not live handles, task stacks or transient engine objects.

A BehaviorNodeDefinitionAsset has a stable AssetId, display/category metadata, schema version, node kind, stable typed input/output/property IDs, defaults, required capabilities and a referenced Luau ScriptAsset. Initial script extension kinds are task/action, condition and utility consideration. Conditions and utility functions are synchronous, bounded and side-effect-free; tasks use start/update/halt with per-agent state and approved command APIs. New control sequences can be authored as reusable parameterized subtrees and exposed as palette nodes. Adding a new generic control-flow primitive with different child scheduling remains a native engine extension, rather than silently allowing scripts to bypass halt/ownership rules.

Provide native generic Luau adapters for those node kinds and register validated definitions from the approved asset manifest when a behavior generation is prepared. New definitions, ports, properties and Luau implementations do not require C++ compilation or a new native BT.CPP plugin. Port schemas use existing approved engine value types and reference wrappers; script-node AssetIds do not register new Flecs component types or bypass DAE-004 reflection limits. The adapter supplies BT.CPP factories/typed conversions and binds instance state, generation checks, authority, error handling and cleanup. Unknown kinds/types, invalid scripts or mismatched ports fail preparation and retain the prior active generation.

DAE-014 discovery exposes current behavior/node schemas and revisions, with descriptions of port meaning and lifecycle. Agents can create a definition plus ScriptAsset, add/reorder/remove nodes, connect typed ports, edit keys/subtrees/profiles and patch bounded UTF-8 Luau source through explicit asset commands. Prepare reports semantic topology/source diffs, dependency/port diagnostics and expected revisions; commit uses DAE-013 transactions and records one undo unit for the related edit. Source writes edit text without executing it. Allowlisted validation/cook and isolated headless/preview jobs separately compile/check Luau, validate graphs and exercise behavior. Manifest-local script references, normal asset ownership and scoped grants apply; no arbitrary shell or gameplay-memory mutation is added.

Editing and adding these scripted node kinds requires no C++ rebuild. Luau checking/bytecode compilation and behavior cooking may still occur through the asset pipeline; this is asset preparation, not a native engine rebuild. A changed node schema identifies affected bindings and requires explicit migration or reports errors rather than silently rebinding by name. Local preview/play reload uses DAE-004/011 staged generation replacement; network matches continue to use approved content and require the existing safe restart/publication policy. New low-level engine APIs or new primitive port types may require C++ work, but ordinary new tasks, conditions, utility scorers and subtree behavior do not.

Acceptance gate: an agent creates a custom Luau task and its node-definition descriptor, adds it to two NPC behaviors with different typed properties and runs isolated validation without a C++ rebuild. Also create a condition, utility scorer and reusable subtree; change/rename a port while retaining its ID; validate incompatible schema changes; undo/redo the multi-asset edit; reject stale revisions; and prove per-agent state, task cleanup, script budgets and failed reload retaining the prior generation. These capabilities are required by the locked contract and remain to be implemented.

Combat utility spacing and encounter coordination

A utility selector first asks native ability rules for eligible options, then scores authored considerations such as valid range, LOS, facing, cost, cooldown, role, target vulnerability, recent use and commitment. Normalize curves and show each contribution; define the no-eligible fallback and handle non-finite/invalid scores. Use stable tie rules and an owned seeded random stream only where the profile requests variety. Score updates have hysteresis/minimum commitment so close scores do not cause oscillation; eligibility is rechecked on actual activation.

Preferred combat range is a soft positioning band, not a global condition that blocks every attack outside one exact distance. Individual abilities retain their real reach and targeting requirements. Melee/ranged profiles choose approach, hold, strafe, retreat or reposition with reachable candidates, clearance, LOS and maximum query budgets. Lost LOS/target triggers authored search, wait, approach or return behavior; an unreachable target does not cause endless direct movement into a wall.

Provide authored burst/recovery rules, maximum consecutive activations and recovery/reposition windows through profile data. Accepted ability/action receipts advance these counters; rejected requests do not become phantom attacks. Combo continuation uses Action Composer windows and native ability requirements rather than tree-level animation timers. Boss phase gates are explicit observable state and profile/subtree choices, with preemption/commitment semantics instead of score changes silently cancelling cinematic or critical attacks.

An EncounterCoordinator may grant bounded attacker/position reservations to avoid every melee NPC crowding and attacking simultaneously. Ownership, expiry, target lifetime, fairness and release on death/halt/unload are explicit. Start with a small optional concurrent-attacker limit and simple reachable positioning candidates; advanced formation, tactical cover queries, squad planning and a full EQS-style product are deferred. Perception/navigation stay usable without the combat coordinator for patrol/dialogue NPCs.

Editor diagnostics and acceptance gates

NPC Designer edits profile references, abilities, sensing/range/recovery curves and behavior parameters through DAE-013 transactions. A minimal integrated tree view exposes node/port schema, child order, subtree bindings and validation; live debugging overlays active nodes and task outcomes without turning runtime memory into authoring defaults. Navigation tools expose bake bounds/profiles, stacked surfaces, area costs, links, unreachable spawns, tile seams and explicit rebuild jobs. DAE-014 agents use the same typed edits and allowlisted jobs. Agent editing covers the full serialized behavior topology, custom node descriptors and Luau source through the validated asset-edit operations described above; it is not limited to profile parameters or selecting existing native nodes.

Diagnostics show perceived/remembered target evidence, current behavior and abort reason, utility eligibility/scores, chosen goal, corridor/partial outcome, pending query budget, motor desired versus achieved movement, progress failures, link/reservation ownership and nav/cell generations. Use bounded status-transition traces sampled on the server; production clients receive only required gameplay state. Local preview may pause/step its separate world; do not pause a live co-op authority through an external debugger.

Validate pinned Windows Recast/Detour and BT.CPP builds with optional network/log plugins off. Prove two agents sharing assets with independent blackboards/task state, typed subtree/port migration, tick-clock waits, Running request deduplication, halt cleanup, noninterruptible ability completion and script error/timeout. Measure instance initialization, steady tick cost, node allocations and decision/LOS/path saturation. No executor is assumed to supply an enforceable per-node time limit for arbitrary blocking native callbacks; allow only reviewed nonblocking nodes and apply Luau budgets.

Navigation gates cover stacked bridge/cave floors, narrow corridors, different capsule profiles, stairs, seams, partial/unreachable goals, queue starvation, dynamic walls/doors, collision clearance at spawns and actual motor feedback after knockback/root motion. Stream/remove a tile during pending searches and following; stale results must fail, links stop safely and no agent walks into unready cells. Validate relevant coordinate envelope and tile/node/reference limits; performance budgets come from measured slice data.

Build melee and ranged enemies with acquisition, loss/search/return, approach, spacing, one accepted attack, recovery and optional encounter slots. Verify no combo spam, no attack from a dead/staggered actor, no unreachable-target treadmill and no frame-rate-dependent decisions at 30/60/144 rendering FPS or headless. Late join observes the correct ongoing action without running a second AI. Library adapters, editor tools and these acceptance checks remain unimplemented by this research; the locked contract does not claim production-ready combat behavior.

Decision Record DAE 018 Visual Effects Authoring and Runtime

Status: LOCKED DAE-018 - 7 October 2026; implementation validation pending

Recommendation and reuse findings

Select pinned Effekseer Core as the reusable particle/effect executor behind DarkAngel VfxService, with an Effekseer renderer adapter using Diligent and a bounded initial feature profile. Keep native weapon trails and decals as specialized engine presentation components. Effekseer supplies substantial effect authoring and playback functionality; DarkAngel supplies asset identity, composition, attachment, timing, multiplayer reconciliation, budgets and lifecycle. The backend choice and engine contract are locked; the renderer and authoring acceptance gates remain required implementation checks. No ready-made Diligent integration is established by this research.

Effekseer is MIT licensed. Its documentation describes sprite, ribbon, ring, model and track renderers, replaceable resource loaders, dynamic inputs and triggers. Ordinary particles simulate on the CPU; GPU particles are a separate, more limited feature. Its native DirectX 12 examples take an application device, queue and command list. These facts make integration plausible, but using its stock graphics backend is not the same as integrating through Diligent resource-state tracking and our render graph. Reuse the device-independent Core and suitable RendererCommon facilities after checking the pinned implementation.

SPARK is a portable C++ particle library, but the reviewed repository does not demonstrate the complete artist workflow and Diligent integration we need. DiligentFX provides rendering and post-processing components; its listed facilities are not an authored combat-effect runtime/editor. A complete custom Niagara-style GPU graph would add a compiler, scheduler, renderer, editor and debugging product. Prefer the Effekseer adapter spike before paying that cost. No alternative is rejected on an unverified claim about maintenance or performance.

Effekseer currently saves editable/runtime-capable .efkefc documents and retains compatibility with older .efkproj/.efk formats. Its documented command-line interface can open, save and export effects without activating the GUI. Do not assume an editable modern effect is plain JSON or adopt the old project format as our permanent schema without a compatibility test.

The separate MIT-licensed effekseer-ai project reports Core-API document creation, node/property/curve editing and export, verified by its author with Effekseer 1.80.6 on Windows. Evaluate its bridge code and document API approach as reusable tooling. Its small public history and self-reported compatibility are not engine acceptance evidence. DarkAngel owns its command contract and may implement a small isolated Core helper directly if the bridge cannot satisfy identity, validation and transaction requirements.

Assets and agent accessible authoring

A versioned VfxDefinitionAsset uses native JSON with stable component IDs, typed parameter IDs, defaults/ranges, resource AssetIDs, transforms, curves, bounds, quality tiers and lifecycle policy. Components reference an EffekseerEffectAsset, WeaponTrailDefinition, DecalDefinition or an existing native mesh presentation primitive. Composition defines named events and explicit relative delays; Action Composer remains the owner of attack timeline timing. Editor layout is separate metadata. New ordinary effects and reusable compositions require data edits and cooks, not a C++ rebuild.

An EffekseerEffectAsset retains one authoritative editable source document plus a versioned import descriptor. JSON inspection snapshots are derived views of that document, not a second effect graph that can drift. Maintain engine stable IDs for nodes and exported parameters through a tested mapping/metadata scheme. Native source paths or sibling indices are revision-scoped adapter addresses, not durable identity. External editor edits must reimport with conflict checks; ambiguous identity changes require explicit rebinding or invalidate mappings rather than silently targeting another node. Full source round-trip with unknown supported fields preserved is an acceptance gate.

Expose schema discovery, node creation/removal/reordering, property and curve editing, resource binding and semantic diffs through DAE-013 EditorService and DAE-014 agent commands. For the supported feature profile, agents can create an underlying effect, not merely adjust a wrapper tint. Run the Effekseer document API in a bounded isolated tool process over staged files; prepare against expected revisions, validate/export, then commit source and identity metadata as one undoable transaction. Failed jobs leave the previous source and cooked generation intact. Source commit and subsequent preview execution are distinct operations.

Reusable VFX modules can be JSON compositions and Luau controllers using declared typed parameters and approved play, update, trigger and stop commands. Generic bridges load these descriptors/scripts without native recompilation. Luau orchestrates effect instances; it is not an unrestricted callback for every particle. Effekseer dynamic expressions remain its bounded presentation mechanism, with supported inputs validated at cook. Existing renderer primitives and exposed APIs can create new effects without C++ compilation; a new low-level simulation operator, graphics primitive or engine API may still require native work. This does not promise that arbitrary new Effekseer node implementations can be supplied in Luau.

Map named engine parameters to validated backend inputs and capabilities. Effekseer documents four external scalar dynamic inputs; do not advertise unlimited parameter bindings. Color, scale, target and triggers use supported explicit APIs where available. Unsupported parameter types or backend features fail validation with an actionable message. New native shader-family work follows DAE-005; approved HLSL source changes use the DXC cook pipeline and do not imply C++ hot loading.

Renderer integration and initial feature profile

Implement sprite, ring, mesh particle, ribbon and track drawing through a Diligent adapter, reusing compatible common geometry code rather than implementing another particle simulator. Start with CPU simulation, approved Unlit/TransparentVFX materials, alpha/additive blending, textures and bounded curves. Validate model/resource translation through the pinned Effekseer loaders and DAE-011 cook pipeline. GPU particles, arbitrary Effekseer material graphs, screen-space distortion, particle lights and scene collision are deferred until their adapters and costs are proved. Reject unsupported content at cook; do not silently render it incorrectly.

Render graph passes declare all color/depth reads, writes, uploads and transitions. Use the DAE-005 initial graphics queue and engine submission/fences; the VFX subsystem does not create another swapchain or submit work independently. A stock DX12/Vulkan renderer is useful as a reference or isolated preview comparison. Production use of native interop would require explicit Diligent state invalidation/restoration and lifetime proof on both backends; prefer a Diligent implementation of the renderer interface. The first spike must estimate this work before broad effect authoring starts.

Validate handedness, axis conventions, meters, matrix layout, depth convention including any reversed depth, camera transforms and color-space conversion. Record whether assets use straight or premultiplied alpha, then apply the matching shader/blend contract. Transparent effects normally depth-test without writing depth and render into HDR scene color before tone mapping and screen UI. Soft intersections require a valid sampled depth input. Distortion, when added, needs an explicit scene-color copy and bounded sampling; feedback into the same target is invalid.

Integrate fog, exposure/emissive limits and outline participation through documented material policy. Sprite depth sorting and additive blending are an initial approximation, not a solution for every intersecting transparent surface. Author effect bounds and validate them over representative animation/parameter ranges. Per-view culling may skip drawing, but effect age and finite lifetime still advance; a hidden loop cannot accumulate unlimited particles or reappear as an ancient burst. Screen-size and overdraw matter alongside particle counts.

Runtime phases attachments and trails

VfxService exists per presentation world/domain, with separate preview and play instances. It owns generation-checked VfxInstance handles, exact asset-generation pins, seed, start time, typed parameter state, attachment and cancellation ownership. Luau/object/action bindings receive narrow handles rather than Effekseer pointers or raw backend handles. Headless authority validates and emits presentation descriptors without creating a graphics device or simulating cosmetic particles.

After authoritative/predicted action updates produce cues, reconcile cue identity and lifecycle; after presentation pose/transform evaluation, resolve sockets and update attachments; then advance bounded cosmetic simulation, build draw data and submit through the render graph. Convert elapsed seconds explicitly to Effekseer 60-Hz frame units. Do not call Update once per rendered frame with its default delta. Use a fixed cosmetic step initially with a bounded accumulator and defined hitch/skip policy; gameplay never waits for decorative particle catch-up. Seeded replay aids preview and visual consistency but is not a cross-platform determinism guarantee.

Attachment modes are explicit: follow an entity/socket, sample the attachment at spawn into world space, or detach on a declared event. Resolve stable socket IDs against the canonical human rig or the unique nonhuman rig; missing sockets report errors or use a declared fallback. Local-space particles follow their emitter; world-space particles retain their spawn transform. Owner destruction, cancellation and cell retirement have defined stop-emission, finish-tail, detach or immediate-kill policies with maximum tail duration. Never keep a raw entity reference after its world/generation expires.

WeaponTrailDefinition samples two authored weapon sockets at bounded presentation-pose intervals and builds a strip from timestamped pairs, with width/color curves, UV policy, finite point capacity and fade lifetime. An Action Composer interval opens/closes emission. Distance/angle subdivision may improve continuity within a hard segment budget. Teleports, correction discontinuities, rig replacement and world travel break the strip so it cannot span the map. The trail is visual; authoritative hit detection uses DAE-007/008 combat poses and hit queries. Effekseer tracks remain useful for particle trajectories but do not automatically provide this exact weapon-sweep contract.

DecalDefinition specifies material, size, normal alignment, depth bias, lifetime/fade and receiver mask. Spawn impact decals from confirmed impact position/normal and declared surface metadata, with separate prediction policy. Use a bounded pool through the renderer decal facilities; attachments to moving rigid surfaces are explicit. Bone-deforming mesh decals and persistent world staining are deferred. A painted hazard circle may be cosmetic, while its authoritative area and lifetime remain a separate gameplay effect.

Networking streaming and resource lifetime

Replicate cue descriptors and persistent presentation state, never individual decorative particle positions. Cue identity includes the relevant world/interest epoch, actor identity, activation ID, stable event/block ID and occurrence ordinal. Owner prediction creates a tentative cue; confirmation promotes or reconciles it, rejection cancels it, and simulation replay deduplicates it. Continuous instances use explicit state/stop identity; disposable one-shots use the delivery/expiry policy from DAE-009. A lost stop message must be recoverable from authoritative state or a bounded lease.

Late join and interest reentry reconstruct current loops/status effects and ongoing action presentation from baseline phase, start time and parameters. They do not replay expired impact bursts. A stale delayed cue cannot cross an interest epoch. Small finite effects may warm up by bounded simulation; expensive/old effects need an authored skip, approximate steady-state or fallback policy. Moving emitters cannot recreate their historical trajectory from only a current transform, so do not promise exact late-join trails. Camera-only and ambient cosmetic effects remain local.

DAE-011 cooks use the exact pinned Effekseer tool/runtime, source and transitive dependency hashes, with registered texture/model/curve/material recipes and backend shader variants. Translate source-relative resources into validated AssetID dependencies and cooked loader mappings; reject escaped paths, missing assets and unsupported features. Tool binaries are build-time dependencies, not production C++ runtime requirements. Use loose immutable artifacts initially. No client source import or arbitrary material compilation is required during a match.

DAE-016 cell retirement stops or detaches owned emitters without unbounded presentation pins holding gameplay cells active. A declared short tail may keep its exact immutable resources until complete; GPU use retires behind engine fences. Hot reload stages a coherent closure, affects new instances by default, and retains old generations for running effects. Preview restart/migration is explicit. Failed source/export/shader/resource validation keeps the last valid generation. Online content changes obey DAE-011 readiness and manifest policy rather than replacing a referenced effect mid-action.

Budgets tools and acceptance gates

Set global, per-effect, per-owner and per-view limits for live instances, CPU particles, trail points, decals, draw calls, transient bytes, lights if later supported and transparent screen coverage. Preallocate/pool bounded instance and geometry storage where appropriate. Quality tiers author lower-cost rates/lifetimes/materials; lower particle count alone may not reduce a giant quad overdraw problem. Prioritize readable attack telegraphs and confirmed combat feedback over decorative ambience. Reserve a simple fallback for essential cues when richer effects are dropped, and expose dropped/throttled counts.

Provide integrated composition/property editing and Action Composer previews, plus external Effekseer editing with deliberate reimport. Preview uses an isolated world and deterministic seed/clock controls for repeatable inspection, without firing damage, network or persistent commands. Debug ownership, active source generation, cue identity/age, attachment failures, bounds, culling, warm-up/skips, pool saturation, draw counts and CPU/GPU costs. An agent can invoke bounded validation and preview capture jobs through the existing job service.

Before adopting broadly, build the pinned native Core statically on Windows and prove Diligent D3D12 plus early Vulkan sprite/ribbon/track/ring/model rendering, alpha/additive behavior, depth, camera conventions, resource reload, device teardown and fence retirement. Compare supported outputs with the stock reference renderer. Test small effects and dense combat scenes; measure adapter cost and transparent overdraw. The shared graphics path, source identity/round-trip and Core helper are feasibility gates, not completed work. If the adapter is disproportionate, revisit the backend decision with measurements before building a second full VFX engine.

Prove an agent creates an effect with two nodes and a curve, binds textures, edits/reorders nodes without rebinding stable identity, prepares a semantic diff, commits, undoes/redoes and previews it without a C++ rebuild. Test stale revisions, external-editor conflicts, invalid sources, unsupported nodes/materials and failed export retaining the old generation. Verify two instances have independent parameters and Luau controller state; new modules load through descriptors and scripts.

The combat slice needs a weapon slash trail, confirmed hit burst/decal, charge loop, status aura, projectile attachment and a readable area telegraph. Verify acceptance/rejection and action replay produce one cue, cancelled loops terminate, late join recreates ongoing effects without historical bursts, owner/cell retirement and world travel release resources, and a teleport breaks the trail. Test 30/60/144-Hz rendering, hitches, culling/reentry and saturated budgets. Confirm cosmetic particle collision and missing VFX never change damage, AI, motor motion or simulation outcomes. These checks remain unimplemented by this research.

Decision Record DAE 019 Audio Runtime Mixing and Authoring

Status: LOCKED DAE-019 - 7 October 2026; implementation validation pending

Recommendation and alternatives

Select pinned Amplitude Audio SDK behind DarkAngel AudioService, reusing its authored events, collections, switches, RTPCs, buses/ducking, channel priority/virtualization, sound banks, effects and spatial pipeline. Amplitude owns audio execution and mixing; DarkAngel owns AssetID integration, object/action bindings, editor transactions, cue reconciliation and lifecycle. Use its default miniaudio device driver rather than maintaining a separate direct-miniaudio event runtime. This reduces engine-owned audio code while preserving data-driven authoring. Implementation and listening checks remain pending.

Amplitude is Apache-2.0 licensed and documents JSON-defined project assets compiled to runtime binaries. The repository states that its API is stable and no breaking changes will be introduced before the first release. Adopt on that stated commitment with an exact tested commit and matching schemas/tools recorded by DAE-003/011; the commitment is not a guarantee about defect-free behavior or every future content schema. The reviewed release page contains no official release, which is recorded as current project status rather than a reason to reject the selected direction. Native SDK upgrades remain deliberate dependency updates.

Direct miniaudio remains a credible lower-level alternative and supplies Amplitude device I/O, but would require more engine-owned event, switch and voice-policy implementation. SoLoud offers buses, filters and virtual voices but similarly needs our authored event integration. Prefer Amplitude because its existing game-audio abstractions cover more of the intended engine workflow. Do not create a parallel event interpreter or a second mixer to reproduce features that the pinned Amplitude build already supplies.

Amplitude exposes sounds, collections, switch containers, events, attenuations, effects, RTPCs, buses, pipelines and bank definitions as data. Its engine configuration includes active and virtual channels, spatial modes and object pools. Verify the exact supported schema/API at the chosen commit, then use those facilities directly through a narrow adapter. An uncovered requirement gets an explicit extension or deferred scope; do not infer that every advanced audio feature is complete merely from a feature checklist.

FMOD Studio and Wwise offer commercial authoring/runtime ecosystems and remain credible future backend choices. Their free indie options have eligibility, project registration and license conditions; they are not unrestricted open-source engine dependencies. FMOD separately lists engines among non-game uses requiring custom licensing, so a free game license cannot be assumed to cover distributing DarkAngel as middleware. Do not select them based on price alone. This proposal avoids that dependency for the initial engine, without claiming their tools cannot be automated.

Use Amplitude stereo spatialization initially and evaluate its own HRTF/Ambisonic modes with a vetted HRIR/AMIR asset and CPU budget when headphone localization is needed. Engine coordinates and dataset licensing/attribution are part of that validation. Steam Audio remains an optional future acoustic-propagation integration if required; it is not needed merely to obtain HRTF already offered by Amplitude. Full reflection/path baking and diffraction are deferred.

Serialized assets and agent authoring

AudioClipAsset references preserved source audio with import settings, spatial channel intent, loading mode and validated loop/cue metadata. AudioProject assets expose the pinned Amplitude sound, collection, switch-container, event, attenuation, RTPC, effect, bus, pipeline and bank schemas through DAE-001 reflection/validation. Reuse their execution semantics instead of designing an equivalent generic event graph. Engine metadata supplies AssetIDs, stable node/action/property IDs, references, revision and editor layout. MusicDefinitionAsset adds engine encounter/transition policy only where the SDK does not already express it.

Maintain one canonical versioned authoring representation with Amplitude-backed fields and engine identity metadata; generated SDK JSON and compiled binaries are derived cook outputs, not independent editable sources. Map UUID AssetIDs/stable subobject IDs to nonzero Amplitude uint64 IDs through a persisted collision-checked registry, never truncating a UUID or using names as identity. Validate weights, ranges, references, event scopes, bus/pipeline cycles and loop bounds. Entity switches and parameter state must be independent for two actors using the same assets; global bus/music actions require an explicit permitted scope.

DAE-013/014 commands discover schemas, create/edit events, import/reference clips, set curves and concurrency, route buses, author music transitions and generate semantic diffs with expected revisions. Commit through the normal transaction/undo system. Validation and isolated preview/offline capture are allowlisted jobs, separate from source edits. Agents can add an ordinary new event or reusable module without C++ compilation and without automating screenshots of an audio graph.

Luau controllers declare typed inputs and compose approved trigger-event, play/stop, RTPC, switch and mix-state requests through the adapter. A generic bridge loads new descriptors/scripts without native recompilation and keeps independent instance state/cleanup. Ordinary new sounds, collections, events, routing and parameter curves use Amplitude data; Luau supplies gameplay-aware orchestration. It never processes PCM or runs in the audio callback. A genuinely new decoder, native DSP/pipeline node, driver or engine API may require reviewed C/C++ work; static registration follows DAE-003 rather than native hot-loaded plugins.

Clips cooking residency and streaming

Keep high-quality WAV/FLAC masters as source assets. Start runtime short effects with resident decoded WAV and long tracks with streamed WAV, then prefer the official Amplitude FLAC codec plugin for lossless long streams after its pinned build, seek/loop and static-registration gates pass. Miniaudio codec availability does not imply Amplitude exposes that codec: Amplitude documents built-in WAV, MP3 and AMS, with other codecs supplied by plugins. AMS is an available compressed cook alternative subject to listening tests; avoid MP3 as the initial loop-sensitive format. Preserve the master and record the selected codec/quality in the recipe.

Use a candidate 48-kHz content/mix profile with floating-point mixing, adapting output to the negotiated device format/rate. Preserve source masters and explicitly author quantization/dither settings when producing integer PCM; never silently replace the master. Cook validates duration, channel layout, sample/loop bounds, peaks and dependency hashes. Mono is the default for point emitters; stereo music and ambience stay stereo unless an explicit spatial downmix is authored. Report peak/loudness data and clipping without automatically normalizing every clip, which would erase intentional sound-design balance.

DAE-011 cooks produce Amplitude JSON using the exact SDK schemas, compile it with pinned flatc/build tools, and record transitive source/schema/tool/codec hashes. Use SDK sound banks as reference/preload groups; they do not require adopting a monolithic package archive, so loose immutable artifacts remain valid. Translate paths and native IDs through the engine loader/FileSystem adapter. Bank registration and underlying sample readiness are separate stages; unload reference-counted banks only after active events/channels and staged reload generations release their dependencies. Each playing stream has independent cursor/decoder state.

Loading, decoding, stream seek preparation and expensive initialization run on controlled workers, never the simulation or device callback. Define event readiness and late policy: a combat one-shot can expire/drop or use a resident fallback; a long loop can start at an approved offset when ready. Do not let async load play an obsolete attack sound seconds later. Handle streaming underruns with a bounded silence/recovery policy and diagnostics, without stalling the game or replaying accumulated samples at high speed.

Threads clocks and ownership

Gameplay remains single-threaded with DAE-002 phases. Use Amplitude documented game/audio/worker thread model: on the presentation control phase, reconcile cues, update entity/listener transforms and RTPCs, then call AdvanceFrame with the correct elapsed-time units at the defined cadence. The SDK driver runs mixer callbacks and SDK workers perform loading; do not build a competing mixer command loop. Pass generation-qualified snapshots, not Flecs/Jolt pointers. Completion and device notifications return through bounded adapter status records; callbacks never directly execute Luau/gameplay.

The audio callback processes prepared SDK pipeline state without engine file I/O, source parsing, logging, general heap allocation, gameplay locks or user scripts. Amplitude documentation describes preallocated mixer buffers and lock-free command queues; verify those paths, capacities and overflow behavior in the pinned implementation and custom plugins rather than treating the documentation as measured timing evidence. Perform bank initialization, unsafe graph replacement, teardown and device recovery through documented safe boundaries. Measure callback deadlines and streaming behavior under contention.

AudioInstance handles carry world/domain and generation, exact source-generation pins, ownership, physical voice or logical loop state, cue identity and cancellation policy. Stop requests are idempotent. A finite tail has a bounded retirement deadline. Keep backend sound/data-source/node memory alive until audio processing can no longer reference it; freeing it immediately after a game-side stop is invalid. Device loss enters a recoverable muted state while the game continues. Rebuild on the control thread, with current loops/music restored under declared policies and expired one-shots discarded.

Map simulation/action time to local audio presentation time and timestamp cue requests with explicit late/expiry policy. Amplitude event Wait actions and AdvanceFrame are not automatically a sample-accurate music scheduler. Use the pinned SDK channel/event timing APIs where proved, and test simultaneous-layer starts and transition offsets. Gameplay attack timing/damage never waits for audio. Slow motion, preview scrubbing and hitch recovery have declared per-category rate/seek behavior rather than pitching all audio blindly.

In solo pause, world-effect playback/clock policy can pause while UI and optionally music remain active. A co-op menu does not pause the authority or all other players audio; local attenuation is a presentation option. Separate preview and play domains prevent editor auditions sharing game variation state or leaking voices. Headless authority uses a null AudioService that validates/produces cue descriptors without a sound device, decoder workload or dependence on audio-completion callbacks.

Mixing voice limits and music

Provide Master, Music, SFX, UI, Ambience and Voice/dialogue buses initially, with optional SFX sub-buses such as weapons and abilities. Bus topology and effect/send chains are data; sliders use decibels in authoring and validated linear gain at the backend. Smooth parameter and snapshot changes to avoid clicks. Snapshot composition has explicit priorities, weights and ownership/release rules so menu, underwater and cinematic changes do not silently overwrite each other.

Reuse Amplitude effect assets, bus ducking and approved built-in pipeline nodes for gain/filtering, spatialization, occlusion/obstruction and output protection. The reviewed pipeline documentation includes Limiter and Clamp nodes; verify configuration, placement and sound in the pinned implementation before advertising their behavior. Reserve headroom and meter bus/master sample peaks and clipping. A clamp is not a transparent limiter, and no true-peak mastering guarantee is assumed. Evaluate the SDK effect/room support for a bounded reverb send before adding new native DSP.

Use Amplitude priorities and active/virtual channel policy for backend voice management. Add engine concurrency groups only for per-event/per-owner gameplay presentation constraints not covered by the SDK. Author reject-new or fade/replace behavior and reserve budget/priority for telegraphs, feedback, UI and music. Cosmetic repetitions may be capped. Under queue pressure, coalesce superseded position/parameter updates while preserving stops and cleanup. Expose allocation, virtualization, steal/drop and stream readiness reasons through bounded diagnostics.

Candidate slice limits are 64 active channels, 192 virtual channels and 8 simultaneous streams, validated against the pinned Amplitude configuration and target hardware. Reuse SDK virtualization rather than maintaining a second engine logical-voice simulator. Test whether virtual channels advance, pause or resume by seek for each codec/loading mode, and author the resulting inaudible-loop/one-shot policy explicitly. Virtualization must not become unbounded decode, allocation or catch-up work; readmission of a stream needs bounded prefetch and seek behavior.

Initial music supports authored track crossfades through Amplitude channels, faders, buses and RTPCs. Prepare all required streams before changing state. Phase-aligned stems and beat/bar transitions are conditional extensions: prove a shared start/seek and scheduling contract in the pinned SDK, including readiness failure and device recovery, before enabling them. BPM/meter and matching sample lengths are necessary but do not alone establish alignment. If SDK controls are only frame/buffer-granular, keep first-slice track crossfades and defer exact stem/bar synchronization instead of introducing a second mixer.

A small engine MusicDirector maps typed intensity/encounter state to authored Amplitude events, switches and RTPC/fade requests. Reuse SDK event timing; add only uncovered policy. Luau can request a music state through approved APIs but cannot schedule sample callbacks. Do not seek music on every frame or prediction correction. Replicated encounter state may guide local presentation without guaranteeing identical sample timing across clients. A DAW, generative composition and arbitrary live instrument graph are outside initial scope.

Spatial audio acoustics and world lifecycle

One listener represents the local player view, not every remote co-op player. Its camera-oriented rotation and authored player/camera position blend are explicit for third-person combat. Validate meters, handedness, front/back, left/right and height from engine transforms. Point sources use authored attenuation distance, rolloff, directional cones and gain bounds. Disable Doppler for ordinary combat by default; enable it selectively with reliable presentation velocity and reset it at teleports/corrections.

Attachments declare entity/socket following, a sampled world-space impact, or listener-relative 2D playback. Match stable socket IDs through DAE-007 rig assets and declare missing-socket fallback. Smoothed observer transforms position cosmetic audio; they do not change server attack/hit timing. If NPC hearing is gameplay, emit a separate authoritative NoiseEvent with radius/tags and perception rules. Audio-device volume, mute, occlusion, voice stealing or local quality must never determine AI sensing.

Start occlusion with bounded staggered Jolt acoustic queries against declared receiver/material masks, excluding the emitter/listener bodies. Smooth the resulting attenuation and low-pass values. It is an approximation, not diffraction or a full room model; a visible occluder is not automatically an acoustically opaque wall. Reverb zones use stable authored 3D volumes, priorities and blends into a bounded shared send. Caves/bridges and nested zones need actual spatial tests. Defer portals, reflection baking, diffraction and Steam Audio scene geometry until an acceptance spike.

DAE-016 regions/cells own ambient emitters and zones. Use presentation residency/preload interests to prepare nearby sound assets without forcing all referenced gameplay cells to remain active. Cell retirement cancels owned loops, releases zones and permits only declared bounded tails with immutable resources pinned. Entity destruction and world travel invalidate attachments and old commands. Persistent global music and session buses have explicit session ownership rather than being accidentally owned by a retiring cell.

DAE-011 reload stages clips, SDK definitions, pipelines and bank closures coherently. New events use the new generation; running channels retain old resources until an explicit stop/restart or supported transition. Verify whether SDK asset/uint64 ID registries permit concurrent generations; if not, serialize replacement after affected instances drain or use a tested separate namespace/preview engine strategy. Never replace live bank data in place merely because AssetID is stable. Failed cook/load/graph validation retains the prior generation. Online changes obey approved manifests/readiness.

Networking and acceptance gates

Use DAE-009/018 cue identities with world/interest epoch, actor, activation, stable event/block ID and occurrence ordinal. Predict permitted owner whooshes/charge sounds, promote matching confirmation and fade/stop rejected predictions. Prediction replay does not trigger a second sound. Hit/damage outcome audio is confirmed unless a separately reconciled cosmetic prediction is explicitly authored. Already-heard speculative audio cannot be undone; design predicted sounds accordingly and reserve definitive impact/death cues for accepted results.

Replicate event descriptors and current loop/status state, not PCM or physical voice assignments. Author late-play expiry, restart/seek and seed/variation policy. Select important variants from a cue seed/confirmed choice when consistency matters; ambient choices may stay local. Late join or interest reentry reconstructs ongoing loops at an approved phase without replaying expired attacks. Reliable/current state or bounded leases recover lost loop-stop messages. Tombstones/epochs reject stale delayed cues after world travel, despawn or interest exit.

First gates build the pinned Amplitude SDK/default driver statically on Windows, compile a representative JSON project using its matching schemas/flatc, and prove native ID mapping, file-system integration, bank/sample readiness and asset retirement. Validate no-device startup, negotiation, unplug/default-device change, safe shutdown, pause and domain separation; confirm SDK singleton/shared-state constraints before supporting simultaneous preview/play engines. Measure callback load, audible latency, underruns, memory, channel/queue saturation and virtual-stream costs in dense four-player combat. These are integration tests, not reasons to reproduce SDK functionality.

Author a layered weapon whoosh, confirmed hit, surface-switched footsteps, projectile loop, status loop, ambience/reverb zone and encounter music crossfade. Test variation independence, bus/snapshot release, mono spatial placement, stereo preservation, distance/cones, occlusion smoothing, teleport Doppler reset, phase-aligned stems, loop boundaries and click-free stops. Check peak headroom with all categories active and verify voice exhaustion preserves required telegraphs or their authored fallback.

Prove an agent creates a new event/curve and Luau controller, binds clips, changes routing and concurrency, prepares a diff, commits, undoes/redoes and performs isolated preview/capture without C++ compilation. Reject bus cycles, invalid loops, stale revisions and missing assets. Verify acceptance/rejection/replay emits one cue, late join restores only current loops, retirement cancels ownership and missing audio leaves combat/AI unchanged. These acceptance tests, editor tools and service code are not implemented by this research.

Decision Record DAE 020 Persistence Save Slots and Migration

Status: LOCKED - approved 7 October 2026; implementation validation pending

Locked direction and reuse findings

Use pinned SQLite as the durable save-slot container, with versioned JSON gameplay records produced by DAE-001 serialization. Use native PersistenceService over the DAE-016 authoritative session ledger; the host/server owns capture, disk writes and restoration. Reuse SQLite transactions, recovery, integrity checking and backup APIs rather than implementing a storage engine. Keep the asset catalog/cache database separate: a save contains player/world state and is not a rebuildable asset index. Initial saves restore at declared safe checkpoints, not an arbitrary frame inside combat.

SQLite is public-domain C and documents application-file-format use, atomic transactions and online backup. It fits a local authoritative writer and an inspectable cross-platform container. Its guarantees depend on the configured journaling/synchronization, working filesystem locks and honest storage flushes; a successful transaction is not a claim that defective hardware cannot lose data. Pin its build through DAE-003 and validate the target Windows filesystem/driver path.

One JSON snapshot with correctly flushed temporary-file publication and backups is a viable small prototype alternative. Multiple independent JSON files require a coherent revision/manifest protocol to prevent mixing world and inventory revisions. SQLite gives the engine a reusable transaction boundary and incremental record access. JSON remains the record payload and export/debug format; binary database bytes are not intended for direct text editing.

Cereal supplies C++ archives and class versioning, while FlatBuffers supplies schema-based binary access and controlled field evolution. Neither supplies the gameplay identity, checkpoint policy, storage transaction or world/content migration contract. Directly archiving native C++ object graphs would also bypass DAE-001 stable property IDs and declared script state. Reuse the existing engine serializer initially; a future binary payload codec needs measurements and must preserve the same versioned record contract. Amplitude use of FlatBuffers does not require using it for game saves.

Authority ownership and save scope

A SaveSlot has a stable UUID, lineage, display name and monotonically increasing committed revision. A slot contains campaign/world-instance identity, shared progress and its player roster/character records under one snapshot revision. WorldDefinition AssetID, saved world-instance identity, runtime WorldSession epoch, PersistentId, AssetID and NetworkId remain distinct. Renaming a slot changes its label, not its identity. Branch/copy operations allocate a new slot identity and preserve internal object identities within that branch.

For the initial co-op policy, campaign progress and in-campaign character progression/inventory live in the host slot. Guest clients receive replicated state and cannot upload inventory/world facts as trusted save data. Player-record binding comes from the session authorization/roster service, using mode-appropriate account/profile identity; it is not a client-selected record key or a transient connection index. Offline local-profile IDs do not imply online authentication. Disconnected roster members retain their latest authoritative records. Importing a personal character between host campaigns and merging progress into each guest solo campaign are deferred explicit policies.

LocalLoopback single-player follows the same host path; GNS LAN and EOS sessions use the same save service without requiring a cloud connection. A dedicated server can own a local slot through the same native interface with a configured storage root and independent worker. Host exit still ends the DAE-009 match; saving does not introduce host migration, server clustering or a remotely shared live database. User settings, remaps, accessibility/audio preferences and editor layouts stay in local profile/workspace storage rather than party world state.

Persist only explicitly declared durable facts: quest/world tags, gates/altar/checkpoint state, claimed/removed pickups, inventory/equipment/progression, encounter progress where authored, destructible/scatter tombstones and persistent dynamic spawns/locations. Snapshot the latest active values plus dormant and disconnected records already in the ledger. A cell that is not loaded must not disappear from the save merely because no live ECS entity exists for it. Required player inventory and world changes use the same transaction boundary, preventing a consumed key from being saved without its corresponding unlocked gate.

Records identities and persistence policy

Each record includes kind, world identity, canonical PersistentId or ScatterInstanceId, native TypeId or script binding identity, schema version and typed payload. Use the DAE-012 stable placement/local-ID mapping for authored objects and a persisted server-assigned identity registry for dynamic spawns. Dynamic spawn IDs are allocated once and retained across save/load; cell crossing never allocates a replacement. Use canonical textual stable IDs in JSON and exact bytes/text keys in SQL rather than converting unsigned IDs through floating-point or signed integer storage.

References serialize world-qualified persistent identity or logical AssetID, with required/optional dependency policy. Never serialize Flecs handles, Jolt body IDs, Detour polygons, pointer addresses or NetworkIds as durable object keys. Authored-object state overlays the current compatible cooked placement; removed-object tombstones prevent resurrecting consumed pickups, cut scatter instances or moved/despawned objects. A persistent spawn record includes definition AssetID, owner/world/location and declared state; loading home and destination cells cannot recreate two copies.

DAE-001 metadata marks saved properties explicitly and declares Preserve, ResetAtCheckpoint, Elapsed or Transient semantics, consistent with DAE-016. Store the complete current durable overlay at capture, not an unbounded command history or every default/runtime field. Asset/schema provenance makes default handling explicit when content changes. Missing fields use version-specific migration/default rules rather than silently taking whatever current asset default happens to exist.

Do not persist animation pose buffers, active hitbox windows, prediction histories, physical contacts, navigation corridors, tree executor stacks, callbacks, task subscriptions or decorative particles/voices. Checkpoint load reconstructs legal actor state through native lifecycle rules and restarts behavior drivers. Equipment/static grants are re-established without double application; transient actions/tasks are absent. Persistent gameplay effects or cooldowns require an authored reconstruction record and policy; they are not inferred from a live library object.

Store duration/cooldown state as declared remaining ticks/time with its tick-rate/version, not a raw process clock. Offline elapsed-time progression is opt-in and bounded; default loading does not simulate missed damage, AI ticks or farming rewards. Saved wall-clock timestamps are metadata unless a specific policy uses them. Persist a dedicated gameplay random-stream state when durable outcomes require it; cosmetic randomness need not be saved. Locations include world/region and the DAE-016 declared coordinate frame, with finite-range and collision-readiness validation before use.

Consistent capture and checkpoint semantics

A save request carries operation ID, slot identity, expected committed revision, reason and checkpoint policy. Validate authority and readiness, then capture at a defined safe simulation boundary after relevant gameplay transactions and ownership transfers commit. Prepare a coherent immutable snapshot from the ledger plus active persistent participants at one capture tick/revision. Required participants either provide validated data or fail the capture; silently skipping a failed inventory/script record is invalid.

Initial capture may briefly quiesce persistent mutation at a safe checkpoint while copying a bounded state view. Serialize/hash/write the immutable copy on a storage worker; workers never traverse live Flecs, Jolt or Luau state. Do not stretch capture across several changing ticks and call the result one snapshot. If size/time exceeds the configured capture budget, defer/fail with diagnostics; a future versioned immutable ledger/copy-on-write capture path requires its own proof. Cell retirement must finish its ledger transaction before capture or remain wholly outside that revision.

Checkpoint/rest/reset is an authored gameplay transaction. Apply its native changes to the session ledger and capture the resulting coherent revision; disk persistence is a separately acknowledged outcome. If disk commit fails after rest, the live session may have advanced while the previous durable revision remains available. Report that state and permit retry; do not claim automatic rollback of already-applied gameplay lifecycle effects. A game may require durable completion before confirming a travel/save-and-quit flow, but persistence does not silently make every gameplay operation synchronous.

Support explicit checkpoint/manual save requests, configured checkpoint autosave and orderly save-and-quit. Initial load resumes players at the recorded validated checkpoint/spawn policy with required region/collision products ready. Arbitrary exact-frame combat resume and operating-system quick-resume snapshots are deferred. Save completion reports Captured, Writing, Committed or Failed with committed revision and capture time; only Committed means durable success. Shutdown waits for an accepted critical save or exposes failure rather than displaying success on queue submission.

Use one serialized writer per slot with a process/slot ownership lock and SQLite connection confined to that worker. Deduplicate operation IDs; reject stale expected revisions. Bound queued snapshots and retained bytes; coalesce ordinary autosaves only when the later capture includes the earlier required state, while critical checkpoint/save-and-quit requests keep explicit completion semantics. Handle Busy, disk-full, I/O, cancellation and process exit with bounded retries and transaction-state checks. A failed write leaves the head pointing to the previous committed revision.

Database transactions backup and recovery

Initial schema separates slot metadata, snapshots/head pointer and typed records indexed by snapshot, world, record identity and type. All world/player/spawn/tombstone records for a new full snapshot and its head update commit in one SQLite transaction. Keep the previous committed snapshot until later bounded pruning, and retain an external known-good backup for database-level damage. Full snapshots are the first implementation; incremental copy-on-write record storage is a measured extension that must preserve equivalent atomic visibility.

Use rollback-journal DELETE mode and synchronous EXTRA initially for the local single-writer slot; enable foreign-key checks and verify settings after open. SQLite documents EXTRA directory synchronization after journal unlink in DELETE mode. Do not use journal_mode OFF/MEMORY or synchronous OFF for durable saves. WAL can be introduced if concurrent-reader measurements justify it, with its checkpoint/sidecar/backup contract and FULL durability settings validated. A gameplay checkpoint and a SQLite WAL checkpoint are different operations.

On failure, check actual SQLite transaction state, rollback if required, close/reset affected statements and retain the old head; not every statement error automatically rolls back the whole transaction. Save success is emitted only after successful COMMIT under the approved durability settings. Journal creation/flush overhead and snapshot copying are measured off the simulation thread. Bound retained generations and temporary disk use, accounting for the old snapshot, transaction journal, staged new data and backup during low-space handling.

Create backups/exports using the SQLite backup API against a stable committed revision, serializing writes while selecting and copying that revision. Check backup_step completion and backup_finish errors; finish returning success alone does not prove every page was copied. Close/validate the destination and publish its completed file using the platform-safe replacement path. Never copy a changing database file or delete a recovery journal because it appears stale. A crash during backup publication must leave the existing backup or a distinguishable incomplete staging file.

On open, allow SQLite recovery, then validate database/application/container version, bounded structure, snapshot checksums and semantic records. Use integrity/foreign-key checks as appropriate; they do not validate gameplay meaning. A SHA-256 digest over the canonical typed snapshot catches accidental payload inconsistency, not malicious editing by someone who can recompute it. Offer recovery from the previous valid revision or external backup with the revision/time clearly reported. Preserve damaged input for diagnosis and do not silently replace player progress with a newly empty slot.

Loading/exporting is not permission to execute SQL supplied by a save. Use fixed prepared statements, bound parameters, expected schema validation, disabled extension loading and bounded SQLite/JSON limits. Reject unexpected executable schema objects before opening imported data for mutation. File paths stay within the selected save root. Encryption, anti-cheat signatures and remote replication databases are outside the initial persistence requirement; host-authoritative co-op does not become a competitive trust service through a checksum.

Schema migration content compatibility and Luau

Version the SQL container schema, snapshot contract, game/content compatibility and individual component/script payloads independently. Stable TypeId/PropertyId keys survive display-name changes. Migrations declare explicit from/to versions and transform saved data step by step; type/range changes, property removal and defaults have authored meaning. A newer required version without a supported path fails clearly. Optional unknown records/fields may be retained opaquely under an explicit schema policy; loading and re-saving with older code must not silently erase future data.

Before a migration that writes, create and validate a known-good backup. Run container/data transformations transactionally on a staged copy or through a fully validated transaction that preserves the prior original on failure. Verify all transformed records, references, digests and compatibility before publishing the migrated revision. Retain the pre-migration backup for explicit recovery. A failed migration is not a reason to overwrite the save with current defaults or automatically downgrade it.

Store gameplay/content compatibility metadata and referenced logical assets, not a requirement that every old cooked artifact hash remain installed forever. Updated compatible content can restore using stable IDs and migration rules; removed/replaced placement, item, world or region identities need explicit remap/retirement tables. Missing required inventory/checkpoint/gameplay definitions block load with a useful report. Optional cosmetic content may use a declared fallback. Do not silently move a saved actor to a similarly named world or nearest unrelated floor.

Luau bindings save only declared versioned data through the DAE-004 state schema: approved scalars, typed records/arrays, AssetID references and persistent entity references. Reject functions, threads, userdata handles, cycles and undeclared VM internals. Restore new per-instance script state after object population/reference wiring and before activation. A script receives a declared restore lifecycle reason so it does not grant loot or subscribe twice as if this were a fresh spawn.

Allow migrations as versioned declarative property mappings/defaults or bounded pure Luau data transformations registered from shipped approved assets. An isolated migration VM has no World/Physics/network/filesystem capabilities and cannot run scripts embedded in a save. Native serializers validate the transformed result. Agents can add ordinary declared script state and migration data/source through DAE-013/014 transactions without C++ recompilation; new native component fields/APIs still follow the native schema/build contract. Avoid introducing Cereal-specific class macros as a second migration identity system.

Canonical JSON uses stable property keys, deterministic ordering and typed round-trip values. Preserve integer identifiers/counters that exceed safe JSON-number precision as schema-declared exact string/byte encodings; reject NaN/infinity and duplicate keys. Configure bounds for file/snapshot/record size, array counts, reference depth and migration CPU/memory. Native parser/serializer choices follow the existing asset/reflection infrastructure; this research does not silently select a second JSON library.

Restoration networking and authoring tools

Read and validate the selected durable revision on a worker, producing an immutable restore plan before changing the live world. Validate migrations, required assets, object identities, ownership, capacity and checkpoint location. Build or reset the WorldSession through DAE-012/016 stages: prepare compatible content, populate base/dynamic objects, apply persistent overlay/tombstones, wire references, restore declared script/native state, then activate once. Dormant records remain in the ledger until their cells activate; loading a save does not activate the entire world.

For a full load/travel, use the coordinated party transition and a fresh runtime epoch. Cancel old tasks/actions, replication/prediction histories, VFX/audio ownership and references; stage a coherent authoritative baseline and client content readiness before admitting input. Clients receive replicated outcomes, not the database or private host roster records. Late join uses current server state rather than applying the original disk snapshot independently. Saved NetworkIds never carry across sessions.

A clear/reset operation selects the exact slot/profile scope and creates an explicit new campaign state or removes the selected slot according to the UI command. World checkpoint resets, deleting a slot and clearing editor asset caches are distinct commands. Cloud upload/import and cross-device transfer are future storage adapters over complete validated snapshots; concurrent cloud versions require explicit conflict/branch handling rather than last-writer merging inventories. Do not place the live SQLite file on a network share or treat cloud synchronization of journal files as a transaction protocol.

Provide a Save Inspector over typed records and a JSON export with IDs, versions, capture tick, committed revision and reference/migration reports. DAE-014 agents discover persistence schemas, author rules/migrations and run bounded round-trip/recovery jobs. Editing gameplay saves is limited to explicit development fixtures/copies through revision-checked typed commands with undo/diffs; production slot inspection is read-only by default. No arbitrary SQL, live host memory mutation or automatic editing of a player save follows merely from authoring access.

The acceptance slice preserves a claimed pickup, inventory/key consumption plus gate unlock, altar checkpoint, encounter state, a cut scatter instance, a moved persistent object and a dynamic dropped item through cell cycles, save/quit and a fresh host session. Verify disconnected player records survive, guest join cannot overwrite another record, LocalLoopback/LAN/online share authority semantics and headless saves need no GPU/audio device. Equipment/effects/scripts activate exactly once; no duplicate loot or actors appear when loading home and destination cells.

Test fault injection during capture, transaction inserts, head commit, journal flush, backup and migration, plus disk-full, locked slots, malformed JSON, duplicate IDs, missing required content and future schemas. Recover a complete old or new revision without mixing inventory/world state; report fallback revision. Test component/script migrations, unknown optional preservation, counter precision and invalid restore positions. Measure capture pause, worker time, memory and disk footprint on the intended world scale. These service implementations, schema tools and crash/durability tests remain unimplemented by this research.

Decision Record DAE 021 Build Packaging and Platform Delivery

Status: LOCKED - approved 7 October 2026; implementation validation pending

Locked direction and reuse findings

Use the DAE-003 C++20 CMake/Ninja/MSVC toolchain, pinned vcpkg graph and static internal targets, extended with CMake install components, CTest and CPack. Start with a relocatable Windows x86-64 game directory delivered as a ZIP, an independently staged developer tools package and a separate headless/server package as its implementation becomes available. DarkAngel owns a small versioned BuildProfile and orchestration layer over these tools plus the DAE-011 cooker; it does not implement a compiler, dependency manager, installer framework or content storage engine.

CMake presets cover shared configure/build/test/package workflows, and CPack packages files selected by install rules, including ZIP archives. Runtime-dependency scanning helps collect linked shared libraries but cannot discover every explicitly loaded SDK binary, resource or data file. Maintain an explicit runtime allowlist and test the staged result. CPack source packaging is a different operation; never distribute the source tree by mistake when producing the game.

Conan, Meson and bespoke scripts offer alternative build workflows, but replacing the already locked CMake/vcpkg choice provides no demonstrated advantage here. Installer and storefront tools should consume the same validated staged directory later. SteamPipe already provides depot/build/branch upload facilities; there is no reason to make an engine patch CDN or launcher for the initial slice. No storefront account, upload or release is created by this decision.

Platform scope and executable boundaries

Windows x86-64 with MSVC and Diligent D3D12 is the first supported editor and game platform. Qualify the first release on Windows 11; exact supported OS builds, minimum GPU feature level, drivers and hardware budgets are recorded from integration tests rather than inferred from the words DirectX 12. Windows 10 compatibility is a separate measured support entry, not an implied guarantee. Preserve the locked early Vulkan validation path, initially on Windows where practical. Linux/headless portability influences platform interfaces now; a Linux shipping game/editor and Steam Deck support require later qualification. Apple, mobile, consoles and browser targets remain deferred.

Separate internal library targets from Editor, Game, Headless/Server, Cooker and validation executables. A shipping Game does not link Dear ImGui editor panels, ImGuizmo, authoring/undo services, importers, MCP bridge or the development command endpoint. Runtime UI remains RmlUi. Development game builds may expose the existing explicitly enabled diagnostics/test profiles. Strip authoring and agent endpoint registration at build time for Shipping, rather than relying only on a hidden menu or a runtime preference.

Headless binaries use the same authoritative gameplay, navigation, persistence and protocol code with null presentation adapters. They must not load Diligent, RmlUi presentation, Effekseer rendering or audio-device backends merely to bootstrap. Select server runtime data by declared dependencies, including collision, animation/combat data, navigation and Luau where needed; server content is not simply a copy of the full client render/audio bundle. A public server package remains an optional later deliverable, not a prerequisite for EOS peer hosting.

Dependency pinning runtime linkage and prerequisites

Keep one checked-in dependency manifest, pinned vcpkg checkout/registry baseline, exact overrides where necessary, approved source exceptions and patch checksums. Preserve the resolved transitive graph, features, triplet and toolchain in build provenance. A baseline provides default/minimum package versions and is not a complete transitive lock by itself. Record exact tested MSVC tools, Windows SDK, CMake, Ninja, DXC, flatc and cooker versions when implementing the skeleton. Host build tools and target runtime libraries are separate dependencies; players do not need a compiler or flatc.

Use static linkage for internal modules and source dependencies that support it, with a consistent MSVC dynamic CRT policy through CMake and a matching vcpkg triplet. Static libraries and a static CRT are separate choices. Use /MD for optimized runtime targets and /MDd only for developer Debug; never distribute debug CRT DLLs. Deliver the authorized Visual C++ redistributable prerequisite for the tested runtime version through the distribution/install instructions or storefront prerequisite support. Reuse Microsoft servicing rather than silently switching the whole graph to /MT just to hide prerequisites.

Some SDKs, notably EOS, have separately distributed runtime binaries and their own terms. Import those as explicit pinned platform artifacts and include the authorized runtime files required by the chosen integration. Respect C API ownership and allocator rules across external DLL boundaries; do not pass C++ standard containers or free SDK allocations with an unrelated allocator. Static-first is not a promise of one executable with no DLLs.

EOS peer networking does not by itself justify adding the crossplay Social Overlay. Epic documents a separate service redistributable/bootstrapper for the overlay and related account/social experience, with storefront-specific behavior. Ship it only if those features are selected and follow the current SDK/storefront requirements. LocalLoopback and GNS LAN must remain usable offline regardless of EOS login or overlay availability. Product/deployment configuration and the appropriate public-client policy are release inputs; privileged server credentials, signing keys, personal tokens and developer authentication tools never enter the client package.

If the renderer selects a DirectX Agility SDK version, stage its approved runtime components in the exact executable-relative SDK path and match the exported version. Do not ship development SDK layers. Otherwise use the qualified system D3D12 path. Vulkan shader products are cooked separately and runtime driver/loader requirements are checked. Backend portability does not mean a single shader binary or GPU driver supports all targets.

Build profiles and cooked content closure

A versioned JSON BuildProfile declares project identity, target platform/architecture, native preset/configuration, renderer backend, content roots/labels, client/server role, feature flags, network deployment selection and output kind. Stable IDs identify roots and referenced profiles; machine-specific paths and credentials are local/CI inputs. Schema validation rejects incompatible features and unknown required settings. Agents can edit profiles and request allowlisted cook/build/package jobs through DAE-014, with bounded diagnostics and artifact results, without arbitrary shell access. Adding Luau behavior or an authored node remains an asset cook operation; extending native services still requires a rebuild.

Use separate Debug, RelWithDebInfo and Release build directories already required by DAE-003. Add an explicit Shipping feature profile using optimized native settings, appropriate diagnostics and no developer endpoints; do not equate a Release compiler configuration with a shipping-safe feature set. The build path is validate profile, resolve pinned tools/dependencies, build native targets, cook declared content, validate closure, stage install components, audit and package. Every stage operates on a frozen source/content revision; report failure without publishing a partially staged result.

The cooker starts from explicit worlds, UI, abilities, actor definitions, registries, save-migration assets and required bootstrap content, then follows DAE-011 dependency kinds. Include declared runtime soft-reference roots and script lookup registries; fail missing required dependencies and unclassified dynamic lookups rather than assuming string-based references will be found by scanning C++. Traverse cycles with stable visited identities. Strip editor-only data deliberately while preserving all runtime semantics. Gameplay and presentation subsets must still satisfy DAE-009 compatibility/readiness rules.

Stage immutable artifacts and a release manifest mapping logical AssetIDs to typed artifact hashes, versions and platform products. Include Luau bytecode and the matching VM/compiler provenance; shader bytecode and material layouts; Ozz animation/combat data; Jolt collision; Detour tiles; RmlUi dependencies; Effekseer effects/resources; and Amplitude banks, samples and referenced SDK definitions according to their locked adapters. Raw meshes/images, editable effect projects, developer databases and workspace layouts are not accidental runtime requirements. Any required runtime source-format document, such as supported UI markup, is an intentional cooked dependency.

Build ID, executable version, protocol/gameplay compatibility ID, content manifest revision and save-schema versions are distinct fields. Embed the release build ID in logs and reports; clients exchange approved protocol/content compatibility before joining. A rebuilt executable need not invalidate every save or byte-identical asset. Shipping loads only the approved release catalog; an editor asset cache or arbitrary loose file in the working directory cannot override it.

Content storage writable data and updates

Retain loose immutable cooked files for the first runtime package, as required by DAE-011. CPack ZIP is a delivery archive extracted before running the game, not a decision to stream runtime audio/terrain from compressed ZIP entries. This keeps initial asset reads and Amplitude long-stream seeking straightforward. Resolve the install root from the executable/configured installation, not the current working directory. The runtime asset interface uses bounded asynchronous reads and logical artifact identity so the storage backend can change without changing gameplay references.

PhysicsFS is a viable open-source archive/search-path reader under the zlib license and would avoid rolling a ZIP/PAK reader. Defer adopting it until loose-file count/startup or distribution measurements justify archives. Its path lookup/override model does not replace the engine manifest, hashes or lifetime rules. If adopted, mount approved containers deterministically, forbid accidental path shadowing, validate paths/bounds and test random seek and streamed audio through the SDK file adapter. Choose container/chunk/compression layout by access pattern and patch size; avoid one compressed multi-gigabyte archive that forces expensive rebuilds or seeks. DirectStorage remains a measured future I/O backend.

Treat installation content as read-only. Saves, user settings, remaps, logs and bounded caches live under a platform user-data directory scoped by product/profile; servers use an explicit writable root. A release update cannot overwrite a campaign database or confuse it with the rebuildable asset catalog. Optional portable developer profiles have an explicit writable directory and are not a shipping assumption. Test non-ASCII names, spaces, read-only installs and launch from another current directory.

Initially replace a complete validated release directory while the game is stopped, or let the distribution platform manage updates. Never overwrite in-use DLLs/artifacts or patch an online match independently. Keep a recoverable previous installation where the updater supports it. Save migration follows DAE-020 and retains its pre-migration backup; executable rollback does not guarantee a migrated save can be read by older code. Hashes detect changed/corrupt files, not hostile replacement of both package and manifest. Trusted signatures/storefront provenance belong to release delivery; modding, DLC overrides and a custom automatic updater remain deferred.

Reproducibility diagnostics licensing and release gates

Use the same checked-in presets and explicit workflow from a clean checkout on CI and a developer command line. CTest runs bounded native/headless tests; the cooker runs schema/dependency checks. CI vendors and binary-cache providers remain implementation choices. vcpkg binary caching reuses ABI-keyed packages and is a performance optimization, not an authority for which dependency version was chosen. Separate trusted cache writes from untrusted builds and do not require a warm cache to produce a valid release.

Record source commit and dirty-state policy, tool/dependency/patch versions, profile, asset inputs and output hashes in a provenance report. Fail release staging from an unexplained dirty tree or mixed revisions. Deterministic content cooks should produce identical artifact hashes for identical declared inputs. Normalize timestamps/order in manifests and archives where supported. Exact bit-for-bit native executables are a separate measured goal because paths, timestamps, link/debug artifacts and signing may differ; version pins alone do not prove it.

Keep matching private PDB/debug symbols and provenance by build ID outside the player package. Retain bounded local startup/crash diagnostics with renderer/device/driver, network mode and content build information; redact credentials and avoid recording whole inventories or personal data by default. Logs and failure messages must work before graphics/audio initialization. Crash upload, analytics and a third-party crash service are deferred; nothing uploads automatically merely because a local diagnostic was produced.

Produce a dependency inventory and third-party notices from the actual resolved runtime/tool graph, including transitive code, codecs, shader tools and fonts/assets. Preserve required license texts and notices, track modifications and redistribution permissions for proprietary SDK/runtime exceptions, and distinguish editor-tool obligations from game-runtime obligations. vcpkg metadata is useful input but does not certify every license condition. Do not redistribute an entire EOS SDK archive, compiler kit or developer credential bundle as engine content. Engine source licensing is a separate product choice and is not settled by these packaging recommendations.

Acceptance begins with a clean Windows build using the documented tools, both cold and cached, followed by a staged game launched without Visual Studio, the source tree, editor cache or development PATH. Test the authorized prerequisites on a clean machine/VM and graphics/network on suitable physical hardware. Verify relocation, a read-only install, non-ASCII user paths, disconnected single-player, offline LAN and EOS online peer play. Confirm Shipping has no authoring/agent endpoint and no unintended editor DLLs; headless starts without a GPU/audio device. Inspect content closure, missing/corrupt artifacts, mismatched protocols, dependency/DLL omissions and clear unsupported-device errors.

Exercise save/load across an update and migration failure, preserve user data on uninstall/update, and verify previous-install recovery without silently downgrading a save. Re-cook a frozen input set twice and compare hashes; compare staged file inventory with the profile/allowlist and license report. Measure cold startup, package size, content I/O, cook time, native incremental build and streaming behavior before adopting archives or a compiler cache. Compile-only checks remain useful during ordinary development, but cannot certify packaging or multiplayer/device behavior. The pipeline, profiles, audits, clean-machine tests and performance results remain unimplemented by this research.
